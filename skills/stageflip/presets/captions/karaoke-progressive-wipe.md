# Karaoke Progressive Wipe — lyric video

The canonical music-video karaoke caption register: line-level lyrics with per-line **progressive left-to-right color wipe** sweeping across the active line as the music plays, three-line stacked layout (previous line dimmed at top, active highlighted in middle with mid-progress wipe, next line preview at bottom), optional outer-glow halo on the active line, ALL-CAPS display-sans typography (Bebas Neue OFL preferred; Anton OFL declared fallback) against a dark canvas. Common uses: music videos, sing-along graphics, karaoke screens, lyric-explainer cards, music-show / social-music graphics.

This preset is the **sixth and final Cluster F preset to land**, closing the cluster to **6/6**, AND the **first Cluster F preset to bind a non-`caption` primitive** — it consumes the `LyricsClip` primitive (T-322), NOT `CaptionClip` (T-316). The two primitives are siblings in the cluster F caption-register space but distinct gap clips: `CaptionClip`'s timing model is transcription-based (per-word `WordTiming[]`), while `LyricsClip`'s is musical (per-line `[startMs, endMs)` windows with a within-line karaoke-wipe progress driven by `(currentTimeMs - line.startMs) / (line.endMs - line.startMs)`). T-367 is also the **first preset to bind any `lyrics`-clipKind**; per the T-362 first-preset-for-clipKind precedent it takes the **clipKind-default** slot in the resolver (`lyrics → lyrics`), NOT the per-presetId override map. Subsequent lyrics presets, if any, would route through `PRESET_ID_BINDINGS` per the T-360 mechanism.

## Visual tokens

The three-line stacked karaoke wipe IS the message. Layout (1280×720 default; vertical compositions preserve the center-screen anchor):

- **Lyric stack** sits at **canvas center** — `position: { x: 128, y: 360, width: 1024, alignment: 'center' }` on the parity composition (10% inset, vertical center, 80% width). At the primitive's default font size 96 (Bebas Neue caps) the longest line in the canonical snapshot (`"WE WERE STRONGER TOGETHER"`, 25 chars) may flex-wrap to two visual lines depending on host font metrics; the wipe still operates per `<text>` element so the parity register reads regardless. Active line at `position.y = 360`; past line at y=280 (y - 80 px default `lineGap`); next preview at y=440 — all three within the 720 px canvas. Center-screen vertical anchor distinguishes T-367 from T-362 / T-365's lower-third (y=432), T-363's upper-center (y=200), and T-366's bottom-of-frame (y=540) in the parity-golden corpus. Same `y=360` as T-364 TikTok, but the three-line lyric stack with karaoke wipe + glow is structurally distinct from TikTok's single-line pill backdrop.
- **Three-line stack** (`maxLinesVisible: 3`, current ± 1 neighbour). The canonical music-video lyric register: past line dimmed above the active, active in the middle, next preview below. T-322 D-T322-7 ships `1 | 3 | 5`; `1` (mono-line) collapses to `'highlight-current'`-style behaviour and loses the lookback / lookahead context that IS the karaoke register; `5` (current ± 2) is the long-form ballad register and too dense for the wipe. **`3` is the canonical pick.**
- **Per-line karaoke wipe**, `style: 'karaoke-wipe'`. Driven by `(currentTimeMs - line.startMs) / (line.endMs - line.startMs)`. Past characters render in the highlight color (default `#F3CE32` yellow); upcoming characters render in `foreground` (default `#CCCCCC` light gray). The wipe is rendered via an SVG `<clipPath>` polygon whose width tracks the per-line ms-progress (T-322 D-T322-4 — stable line-index-derived `clipPath` IDs for byte-deterministic output). The SVG `<foreignObject>` carrying the wipe overlay is masked by a `<rect>` whose width = `karaokeProgress * 100`% of the line's region. Active line at frame 105 sits at exactly 40% wipe progress: `(3500 - 2500) / (5000 - 2500) = 0.40`.
- **Active-line opacity** is full (`1.0`); past / next lines render at the bundle's `muteOpacity: 0.5` — visibly dimmed but readable. The dimming-not-hiding posture is what makes the three-line stack a stack rather than a single mono-card.
- **Light white outer glow halo** on the active line only. `glow: { color: '#FFFFFF', blur: 6 }`. Renders an SVG `<filter>` `feGaussianBlur` halo around the active line's wipe overlay only — past / future lines do NOT glow per T-322 D-T322-6. The `blur: 6` `stdDeviation` produces a perceived halo of ~10 px diameter at the primitive's render coordinates, matching the original stub's "10 px outer glow" prose at a slightly-conservative numerical setting. **Static glow only** in v1; the stub's "100 ms build" animated build-up posture is out of v1 scope (T-322 v1 ships static glow per D-T322-6).
- **Background** is the canvas backdrop — lyric overlays appear against video footage at compose time. The LyricsClip primitive's container is `transparent`; the bundle's `DEFAULT_BACKGROUND: '#000000'` is a default for prop fallback only. The `buildProps.background: '#0E0E12'` declares the dark-canvas music-video aesthetic for documentation alignment with the cluster-E broadcast-register precedent (T-355 / T-356 / T-357), but the primitive may not honor `background` as a full-canvas backdrop; the parity golden therefore renders against the host bundle's default canvas color (D-T367-12 — canvas-bleed quirk inherited from T-322 / T-362). Music-video aesthetic standard is dark-canvas-by-design (lyric overlays appear against video footage which is typically dark-skewed), so any canvas-bleed degradation against a non-dark host canvas is documented but not a parity-blocker.
- **No bounce / no per-word scale.** T-322 ships no per-line bounce or per-word scale pulse; the three style bundles are sealed. The original stub's "bounce on active word (1.0 → 1.05 → 1.0, 200 ms)" alternative is out of v1 scope.
- **No line-fade-out / slide-up cross-fade.** T-322 ships per-line entrance only (`'none'` / `'fade'` / `'rise'`); cross-line fade-out / slide-up is implicit in the stack-shift between frames, NOT a configurable transition. The original stub's "Lines fade out or slide up as the next line appears, 400 ms" prose describes a host-pipeline cross-fade between successive `LyricsClip` mounts at the composition layer, not a per-line primitive transition.

## Typography

- **`preferredFont: Bebas Neue`** (SIL OFL 1.1 via Google Fonts, Dharma Type). The canonical music-video display sans-serif: condensed, all-caps, mass-typographic, stage-light register. License-clean and license-cleared via the StageFlip font pipeline (no BYO posture).
- **`fallbackFont: Anton`** (SIL OFL 1.1 via Google Fonts, Vernon Adams), weight `400`. Reconciled from the original stub's identical-preferred-and-fallback (both Bebas Neue) per D-T367-8: the `LyricsClip` primitive's `DEFAULT_FONT.family` ships `'Bebas Neue, Anton, ${SYSTEM_FONT_STACK}'` — Anton is the OFL face the bundle actually renders when Bebas Neue is not preloaded. Declaring Anton at weight 400 aligns the frontmatter with the bundle's actual fallback chain. Anton is metrically close to Bebas Neue — both are condensed display sans-serifs designed for poster / banner / signage use — so the parity register survives the substitution. Both faces are OFL via Google Fonts; license-clean.
- **`fontSize: 96`** at weight `700` (the bundle's `DEFAULT_FONT`). Heaviest of the cluster F register space (T-362 Hormozi 96 / 800 / caps, T-363 MrBeast 108 / 800+ / caps, T-364 TikTok 72 / 700, T-365 Ali Abdaal 64 / 600, T-366 Netflix 56 / 500). The lyric-video aesthetic IS heavy display caps; weight 700 size 96 is canonical. The original stub's "36–72 pt @ 1080p" prose maps to a 1080p canvas; on the parity 1280×720 composition the bundle's size 96 reads as the equivalent visual register. Tenants on different canvas sizes scale via the optional `font?` prop on the primitive.
- **`casing: 'uppercase'`** (per-preset override; bundle defaults to `'as-is'`). ALL-CAPS canonical posture per the lyric-video canon. Applied at render time via the primitive's `applyCasing` helper — the underlying `lines[].text` payload preserves authored case for transcript editing. The original stub's "ALL CAPS for impact" + "ALL CAPS is canonical for high-impact lyric videos; Mixed Case is acceptable for ballad / acoustic register" aligns: this preset is the high-impact register; ballad / acoustic compositions would use `casing: 'as-is'` at compose time.
- **`letterSpacing` is unset** — defaults to the browser's `normal` (~0). The bundle's font supports manual letter-spacing via `font.letterSpacing` if a tenant wants tighter or looser caps; v1 ships none.
- **Comfortable line widths**: 4–5 words per line, ~24 chars maximum (the longest canonical line `"WE WERE STRONGER TOGETHER"` at 25 chars). At weight 700 size 96 caps, line widths approach the 1024 px position width and may flex-wrap on hosts whose Bebas Neue / Anton metrics are wider than expected. Production tenants split lyrics at musical phrase boundaries upstream; the parity snapshot is illustrative.
- **Tabular numerals are not relevant** — text-heavy register; numeric content uses the bigNumber preset family (Cluster E).
- **Tenants may pass an alternative display sans** (e.g. Montserrat Bold) at compose time via the optional `font?` prop on the primitive — the original stub's "Bebas Neue (default), Anton, or Montserrat Bold per the brief" prose maps to this compose-time override path. Montserrat is NOT in the bundle's actual `DEFAULT_FONT.family` chain; the bundle's chain is `Bebas Neue, Anton, ${SYSTEM_FONT_STACK}`. Compose-time alternatives are tenant choice; the preset contract is the bundle's default chain.

## Animation

- **Per-line karaoke wipe** is the defining animation. Drives `(currentTimeMs - line.startMs) / (line.endMs - line.startMs)` clamped to `[0, 1]`. The wipe is rendered via an SVG `<clipPath>` rectangle whose width tracks the per-line ms-progress (`width = karaokeProgress * 100`%). Wiped portion renders in `wipeColor` (defaults to `highlightColor` when both unset, `#F3CE32` yellow); unwiped portion renders in `foreground` (`#CCCCCC` light gray). Stable line-index-derived `clipPath` IDs (T-322 D-T322-4) make the rendered SVG byte-deterministic across runs; no `crypto.randomUUID()` is used.
- **Per-line entrance**, `entrance: 'fade'` (the bundle's default). Each line fades from opacity 0 to 1 over 12 frames (T-322 `ENTRANCE_FRAMES`) starting at `lineStartMs`. At the parity reference frame 105 (= 3500 ms), all three visible lines have completed their entrance — line 0 (entered at 0 ms, complete at frame 12), line 1 (entered at 2500 ms = frame 75, complete at frame 87), line 2 (entered at 5000 ms = frame 150, but visible in the stack as a preview before its entrance). The `'rise'` entrance variant translates the line up 12 px alongside the fade; T-367 picks `'fade'` for cleanliness against the canvas-bleed register.
- **Active line ms-progress** is the only within-line animation. A line becomes active when `currentTimeMs >= line.startMs && currentTimeMs < line.endMs`. The active line picks `{ wipeColor }` for the past-cursor portion and `{ foreground }` for the future portion; the line's wipe progress sweeps left-to-right linearly with time. No easing curve — the wipe is linear ms-progress per T-322 D-T322-3 (the bundle's three style enums each have sealed semantics; karaoke-wipe is "linear ms-progress").
- **No active-line bounce or scale pulse.** T-322 ships none; the original stub's "bounce on active word (1.0 → 1.05 → 1.0, 200 ms)" prose is out of v1 scope.
- **Static glow halo** on the active line. The glow is a static `<filter>` Gaussian blur (T-322 D-T322-6); no animated build-up over 100 ms. The original stub's "glow on active word (10 px outer glow building 100 ms)" prose maps to a v2 inline-animation enhancement; v1 ships the static halo at `blur: 6`.
- **Cross-line transitions** are implicit. As `currentTimeMs` crosses a line's `endMs` boundary, the line shifts up the stack by `lineGap` (80 px default) and the next line takes its place; this stack-shift is geometric, not animated. The original stub's "Lines fade out or slide up as the next line appears, 400 ms" prose describes a host-pipeline cross-fade between successive `LyricsClip` mounts (each lyric "phrase" being its own mount with snap-cut replacement); within a single mount the stack-shift is implicit.

## Rules

- **Bound primitive**: `lyrics` from `@stageflip/runtimes-frame-runtime-bridge` (`packages/runtimes/frame-runtime-bridge/src/clips/lyrics.tsx`, exported as `Lyrics` + `lyricsClip`). The `lyrics` `clipKind` is in `VALID_CLIP_KINDS` (per `scripts/check-preset-integrity.ts`); the v1 resolver in `packages/parity-cli/src/generate-fixture.ts` routes `karaoke-progressive-wipe` via the **clipKind-default** path (`lyrics → lyrics`) — D-T367-4 mirrors T-362 hormozi's first-preset-for-clipKind precedent. Composing tools should mount `Lyrics` with `style: 'karaoke-wipe'`, a `lines: [{ text, startMs, endMs }]` payload, and a `position` — the bundle supplies font / casing / foreground / highlight / wipeColor / muteOpacity / lineGap / entrance defaults. T-367 additionally declares `casing: 'uppercase'`, `maxLinesVisible: 3`, `glow: { color: '#FFFFFF', blur: 6 }`, and `background: '#0E0E12'` as preset-level overrides.
- **Line-level timing is mandatory.** The primitive consumes `lines: [{ text, startMs, endMs }]`; word-level timestamps break the per-line karaoke wipe (the wipe is per-`<text>`-element, not per-word). Tenants without per-line timestamps must split phrases upstream into line-level data — beat detection / audio-track parsing is a host concern (T-322 D-T322-5; the primitive accepts pre-aligned `lines[]` as data and does not parse audio).
- **`musicCue` is host data, not primitive data.** The original stub's "Without a `musicCue`, the preset is unusable; escalate" prose describes a compose-time data wiring: the host pipeline emits the `lines[]` from a music-track / lyrics-database lookup (or from manual authoring), aligned to the song's beat. The primitive consumes the result; it does NOT decode audio or detect beats. The preset is unusable WITHOUT pre-aligned `lines[]`, but the alignment happens upstream of the runtime.
- **`style: 'karaoke-wipe'` is the canonical enum value.** Three style bundles are available on the primitive (`'karaoke-wipe'` / `'three-line-stack'` / `'highlight-current'`); T-367 picks `'karaoke-wipe'` to match the preset's name and the original stub's "Defining technique: progressive left-to-right color wipe" rule. `'three-line-stack'` (full-line color flip, no within-line wipe) is the ballad / acoustic register and could be a sister preset; `'highlight-current'` (mono-line, no neighbours) is the high-impact mono-card register and could be a sister preset. Both alternative styles are documented but not chosen for T-367's canonical golden.
- **`maxLinesVisible: 3` is the canonical music-video lyric register.** `1` and `5` are out-of-canon for this preset (mono-line and ballad / long-form respectively).
- **ALL-CAPS is canonical for high-impact lyric videos.** Mixed Case is acceptable for ballad / acoustic register (would be a sister preset with `casing: 'as-is'` and `style: 'three-line-stack'`); T-367's high-impact register uses `casing: 'uppercase'`. Tenants must not normalize transcripts to title-case or sentence-case for this preset.
- **Static glow at `blur: 6` is the canonical halo.** Removing the glow (passing `glow: undefined`) loses the lyric-video aesthetic but is not a parity-blocker; tenants who prefer the no-glow register on a tighter-aesthetic composition may override at compose time. Animated glow build-up is out of v1 scope.
- **Center-screen vertical anchor.** The default `position.y` is canvas center (y=360 on the 1280×720 parity composition); tenants on vertical compositions re-anchor to canvas center. The lyric-video canon places the lyric stack at canvas center against the music-video footage; the music-video footage IS the visual context, the lyrics ARE the message.
- **Theme slot mapping**: `background` and `foreground` map to palette roles per `lyricsClip.themeSlots`. Tenant theme overrides flow through these slots at composition time without touching the preset; tenants overriding `foreground` to a non-`#CCCCCC` shade reduce the dim-vs-active contrast (the active line's `highlightColor: #F3CE32` yellow's contrast against the foreground depends on the foreground being light gray, not white) and should reconsider whether the `'karaoke-wipe'` register is the right preset.
- **Reference frame for parity is mid-hold (frame 105)** — `currentTimeMs = 3500 ms` at 30 fps. Line 0 (`'ONCE UPON A TIME'`, 0..2500) is past — renders dimmed at top via `muteOpacity: 0.5`. Line 1 (`'WE WERE STRONGER TOGETHER'`, 2500..5000) is **active** at exactly 40% wipe progress: leftmost ~40% of glyphs in `#F3CE32` yellow, rightmost ~60% in `#CCCCCC` foreground gray. Line 2 (`'NOW WE SING ALONE'`, 5000..7500) is preview — renders dimmed at bottom via `muteOpacity: 0.5`. Soft white outer glow halo around line 1 only. The parity golden documents the canonical three-line stack with mid-progress karaoke wipe — the single frame where all three layers (past + active + next) AND the wipe progress AND the glow halo AND the dim-vs-active contrast read in one image. Frame 60 (line 0 active at 80%) was considered but degenerates to a one-or-two-line stack (no past line above; line 1 below as preview) and misses the canonical three-line register; frame 105 is the clear pick.
- **No live data.** The `permissions` array is empty; no network call, no telemetry source. Audio sync / beat detection / live transcription are host concerns.

## Acceptance (parity)

One reference-frame fixture at `frame: 105` (mid-hold per ADR-004 §D5; D-T367-7):

- `golden-frame-105.png` — three-line stack rendered at the system-stack fallback (Bebas Neue not preloaded; Anton not preloaded — primitive-side FontManager preload concern flagged for follow-up, T-362 carryover) at the bundle's default 96 px / weight 700 caps; **line 0** (`'ONCE UPON A TIME'`) dimmed at top (y=280) at `muteOpacity: 0.5` in `#CCCCCC` foreground gray; **line 1** (`'WE WERE STRONGER TOGETHER'`) **active** in the middle (y=360) showing a left-to-right karaoke wipe at ~40% progress — leftmost ~40% of glyphs in `#F3CE32` yellow, rightmost ~60% in `#CCCCCC` foreground gray, with a soft white outer glow halo (`blur: 6`) around the active line; **line 2** (`'NOW WE SING ALONE'`) preview at bottom (y=440) at `muteOpacity: 0.5` in `#CCCCCC`; ALL-CAPS Bebas Neue / Anton fallback typography; on whatever the host generator's default canvas color is (the bundle's intended dark-canvas register `#0E0E12` is documented in `buildProps.background`, but the LyricsClip container is transparent so canvas-bleed against a non-dark host canvas is documented per D-T367-12). The longest line (`'WE WERE STRONGER TOGETHER'`, 25 chars at size 96 caps) may flex-wrap to two visual lines if the host font metrics are wider than expected; the wipe operates per `<text>` element so the parity register reads regardless — document whichever wrap behaviour lands.

If floating-point drift makes the wipe progress polygon read as `40.0%` vs `39.97%`, acceptable — the parity contract is "exactly one line mid-wiping at clearly-non-trivial progress, two neighbours dimmed, white glow halo on the active line." Document whatever lands.

Thresholds: **PSNR ≥ 42 dB**, **SSIM ≥ 0.98** (stricter than the generator default `35 / 0.95`; mirrors the cluster E / cluster F sister presets per D-T367-11). The preset-driven-thresholds follow-up flagged during T-359b is the formal mechanism for per-preset deviation; for now the threshold values are hand-pinned in `parity-fixtures/captions/karaoke-progressive-wipe/thresholds.json` post-generation. A three-line lyric stack with mid-progress karaoke wipe + glow halo against a dark / canvas-bleed background is moderately antialiasing-sensitive: the wipe-edge `<clipPath>` polygon produces a hard left-to-right boundary that can jitter at sub-pixel boundaries; the SVG `feGaussianBlur` glow filter alpha-composites against the canvas; the past / next dimmed lines depend on the `muteOpacity` resolution path. `42 / 0.98` should be comfortable. If it fails after hand-pinning, escalate (likely a Bebas Neue / Anton font-fallback render-mismatch on the host system, OR clipPath-edge antialiasing variance, OR glow-filter Gaussian-blur variance).
