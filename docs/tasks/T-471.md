# T-471 — `AudienceAiPromptClip`

**Branch**: `task/T-471-audience-ai-prompt-clip`

## Goal

Ship the **AudienceAiPromptClip** family — the THIRD and FINAL Phase
15 marquee differentiator. Voters submit prompts OR upvote
shortlisted prompts; the winning prompt triggers Phase 14 asset
generation (video via Seedance T-430, music via ACE-Step T-432, etc.
per the clip's `targetModality`); the generated asset is then embedded
statically in the static-fallback view. This clip demonstrates the
**cross-product synergy**: audience-driven authoring of AI-generated
assets — a capability Slido / Mentimeter / Poll Everywhere
structurally cannot offer.

Per-kind shapes (already in `@stageflip/audience-contract`):

- Vote: `{ kind: 'audience-ai-prompt', action: 'submit' | 'upvote',
  text?: string, promptId?: string }`. Mirrors LiveQA's dual-action
  shape (submit vs. upvote).
- Aggregation: `{ prompts: readonly { id, text, upvotes }[],
  winnerPromptId: string | null, generatedAssetCacheKey: string | null
  }`. The `generatedAssetCacheKey` references the P14 asset-cache
  (ADR-008 §D1).
- Rendering: TWO states:
  1. **Voting phase** (winnerPromptId === null): prompt feed with
     upvote buttons.
  2. **Generation phase** (winnerPromptId !== null,
     generatedAssetCacheKey === null): "Generating with AI…"
     loading state.
  3. **Final state** (both set): static-fallback embeds the generated
     asset (video tag for `video-gen` modality / audio tag for
     `music-gen` / img for `tts` waveform or image, per
     `clip.props.targetModality`).
- Voter UI: tabbed Submit / Browse like LiveQA. Submit emits `{
  action: 'submit', text }`. Browse renders the prompt feed; upvote
  emits `{ action: 'upvote', promptId }`; per-promptId memo to
  disable already-upvoted.

§13 verification is option-1 — `render-e2e.test.ts` drives the
static-fallback with a known winner + cacheKey snapshot + asserts
the generated-asset element is present + addresses the cacheKey.

## Implementation notes

- **Schema**: `props: { prompt: z.string().min(1), targetModality:
  z.enum(['video-gen', 'music-gen', 'image-gen', 'tts']),
  topN: z.number().int().positive().max(100).default(20),
  maxPromptLength: z.number().int().positive().max(500).default(200),
  sessionId: z.string().optional() }`.
  - `targetModality` values match P14's `AdapterModalityKind` for
    the modalities a voter might want to drive: `'video-gen'` (T-430
    Seedance / T-431 Runway), `'music-gen'` (T-432 ACE-Step / T-433
    YuE), `'image-gen'` (no v1 reference adapter; future), `'tts'`
    (T-426 Kokoro / T-427 Fish-Speech — for voice-driven prompts).
    Note: `image-gen` isn't a P14 modality on `main` yet; including
    it is forward-compat.
  - `permissions: z.tuple([z.literal('audience-network')])`.
  - `provenance: audienceProvenanceSchema.optional()`.
- **Static-fallback rendering**: three-state dispatcher inside the
  pure render function:
  - Voting (`winnerPromptId === null`): render the prompt feed as a
    vertical list with `text` + upvote count per row. NO upvote
    buttons in static-fallback (it's read-only at this layer).
  - Generation (`winnerPromptId !== null, generatedAssetCacheKey ===
    null`): render a "🪄 Generating with AI…" placeholder with the
    winner prompt text.
  - Final (`winnerPromptId !== null, generatedAssetCacheKey !==
    null`): render the winner prominently + the generated asset
    element per `targetModality`:
      - `video-gen`: `<video src={...cacheKey} controls />`
        OR `<div data-cache-key={cacheKey} data-modality="video-gen" />`
        (the test's choice — emit BOTH for testability).
      - `music-gen`: `<audio src={cacheKey} controls />`.
      - `image-gen`: `<img src={cacheKey} alt={winnerPrompt.text} />`.
      - `tts`: `<audio src={cacheKey} controls />` (TTS produces
        audio).
    - Below the asset, render the full prompt feed (read-only). Total
      label reads `${prompts.length} prompts`.
  - Cache-key URL resolution: defer the actual scheme/URL resolution
    to a future task. Emit the cacheKey as a `src` attribute directly
    (browsers will fail to load it; tests assert on the attribute
    being present + correct). Document this in the static-fallback
    TSDoc.
- **Live-mount rendering**: identical state dispatch; upvote buttons
  rendered in the prompt-feed list. Updates via WebSocket snapshot
  events.
- **Voter UI** (`audience-ai-prompt-voter-input.tsx`):
  - Tabbed Submit / Browse (mirror LiveQA's pattern from T-464).
  - **Submit**: `<textarea maxLength={maxPromptLength}>` + submit
    button. Emits `{ action: 'submit', text }`.
  - **Browse**: prompt list with upvote button per row. Emits
    `{ action: 'upvote', promptId }`. Local memo of upvoted
    promptIds to disable after upvote.
  - Once `winnerPromptId !== null`, both tabs disable + show
    "Voting ended. Winner: …".
- **Mirror T-470 exactly** for layout / tests / dispatcher registration.
- **Determinism perimeter**: same as prior — static-fallback pure;
  factory's `runAudienceClient` is the only non-deterministic surface.
