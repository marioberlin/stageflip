# T-358a — `outcome-row` runtime-clip primitive (row of N color-coded shapes)

**Branch**: `task/T-358a-outcome-row-primitive`

## Goal

Ship a small generic frame-runtime-bridge clip — `outcome-row` — that renders a horizontal row of N independently color-coded shapes (chips). The primitive is the missing piece that blocked T-358 (`cricket-ball-by-ball-dots`): the Implementer surveyed every existing clip in `packages/runtimes/frame-runtime-bridge/src/clips/` and confirmed none cleanly carries the visual register "row of N independently colored shapes":

- `kpi-grid`'s Zod schema constrains `columns: 2|3` and `rows: 2|3` (rejects 6×1) and ships heavy dashboard chrome with no per-card color override slot.
- `timeline-milestones` has a single shared `accentColor`, no per-milestone color.
- `audio-visualizer`, `stock-ticker`, `comparison-table`, `chart-build`, `pie-chart-build`, `line-chart-draw`, the chart family (T-406), and every dashboard composite either lock color globally, model a different geometry, or impose props (axes, scales, labels) the chip-row use cases don't have.

T-358 surfaces the gap first, but the same primitive is needed by Cluster B's `cricket-scorebug` (T-336+), tennis tiebreak mini-points, F1 sector-history rows, soccer last-N-shots indicators, and any future scorebug-family preset. Building `outcome-row` once as a reusable generic amortizes the cost across multiple presets; the per-cluster prop-builder logic (cricket-outcome → color mapping, etc.) lives in `parity-cli` resolver shims, not in this primitive.

T-358a is **S-sized**: ~50–80 LOC component + ~30–50 LOC tests + index exports + 1-line skill-catalog row. It does NOT touch T-358's preset markdown, the parity resolver entry, or the parity goldens — those land in the T-358 retry PR after this primitive merges.

## Architectural decisions

### D-T358a-1. Generic `outcome-row` vs cricket-specific `score-bug-dots`

T-358a ships a **generic** primitive named `outcome-row`, NOT a cricket-specific `score-bug-dots`. Rationale:

- The shape "row of N independently colored chips" recurs across at least four cluster B/E preset families: cricket ball-by-ball (6 dots), tennis tiebreak (~7–13 mini-points), F1 sector-history (last N sectors), soccer last-N-shots (on / off-target indicators). A cricket-specific clip would need re-implementation for each.
- Cluster-specific semantics (cricket outcome → color, tennis won/lost → color) belong in the `parity-cli` resolver's `buildProps` shim, not in the runtime primitive. The primitive accepts pre-resolved `{ color, label? }` chips.
- The primitive is small enough (~50–80 LOC component) that the genericity cost is zero. Reviewer should reject the spec if `OutcomeRow` grows cluster knowledge.

If a Reviewer demands the cricket-specific name, escalate per CLAUDE.md §6 — the multi-cluster reuse evidence is the spec's anchor.

### D-T358a-2. Maximum chip count — 12

`chips` array bounded `1..12`. Rationale:

- Covers the longest plausible row in cluster B/E presets: a tennis tiebreak runs to 7 winning points but can extend; a cricket over with no-balls / wides / free-hits can reach ~12 deliveries; F1 sector history fits 6–10 comfortably.
- Higher bounds invite layout pathologies (chip width below ~50px on a 1920×1080 canvas at 80px padding). If a future preset needs 16+, the cap is a one-line bump after layout review.
- Below the cap the schema is permissive — the chip width is `flex: 1` per chip; spacing is uniform.

### D-T358a-3. Shape variants — `circle | square | rounded` (default `circle`)

v1 ships exactly three shapes. Rationale:

- Circle (default) covers cricket dots, tennis points, soccer indicators.
- Square + rounded-square cover F1-style sector blocks and hockey-style outcome chips.
- No diamonds, triangles, or custom SVG paths in v1 — keeps LOC envelope small. Each is a one-conditional-branch addition for future presets.

Implementer's leeway: name the literal `'rounded'` or `'rounded-square'` — pick one and stick with it; document in TSDoc.

### D-T358a-4. Per-chip color (required) + theme slots for fill / outline (optional)

Each chip's `color` is **required** (that's the whole point of the primitive). The schema rejects chips missing `color`.

Theme slots are **optional convenience** for cluster owners who don't want to specify every chip explicitly. v1 exposes:

- `defaultFill`: theme slot `palette.surface` — used as the chip's fill when no per-chip color overrides are set (rare, but useful when the preset's compass source defines a single default with rare exceptions).
- `outlineColor`: theme slot `palette.foreground` — drawn around every chip uniformly; cluster owners can null it out by passing `outlineColor: 'transparent'`.

Per-chip `color` always wins over `defaultFill`. The primitive does NOT silently fall through to a theme slot when `color` is `undefined` — the schema requires `color`, so the fall-through never executes.

### D-T358a-5. Entrance animation — staggered fade-in matching the chart-family pattern

Per CLAUDE.md §3 the clip is frame-deterministic. v1 entrance:

```ts
// per chip i, with delay = i * 4
const opacity = interpolate(frame, [delay, delay + 12], [0, 1], {
  extrapolateLeft: 'clamp',
  extrapolateRight: 'clamp',
});
```

For 6 chips this settles by frame 4*5 + 12 = 32; for 12 chips by frame 4*11 + 12 = 56. Both well inside a typical 60fps mid-hold window. T-358's parity fixture renders at frame 60, so all six chips are fully opaque.

The pattern matches `kpi-grid`'s spring stagger (200ms / ~12 frames) and the chart family's per-element fade-in. No spring physics — `interpolate` keeps the LOC count honest. If the Reviewer demands spring matching, document and pick the closer match.

## Test plan

`outcome-row.test.tsx` cases (5–8 — Implementer trims to fit coverage):

1. **Schema accepts minimal valid input** — `outcomeRowPropsSchema.parse({ chips: [{ color: '#000' }] })` does not throw.
2. **Schema rejects empty chips** — `.parse({ chips: [] })` throws (min 1).
3. **Schema rejects over-cap chips** — `.parse({ chips: <13 chips> })` throws (max 12).
4. **Schema rejects chip missing color** — `.parse({ chips: [{ label: 'x' }] })` throws (color required).
5. **Render at frame 60 produces N chips with correct colors** — render `<OutcomeRow chips={[{color: '#f00'}, {color: '#0f0'}, {color: '#00f'}]} />` at `frame=60`; assert three chip elements (data-testid `outcome-row-chip-0/1/2`) with the expected fills.
6. **Render at frame 0 produces chips with opacity 0** — same render at `frame=0`; first chip's opacity is 0 (or near-zero); validates entrance window pre-start.
7. **Stagger ordering** — at `frame=10`, chip 0 is partially visible (opacity in (0, 1)) and chip 5 is still at opacity 0; validates `delay = i * 4` ordering.
8. **Determinism** — render the same props twice at frame 60; the rendered HTML strings are byte-identical (catches accidental `Date.now()` / `Math.random()` use).

Test environment: `@testing-library/react` + `vitest`; `FrameProvider` wrapper provided by the bridge per existing test patterns (see `kpi-grid.test.tsx` if it exists or the bridge's test-setup.ts).
