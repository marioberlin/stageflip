# T-411a — TenantSettings storage layer

**First downstream PR of T-411** (parent spec merged in #472, commit
`f25405d8`). Implements the **storage layer only** per T-411 §D-T411-1 +
§D-T411-2: extends `@stageflip/storage` with a `TenantSettingsStore`
contract and ships implementations on the in-memory, Postgres, and
Firebase adapters.

Strict scope: NO API, CLI, permission-shim, or UI. Those land in:

- **T-411b** — tRPC router + CLI (`tenantSettings.get / setInteractive
  / list`; `stageflip tenant set-interactive`).
- **T-411c** — permission-shim wiring for the interactive runtime host
  (D-T411-4 mount-time matrix).
- **T-411d** — docs cross-link + `skills/stageflip/concepts/tenant-settings/SKILL.md`.
- **T-411e** — admin UI (deferred per T-411 D-T411-7).

The parent T-411 spec covers all design decisions. This sub-spec covers
the storage carve-out: file touches, AC subset, test posture, and the
3-adapter parity that makes `T-411b` (and downstream consumers) able to
pick the adapter at boot without changing the consumer code.

## §13 (structural extension) statement

**NOT a structural extension.** Adds a new storage facet to existing
storage adapters. No new clipKind / element type / compositing mode /
runtime kind. Render verification N/A — no rendered output changes.

Per CLAUDE.md §13, the structural-extension obligation applies to
changes that add a new degree of freedom to the document model, the

storage adapter does not meet that bar.

## Architectural decisions

All design decisions are inherited from the parent T-411 spec. This
sub-spec only restates the storage-relevant ones for inline
reviewability.

### D-T411a-1 — Re-statement: extend, don't fork (per T-411 D-T411-1)

The new `TenantSettingsStore` ships as a **separate facet interface**
in `@stageflip/storage`, NOT as additional methods on the existing
`StorageAdapter` interface. Rationale:

- Adapters that want to persist tenant settings can implement BOTH
  interfaces; adapters that don't (e.g. a future test stub) can
  implement only `StorageAdapter`. No mandatory implementation churn
  on existing consumers.
- `StorageAdapter`'s 3 method pairs are doc-scoped (`docId`-keyed);
  `TenantSettingsStore`'s methods are tenant-scoped (`tenantId`-keyed).
  The two key spaces don't collide, but the type system shouldn't
  pretend they're the same store.
- Future tenant-scoped facets (audit log, region-replication policy,
  SSO config — explicitly out of scope per T-411) can be added as
  parallel facets without disturbing existing adapters.

### D-T411a-2 — Schema verbatim from T-411 D-T411-2

```ts
// packages/storage/src/tenant-settings.ts
export const tenantSettingsSchema = z
  .object({
    tenantId: z.string().min(1),
    features: z
      .object({
        interactive: z.enum(['disabled', 'preview', 'ga']),
      })
      .strict(),
    updatedAt: z.string().datetime(),
    updatedBy: z.string().min(1),
  })
  .strict();
export type TenantSettings = z.infer<typeof tenantSettingsSchema>;
```

`.strict()` at both the outer object AND the `features` sub-object so
unknown keys at either level are rejected at parse time. v1 surface is
deliberately minimal; future widening is non-breaking (additional
optional fields on `features`, sibling fields on the outer object).

### D-T411a-3 — Contract: `TenantSettingsStore` interface

```ts
// packages/storage/src/tenant-settings-store.ts
export interface TenantSettingsStore {
  /**
   * Read a tenant's settings. Returns null when the row is absent;
   * callers (T-411b's tRPC `get` procedure) materialise the
   * default-deny posture per T-411 D-T411-5.
   */
  getTenantSettings(tenantId: string): Promise<TenantSettings | null>;

  /**
   * Upsert a tenant's settings. The adapter validates the payload
   * with `tenantSettingsSchema.parse()` before persisting (defence in
   * depth — callers also validate, but the adapter is the last
   * gate).
   */
  putTenantSettings(settings: TenantSettings): Promise<void>;

  /**
   * Superadmin-only: list every tenant's settings. Used by T-411b's
   * `tenantSettings.list` procedure for incident-response triage.
   * Returns an empty array when no rows exist.
   */
  listTenantSettings(): Promise<TenantSettings[]>;
}
```

The interface lives in its own file for clarity and is re-exported
from `packages/storage/src/index.ts`. The 3-method shape is the
minimum useful surface; T-411b's API procedures map 1:1 onto these
methods plus the default-materialisation logic.

### D-T411a-4 — In-memory adapter: separate class, not bolted onto `InMemoryStorageAdapter`

A new `InMemoryTenantSettingsStore` class implements
`TenantSettingsStore`. It is NOT a method extension on
`InMemoryStorageAdapter` because the two stores have independent
lifecycles and reset semantics. Tests can wire either or both.

A `reset()` test-only hook clears all rows (mirrors
`InMemoryStorageAdapter.reset()`).

### D-T411a-5 — Postgres adapter: separate class + new migration

A new `PostgresTenantSettingsStore` class lives in
`packages/storage-postgres/src/tenant-settings.ts`. It accepts the
same `AdapterPool` shape as `PostgresStorageAdapter` so deployments
can pass one pool to both.

The migration `packages/storage-postgres/src/migrations/0002_tenant_settings.sql`
adds a single table:

```sql
CREATE TABLE tenant_settings (
  tenant_id   TEXT PRIMARY KEY,
  features    JSONB NOT NULL,
  updated_at  TIMESTAMPTZ NOT NULL,
  updated_by  TEXT NOT NULL
);
```

`features` is JSONB (not separate columns) so widening v1's
`{ interactive }` shape to future fields is a code-level change with
no DDL migration.

The `0002_` prefix follows the existing `0001_init.sql` numeric
ordering.

### D-T411a-6 — Firebase adapter: structural Firestore facade

A new `createFirebaseTenantSettingsStore({ firestore })` factory ships
in `packages/storage-firebase/src/tenant-settings.ts`. It targets a
`tenant_settings/{tenantId}` collection.

Per the T-411 D-T411-1 region-routing requirement, deployments using
the existing `RegionRouter` pass the per-region Firestore instance to
this factory:

```ts
// At boot:
const usStore = createFirebaseTenantSettingsStore({
  firestore: regionRouter.getFirestoreForOrg({ region: 'us' }),
});
const euStore = createFirebaseTenantSettingsStore({
  firestore: regionRouter.getFirestoreForOrg({ region: 'eu' }),
});
```

The factory itself is region-agnostic; the wiring layer (T-411b) picks
the right store per request based on the tenant's region. This sub-PR
ships the factory; the per-tenant routing logic is a T-411b concern.

The factory uses a structural `FirestoreTenantSettingsLike` interface
(mirroring `BucketLike` / `FileLike` in `asset-storage.ts`) so unit
tests can pass an in-memory shim — no Firebase emulator required for
the structural happy paths. (A future PR may add an emulator-based
integration test under T-411b's wiring; this sub-PR's scope is the
adapter.)

### D-T411a-7 — Default-deny: out-of-scope for this sub-PR's storage layer

Per T-411 D-T411-5, an absent tenant row maps to
`features.interactive: 'disabled'`. **The store itself returns `null`
for an absent row** — the default-materialisation lives one layer up
in T-411b's tRPC procedure. This keeps the store interface pure
(getters return what's persisted; nothing more).

This sub-PR's tests assert: (a) `getTenantSettings('absent') ===
null`; (b) `putTenantSettings` followed by `getTenantSettings`
round-trips. The default-deny **end-to-end** behaviour is verified by
T-411b's tests on the procedure layer.

## Acceptance criteria (storage subset of parent T-411 AC list)

### Schema

1. `packages/storage/src/tenant-settings.ts` exists with the
   `tenantSettingsSchema` Zod schema per D-T411a-2 (verbatim from
   parent T-411 D-T411-2).
2. `tenantSettingsSchema` rejects unknown keys at the outer object AND
   the `features` sub-object (`.strict()` at both levels).
3. `tenantSettingsSchema` rejects invalid `features.interactive` enum
   values (anything outside `'disabled' | 'preview' | 'ga'`).
4. `tenantSettingsSchema` rejects missing required fields.
5. `tenantSettingsSchema` rejects empty `tenantId` and empty
   `updatedBy`.
6. `tenantSettingsSchema` rejects malformed `updatedAt` (not an ISO
   8601 datetime).

### Contract

7. `TenantSettingsStore` interface defined in
   `packages/storage/src/tenant-settings-store.ts` with the 3 methods
   per D-T411a-3.
8. Interface and schema re-exported from `packages/storage/src/index.ts`.

### In-memory adapter

9. `InMemoryTenantSettingsStore` class in
   `packages/storage/src/in-memory-tenant-settings.ts` (or co-located
   in `tenant-settings-store.ts`) implements `TenantSettingsStore`.
10. `getTenantSettings('absent')` returns `null`.
11. `putTenantSettings` followed by `getTenantSettings` returns the
    same payload (round-trip).
12. `putTenantSettings` is upsert: a second call for the same
    `tenantId` overwrites the first.
13. `listTenantSettings()` returns all stored rows; empty store
    returns `[]`.
14. `putTenantSettings` validates the payload with
    `tenantSettingsSchema.parse()` and rejects invalid input (defence
    in depth).
15. `reset()` test hook clears all rows.

### Postgres adapter

16. `PostgresTenantSettingsStore` class in
    `packages/storage-postgres/src/tenant-settings.ts` implements
    `TenantSettingsStore`.
17. New migration `packages/storage-postgres/src/migrations/0002_tenant_settings.sql`
    creates the `tenant_settings` table per D-T411a-5.
18. Adapter passes the same round-trip / upsert / list-empty / list-many
    test surface as the in-memory adapter (contract conformance —
    AC #11–13 mirrored).
19. Adapter validates the payload with `tenantSettingsSchema.parse()`
    before INSERT/UPDATE.
20. Adapter handles the `updatedAt` round-trip through PG TIMESTAMPTZ
    correctly (string in → ISO string out, matching the existing
    `toIso()` helper pattern in `adapter.ts`).
21. Tests exercise the adapter against `pg-mem` per the existing
    `adapter.test.ts` pattern (no real Postgres required for unit
    tests).

### Firebase adapter

22. `createFirebaseTenantSettingsStore({ firestore })` factory in
    `packages/storage-firebase/src/tenant-settings.ts` returns an
    object satisfying `TenantSettingsStore`.
23. Factory accepts a structural `FirestoreTenantSettingsLike`
    interface so tests pass an in-memory shim (mirrors `BucketLike` /
    `FileLike` in `asset-storage.ts`).
24. Adapter targets the `tenant_settings/{tenantId}` collection per
    D-T411a-6.
25. Adapter passes the same round-trip / upsert / list-empty / list-many

26. Adapter validates the payload with `tenantSettingsSchema.parse()`

## Determinism posture

Storage adapters are I/O-bound and live outside the determinism-gated
paths (`packages/frame-runtime/**`, `packages/runtimes/**/src/clips/**`,
`packages/renderer-core/src/clips/**`). The determinism rules in
CLAUDE.md §3 do NOT apply to this PR.

The Zod schema validation IS deterministic for the same input (pure
function); this is a property of `zod`, not a determinism-gate
requirement.
