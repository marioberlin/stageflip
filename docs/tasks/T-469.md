# T-469 — `HeatmapClip`

**Branch**: `task/T-469-heatmap-clip`

## Goal

Ship the **HeatmapClip** family — the first of three Phase 15 marquee
differentiators (per ADR-010 §D1 + §D7): spatial input that Slido /
Mentimeter / Poll Everywhere / Vevox / Wooclap structurally cannot
reach. Voters tap an (x, y) coordinate on an underlying image / chart
surface; the aggregation accumulates (x, y, intensity) per-tap; the
renderer composites a heatmap visualization over the image.

Per-kind shapes (already in `@stageflip/audience-contract`):

- Vote: `{ kind: 'heatmap', x: number (0..1), y: number (0..1),
  intensity?: number }`.
- Aggregation: `{ taps: readonly { x, y, intensity }[], totalTaps,
  gridResolution: { w, h } }`.
- Rendering: a `<canvas>` overlay on the underlying image. Each tap
  contributes intensity to a 2D grid (Gaussian kernel, σ derived from
  `gridResolution`). The grid is normalized + colormapped (blue →
  green → yellow → red) and rendered as the canvas image data.
  Underlying image (`clip.props.imageRef`) renders BELOW the canvas;
  canvas composited at ~70% opacity.
- Voter UI: a tap-target on the underlying image. Tap captures
  normalized (x, y) per the tap's position within the image's
  bounding rect. Tap submits + optionally allows multiple taps if
  `clip.props.maxIntensity > 1`.

§13 verification is option-1 — `render-e2e.test.ts` drives the
static-fallback with a known taps set + asserts:
1. `<canvas>` element present + non-zero dimensions.
2. Underlying `<img>` element present with the correct `src`.
3. Canvas pixel data is non-blank (read via `getImageData` after a
   small wait for rasterization).
4. Pixel bucket assertion: at least one bucket has >threshold non-
   transparent pixels in the heat-colormap range (red/yellow/green/blue).

## Implementation notes

- **Schema**: `props: { prompt: z.string().min(1), imageRef:
  z.string().url(), maxIntensity: z.number().int().positive().max(20).default(1),
  gridResolution: z.object({ w: z.number().int().positive().max(256),
  h: z.number().int().positive().max(256) }).default({ w: 32, h: 32 }),
  sessionId: z.string().optional() }`.
  - `imageRef`: full URL or a `cacheKey:` reference (the renderer
    resolves via the existing asset-cache pattern — punt strict format
    to follow-up).
  - `permissions: z.tuple([z.literal('audience-network')])`.
  - `provenance: audienceProvenanceSchema.optional()`.
- **`rasterize.ts`** — PURE function:
  ```ts
  export function rasterizeHeatmap(
    taps: readonly { x: number; y: number; intensity: number }[],
    gridResolution: { w: number; h: number },
    canvasWidth: number,
    canvasHeight: number,
  ): ImageData
  ```
  - Allocate a `Float32Array(gridResolution.w * gridResolution.h)` for
    accumulation.
  - For each tap: splat a Gaussian kernel centered at `(tap.x *
    gridResolution.w, tap.y * gridResolution.h)` with σ = 2 cells +
    weight = `tap.intensity`.
  - Normalize the grid to [0..1].
  - Upsample to canvas dimensions (nearest-neighbor or bilinear; use
    nearest-neighbor for deterministic byte-exact output).
  - Colormap: blue → green → yellow → red transition based on the
    normalized value; alpha = `value * 255 * 0.7` (≤70% opacity).
  - Return `ImageData(rgbaArray, canvasWidth, canvasHeight)`.
  - **Deterministic**: no `Math.random`, no `Date.now`, no `setTimeout`.
    Use only arithmetic operations + a deterministic exp() approximation
    if needed for the Gaussian kernel.
- **Static-fallback rendering**:
  - Render `<img src={clip.props.imageRef}>` below.
  - Render `<canvas width={w} height={h}>` above, absolutely positioned.
  - In `useEffect` (or equivalent for the runtime context — defer to
    the render-context's "canvas-ready" hook if T-454 provides one):
    create canvas 2D context, call `rasterizeHeatmap`, call
    `ctx.putImageData(imageData, 0, 0)`.
  - The static-fallback returns React elements; the canvas
    drawing happens via a ref + an effect that ALSO runs in the test
    environment (jsdom + happy-dom both support `<canvas>` minimally).
  - If the test environment lacks canvas 2D support, the test
    asserts on canvas presence + dimensions but skips `getImageData`;
    document the limitation.
- **Live-mount rendering**: identical to static-fallback in v1 — the
  taps update via WebSocket snapshot events; the canvas re-rasterizes
  on each snapshot.
- **Voter UI** (`heatmap-voter-input.tsx`):
  - `props: { prompt, imageRef, maxIntensity, onSubmit, disabled? }`.
  - Renders `<img>` with onClick handler.
  - On click, compute normalized `(x, y)` from `event.clientX -
    rect.left, event.clientY - rect.top` divided by `rect.width,
    rect.height`. Clamp to [0..1].
  - Emit `{ kind: 'heatmap', x, y, intensity: 1 }` (single-tap v1; if
    `maxIntensity > 1`, allow multiple taps but each tap is still
    `intensity: 1` — the server accumulates).
  - Show "Tap submitted" feedback after each tap. If `maxIntensity > 1`,
    allow re-tap up to `maxIntensity` times then disable.
- **Mirror T-468 exactly** for layout / tests / dispatcher registration.
- **Determinism perimeter**: same as prior — `rasterize.ts` is the new
  pure module; static-fallback uses it; factory's `runAudienceClient`
  is the only non-deterministic surface.
- **Canvas + test environment**: happy-dom provides `<canvas>` element
  but the 2D context may not implement `putImageData` / `getImageData`
  fully. Tests should: (a) assert canvas element + dimensions present;
  (b) attempt `getImageData` in a try/catch — if it succeeds, assert
  on pixel buckets; if it throws, skip with a documented note. The
  CI happy-dom version should support enough.
