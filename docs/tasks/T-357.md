# T-357 — Preset: `olympic-medal-tracker` (standings, LiveDataClip, Cluster E)

**Branch**: `task/T-357-olympic-medal-tracker`

## Goal

Promote the existing `olympic-medal-tracker` preset stub from `status: stub` to `status: substantive` and ship it as the **fifth Cluster E preset to land** (after T-359 / `f1-sector-purple-green`, T-358 / `cricket-ball-by-ball-dots`, T-360 / `big-number-stat-impact`, T-356 / `bloomberg-ticker`). The preset captures the universal Olympic / world-championship medal-table convention: a vertical ranked panel listing top countries by gold count, with country code + gold/silver/bronze counts + total + rank-delta arrow per row. Common uses: Olympic broadcast lower-third or fullscreen interlude during medal-ceremony coverage; world-championship aggregations; college-tournament leaderboards (March Madness adjacent); any sport whose closing graphic is "who is winning the meet".

T-357 is the **second Cluster E preset to bind `LiveDataClip`** (after T-356) AND the **first preset to ship using `clipKind: standings`**. The clip-family duality matters: per ADR-003 §D2, `live-data` is an interactive-tier family with two render paths — `liveMount` (host fetches a medal-table feed, renders live with periodic refresh) and `staticFallback` (deterministic snapshot for parity goldens, exports, screenshots). T-357 covers the **staticFallback path** end-to-end (parity golden + signed sign-off); the liveMount path is documented in prose only — host responsibility per ADR-003 §D2.

T-357 is **M-sized** (on par with T-356) because of: (1) the **near-certain primitive carve-out** (D-T357-2) — none of the existing bridge primitives carries a vertical N-column ranked table cleanly; (2) a new resolver entry for `standings` (~15–25 LOC) plus the canonical-snapshot constant; (3) the LiveDataClip-vs-parity bypass (D-T357-12). Inherits T-359a's multi-variant infra in trivial-arity mode, T-359b/T-359c's prod-renderer pipeline, T-358a's primitive-carve-out precedent (`outcome-row`), T-356a's analogous carve-out (`news-ticker-bar`), T-360's multi-preset-per-clipKind resolver shape.

## Architectural decisions

### D-T357-1. On-disk location — modify the existing stub in place

The stub already exists at `skills/stageflip/presets/data/olympic-medal-tracker.md` (verified on disk: 58 lines, all six H2 sections present at stub fidelity, `status: stub`). T-357 **modifies** that file — does NOT create a new one. `id: olympic-medal-tracker`, `cluster: data`, `clipKind: standings`, `permissions: [network]`, `source: docs/compass_artifact.md#olympic-medal-tracker` stay. Mirrors T-356 / T-358 / T-359 / T-360's stub-promotion pattern.

### D-T357-2. **Pivotal decision** — primitive fit: NO existing primitive fits; carve out `T-357a standings-table` follow-up

**Verified during spec drafting** (read `packages/runtimes/frame-runtime-bridge/src/clips/index.ts` plus the three closest candidates):

- **`comparison-table.tsx`** — fixed two-column (`leftHeading`/`leftRows` + `rightHeading`/`rightRows`). A medal table needs **5–7 columns** (rank, country code, gold, silver, bronze, total, rank delta). Wrong arity. Cannot be coerced without rewriting the prop schema.
- **`financial-statement.tsx`** — hierarchical P&L / balance-sheet / cash-flow assembly with `statementType: 'pnl'|'balance_sheet'|'cash_flow'`, semantic-role-keyed KPI strip, line/section/subtotal/total row kinds, period-column variance display. The shape is "financial statement", not "ranked sports standings". Coercing it would semantically misuse the primitive (a row's `semanticRole: 'revenue'` is wrong-domain for a country's gold count).
- **`kpi-grid.tsx`** — composes `AnimatedValue` cards in a fixed grid. Not a ranked vertical row layout. Wrong shape.
- **All other bridge clips** (verified via `index.ts`): `outcome-row` (T-358a) is a horizontal chip strip; `news-ticker-bar` (T-356a) is a horizontal scroll; `lower-third`, `pull-quote`, `testimonial-card` are single-card chyrons; the dashboard family (`marketing-dashboard`, `okr-dashboard`, `hr-dashboard`, `product-dashboard`, `sales-dashboard`) is too heavy / too compositional; `stock-ticker` is a candlestick chart. None carry "vertical N-row ranked table with country | medal counts | rank delta" cleanly.

**Decision**: the Olympic medal-table shape requires a **new generic primitive** — `standings-table` — that renders a vertical ranked list of N row entries (rank, label/code, K medal/score columns, optional total, optional delta-arrow) with frame-driven entrance stagger. T-357a (analog of T-356a → news-ticker-bar, T-358a → outcome-row) carves this out as a separate small primitive PR. T-357's own PR is **paused** at the preset-markdown stage until T-357a merges, then the resolver entry + parity golden land in the T-357 retry PR.

**Mandated check at implementation start**: the Implementer re-verifies (a) the three candidate primitives (`comparison-table`, `financial-statement`, `kpi-grid`) still carry the schemas described above and (b) no new ranked-table primitive has appeared in `packages/runtimes/frame-runtime-bridge/src/clips/` since spec-drafting time. If either is false (a fitting primitive exists OR has appeared), document the find and skip the carve-out — wire directly. If both hold (almost certain), STOP IMMEDIATELY and escalate per CLAUDE.md §6 with a one-line spec sketch for `T-357a standings-table`:

```
props: {
  rows: { rank: number, code: string, values: number[], total?: number,
          delta?: 'up'|'down'|'flat'|number }[],   // 1..16
  columns: { key: string, label: string,
             kind: 'rank'|'label'|'numeric'|'delta'|'total',
             color?: string }[],
  rowHeight?: number, headerHeight?: number,
  background?: string, foreground?: string,
  goldColor?: string, silverColor?: string, bronzeColor?: string,
  upColor?: string, downColor?: string, flatColor?: string,
  staggerMs?: number,                                // entrance only
  bandPosition?: 'overlay'|'fullscreen',
}
```

Frame-derived; fully deterministic; no Date/random/timer. Browser-safe. The primitive is generic — Olympic, F1 constructors' standings, NBA conference standings, March Madness bracket aggregations, any "ranked panel of N entries with K numeric columns" reuse it.

**Do NOT** try to shoehorn the medal-table shape onto `comparison-table` (wrong arity), `financial-statement` (wrong semantic domain), `kpi-grid` (wrong layout), `outcome-row` (horizontal, wrong axis), `news-ticker-bar` (horizontal scroll, wrong axis), or any other existing primitive. The carve-out is the correct pattern; T-356a + T-358a established the precedent; T-357a follows.

### D-T357-3. Resolver entry shape — clipKind-default keyed by `standings`, with cached-snapshot constant

T-360 D-T360-2 evolved the resolver to `(clipKind, presetId)` keyed lookups with backward-compat fallback (`PRESET_ID_BINDINGS` first, then clipKind-only). T-357 lands a **clipKind-default** entry (matches T-356's `newsTicker → news-ticker-bar` and T-358's `scoreBug → outcome-row` posture, NOT a per-preset override): the `standings` clipKind is generic enough that future sports / racing / college-tournament presets can share the binding. Per-preset overrides are added later if a sister preset needs different visual tokens.


### D-T357-4. Static-fallback content — `OLYMPIC_CANONICAL_STANDINGS` constant; five representative rows

The cached snapshot is the parity-golden payload. Per D-T357-3 the constant ships **five rows** (top-5 leaderboard) — USA leading (28/22/19 = 69), CHN second (24/19/16 = 59), JPN third (14/11/13 = 38, ↑), AUS fourth (12/10/14 = 36, ↓), GBR fifth (11/16/15 = 42, ↑). Mix of medal counts and a mix of rank-delta arrows (3× active deltas + 2× flat) exercise both ↑/↓ color paths AND the flat-state path in a single golden. Five rows fit the 1920×1080 canvas comfortably at the default `rowHeight: 64` plus header (48) — total panel height ~370 px, leaves abundant whitespace for a centered overlay or a fullscreen interlude with title space. The values are illustrative — cluster owners rebrand at compose time. Document the constant with TSDoc citing this decision.

**Why a constant + not a JSON file**: same rationale as T-356 D-T356-4. The preset's parity contract is the **shape** (rank + code + medal counts + delta → styled row), not the literal values. Inlining as a TS constant keeps the resolver self-contained and obvious to a Reviewer; a JSON file would invite drift between the preset prose and the renderer.

### D-T357-5. Single canonical mid-hold variant; concrete frame `60`

ADR-004 §D5 + T-313 specify a single canonical mid-hold reference frame per preset. T-357 ships **one mid-hold fixture** at `frame: 60`. At 30 fps and the proposed `staggerMs: 80` (~2.4 frames per row), all five rows have entered + settled by frame ~12; frame 60 is a well-past-entrance steady-state hold. The golden captures one frame; the manifest pins `frame: 60`.

If frame 60 lands during an animation transient (no rows fully settled — should not happen with the proposed stagger but verify), the Implementer adjusts the canonical frame to 90 (within ±30 of the 60-frame convention) and documents the choice. Do NOT introduce a second variant — the preset's stylistic point is the ranked-table shape itself, not a per-frame state swap (contrast with T-359 which has three semantically-distinct variants). The stub's existing `## Acceptance (parity)` lists four reference frames (0/30/60/120) covering entry through post-flash; T-357 collapses to single mid-hold per the cluster-E one-variant convention (D-T357-5).

### D-T357-6. Country representation — ISO 3-letter codes (license-clean); flags out-of-scope

The preset uses **ISO 3-letter country codes** (USA, CHN, JPN, AUS, GBR) — ASCII glyphs that any registered Latin-script font renders correctly. License-clean, browser-safe, no inline raster assets, no flag-licensing concern (national flags are technically free but flag-image asset packs from third parties carry licenses).

**Rejected**: inline flag PNGs / SVGs. Reasons: (a) v1 contract is "no inline raster assets in the preset prose / parity golden"; (b) flag artwork from public packs (flag-icons, country-flag-icons, etc.) ships under MIT / CC0 in most cases but introduces a third-party dependency the parity render does not need; (c) the preset's identification anchor is the medal counts + rank, not the flag (the flag is decoration); (d) hosts that want flags can wire a tenant-asset slot at compose time without changing the preset.

The stub's `## Visual tokens` mentions "Country flags as identification anchors" — this is a v2 enhancement, NOT a v1 requirement. T-357 revises the stub prose to clarify: ISO 3-letter codes are the v1 baseline; flags are a future tenant-asset hook. Document this in the preset's `## Visual tokens` AND in the PR body.

### D-T357-7. Font posture — `IBM Plex Sans` (ofl, w600) for the table; BYO posture inherited from stub but updated fallback face

### D-T357-11. LiveMount vs staticFallback in the prose contract — both documented; only staticFallback ships goldens

T-357's `## Rules` documents BOTH render paths per ADR-003 §D2:

- **liveMount**: host fetches a medal-table feed (e.g., a sports-data provider's Olympics endpoint, a custom IOC results aggregator); a refresh policy of 30–60 s ticks the rows; the per-row update flash (200 ms pulse) renders on rank change; the WR/OR record-flash overlay (per stub's `## Animation`) renders on per-event records. **Host owns this entirely.** The preset documents the endpoint shape contract (`{ rank, code, gold, silver, bronze, total, delta }[]`) but does not implement fetching, authentication, polling, or rate-limiting.
- **staticFallback**: the `OLYMPIC_CANONICAL_STANDINGS` constant (D-T357-4) substitutes for the endpoint payload. The deterministic frame-runtime path renders the constant via the bound `standings-table` primitive. This is the **parity-golden path** AND the path used for non-interactive exports (PNG / non-live MP4) per ADR-003.

The preset's frontmatter does NOT today carry a structured `interactiveTier` / `liveMount` / `staticFallback` block — the schema (`packages/schema/src/presets/frontmatter.ts`) does not expose those fields (verified). The contract lives in `## Rules` prose. If a Reviewer demands a schema field, escalate — that is a preset-system schema change (out of envelope; analog of T-308's invariant set evolution).

### D-T357-12. LiveDataClip-vs-parity integration — bypass the LiveDataClip wrapper; mount the inner `standings-table` directly

`packages/runtimes/interactive/src/clips/live-data/static-fallback.ts` ships `defaultLiveDataStaticFallback` — a generic Element[] generator that emits a header `TextElement` + a body `TextElement` (JSON-pretty-printed snapshot body). This is **NOT** a styled standings panel; it is a generic developer-facing fallback for any LiveData clip without a custom renderer.

T-357's parity flow **bypasses** the LiveDataClip wrapper and `defaultLiveDataStaticFallback` (same posture as T-356 D-T356-11). The resolver returns a binding to `standings-table` (a frame-runtime-bridge primitive); the renderer mounts `standings-table` directly with the `OLYMPIC_CANONICAL_STANDINGS` payload (D-T357-4) inlined as props. The wrapper's job (host the live mount, emit telemetry, route to staticFallback on failure) is a runtime concern that does not surface in the parity flow.

**Rationale**: identical to T-356 D-T356-11. The parity golden's purpose is to verify the **rendered visual** matches the stub's prose contract. Routing through the LiveDataClip wrapper would bring its telemetry surface, its endpoint-prop validation, and its placeholder-on-missing-snapshot fallback into the parity render — none of which contribute to the visual output and all of which would couple the parity golden to wrapper behavior that legitimately changes between releases (T-391/T-392 evolution). The bypass keeps the parity contract focused on **the visual**, not the integration mechanism.

Document this bypass in the preset's `## Rules` AND the resolver entry's TSDoc so a future reader does not assume the parity path exercises LiveDataClip end-to-end. The integration is exercised by T-391/T-392's own tests; T-357 is not the right harness for that surface.
