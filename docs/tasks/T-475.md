# T-475 — Latency tests

**Branch**: `task/T-475-latency-tests`

## Goal

Ship the **live-aggregation latency test harness** per ADR-009 §D4.
Verifies the audience-backend's end-to-end voter-tap → presenter
screen latency meets the SLA budget:

| Hop | p50 target | p95 ceiling |
|---|---|---|
| Voter tap → backend ack | < 100 ms | < 250 ms |
| Backend persist (events sub-collection write) | < 50 ms | < 150 ms |
| Snapshot aggregation (events → AggregationSnapshot) | < 100 ms | < 300 ms |
| Backend → presenter socket frame | < 50 ms | < 150 ms |
| **End-to-end** | **< 200 ms** | **< 500 ms** |

This is the in-process latency check — drives synthetic voter taps
against the `InMemoryAudienceResultsStore` + the `apps/api`
WebSocket multiplexer via Hono's `app.request(...)` (no real socket).
The K6-based **load test** at 1000 concurrent voters is **T-477**;
T-475 covers the per-hop latency-budget verification at a smaller
scale (10..100 concurrent voters).

Carries three concerns:

1. **`apps/api/src/test/audience-latency.bench.ts`** (or similar
   path) — vitest-based latency harness:
   - Synthetic voter taps at 3 concurrency levels: 10, 50, 100.
   - Records per-hop wall-clock latencies via injectable
     `Date.now()` proxy (avoids the determinism perimeter concerns —
     this lives in `apps/api/src/test/` outside `packages/runtimes/**`).
   - Reports percentile latencies (p50 / p95).
   - Asserts against the SLA budget.
2. **`apps/api/src/test/audience-latency-helpers.ts`** — pure helpers:
   - `synthesizeVoterTaps(count: number): VoterTap[]` — deterministic
     synthetic taps with voter-token + timestamp + payload.
   - `computePercentile(samples: readonly number[], pct: number):
     number` — pure stats helper.
3. **CI integration** — wire the latency-bench into the existing
   workspace test suite OR add a separate `pnpm test:latency` script
   gated on the `test` job. Recommend the latter; latency-tests can
   be flaky on shared CI runners and are best run via opt-in.

**Strict scope** — in-process latency verification. NO real WebSocket
connection (use Hono's `app.request`). NO K6 load test (T-477). NO
Firestore-backed measurement (in-memory only — T-477 will exercise
the Firestore path at load). NO presenter-side rendering latency
measurement (that's downstream of the backend; ADR-009 §D4 only
measures the backend hop).

## Implementation notes

- **`synthesizeVoterTaps(count)`** — deterministic. Each tap is
  `{ voterToken: \`voter-${i}\`, sessionId: 's-bench', payload: { kind:
  'live-poll-multiple-choice', optionIndex: i % 3 }, timestampMs: i * 10 }`.
- **`computePercentile`** — sort samples + index at
  `Math.floor((samples.length - 1) * pct)`. Document the convention
  (no interpolation — closest sample).
- **Latency harness**:
  - For each concurrency level (10, 50, 100):
    1. `openSession` for a synthetic LivePollMultipleChoiceClip.
    2. Fire N taps via `app.request('/v1/audience/sessions/s-bench/...')`
       (Hono in-process request).
    3. For each tap, record:
       - `t0 = now()` BEFORE the request.
       - `t1` AFTER ack received.
       - `t2` AFTER snapshot includes the tap (poll via repeated
         `/state` requests; the cadence is the audience runtime's
         snapshot cadence — 30Hz / ~33ms).
    4. Compute percentiles + log.
    5. Assert: end-to-end p50 < 200ms, p95 < 500ms.
- **Test environment**: vitest in node mode (NO happy-dom; the
  latency tests don't need DOM). Direct in-process Hono calls.
- **Determinism**: latency itself is non-deterministic (wall-clock).
  But the test asserts on PERCENTILES, not on individual samples,
  with comfortable margins above the SLA targets.
- **CI runner sensitivity**: shared CI runners (GitHub Actions) are
  noisy. The latency suite is opt-in to avoid flake; production
  validation happens at deploy-time.
- **No `console.log`** outside the explicit test artifact-logging
  path (use `process.stderr.write` if needed — document the
  exception in TSDoc).
- **Pre-empt skills-sync drift**.
