# T-430 — `@stageflip/video-seedance` (Seedance 2.0 video adapter; 15s 1080p + native audio + lip-sync; proprietary-byo; stub-mode v1)

**Branch**: `task/T-430-video-seedance`

## Goal

Ship the **fifth reference adapter** in the Phase 14 β sequence
(T-426..T-434) and the **first `video-gen` modality adapter**:
`@stageflip/video-seedance`. Wraps the Seedance 2.0 commercial
text-to-video model accessed via the fal.ai HTTPS API (15s output
at 1080p; native audio; lip-sync — rare among text-to-video models;
batch latency ~1–3 min per video; tenant-supplied API credentials)
behind the `VideoGenerationProvider` interface from T-419, declares
an `AdapterDescriptor` per T-418, and exercises the
**`proprietary-byo`** license posture for the **third** time
(T-428's Tripo3D was the first; T-429's Meshy was the second).

T-430 is the structural sibling of T-428 / T-429 (same
proprietary-byo + remote-service posture) translated to the
`video-gen` modality. The deltas are functional, not structural.

| Field | Tripo3D (T-428) | Meshy (T-429) | Seedance (T-430) |
|---|---|---|---|
| Modality | `three-d` | `three-d` | **`video-gen`** |
| `id` | `tripo` | `meshy` | **`seedance`** |
| Stub payload | unit cube GLB | icosahedron GLB | **minimal valid MP4** (1 frame, 1080p, silent) |
| Distinguishing capability | quad topology + rigging | triangle-soup + no rig | **15s @ 1080p + native audio + lip-sync** |
| `sandbox.baseUrlEnvVar` | `TRIPO_API_BASE_URL` | `MESHY_API_BASE_URL` | **`FAL_API_BASE_URL`** |
| `costPerCall.usd` | `0.5` | `0.2` | **`1.5`** (per-video; tenant pays fal.ai; representative-call hint; placement in `enterprise` cost-tier bucket) |
| `latencyMs.{p50,p95}` | `60_000 / 120_000` | `60_000 / 90_000` | **`90_000 / 180_000`** (~1–3 min typical; batch tier) |
| `model` cache-key field | `tripo:character` | `meshy:prop-environment` | **`seedance:2.0`** |

T-430 ships in **stub mode**: the `generate()` body emits a
deterministic placeholder MP4 byte payload (a minimal valid
single-frame MP4 emitted via a hard-coded base64 fixture for
simplicity — see "Stub MP4 fixture rationale" below) and returns a
shaped `VideoGenResult`. Production wire-up (real fal.ai HTTPS
API call + MP4 download) is gated on a follow-up task (T-430a) —
same v1-stub-mode-with-production-deferral pattern as
T-426 / T-427 / T-428 / T-429.

T-430 is M-sized: one new package, ~350–500 LOC across 3 src
modules (descriptor / provider / stub-video) + matched tests,
~250–400 lines of spec, no schema / parity / clip / preset / ADR
changes.

## Stub MP4 fixture rationale

The MP4 container (ISO base media file format) is structurally more
complex than WAV (Kokoro / Fish Speech) and GLB (Tripo3D / Meshy):
it requires a `moov` box with a `trak` containing sample-table boxes
(`stsd` / `stts` / `stsc` / `stsz` / `stco`), even for a placeholder.
Synthesizing this procedurally in TypeScript adds ~400–600 LOC of
box-format writer code with little payoff — the production wire-up
(T-430a) replaces the stub entirely with a real H.264 + AAC MP4
downloaded from fal.ai.

T-430 takes **Option A**: ship a hard-coded base64-encoded minimal
valid MP4 fixture (~200–600 bytes) and decode it inside
`generateStubMp4DataUri` on each call. Trade-offs:

- **Pros**: ~50 LOC instead of ~500; trivially deterministic; no
  box-format writer surface to maintain; the stub is intentionally
  byte-identical across all inputs (matching the Meshy stub's
  posture, where the GLB bytes also don't embed the prompt / seed).
- **Cons**: the fixture is opaque; reviewers must trust it's a
  valid MP4 (mitigated by an `ftyp` magic-bytes test at offset 4).

The fixture used is a 188-byte minimum-viable MP4 with an `ftyp`
brand of `isom` (ISO base media) and a tiny `moov` declaring a
1080×1920 single-frame track with an empty `mdat`. Decoders
recognize the container; there's no codec-recognized frame data.
Production wire-up replaces the entire body and the surrounding
`url: string` shape stays identical.

## BYO credentials posture

Seedance is the **third adapter to declare the `proprietary-byo`
license posture** (Tripo3D was the first via T-428; Meshy was the
second via T-429) and the **first `video-gen` modality** to do so.
Per ADR-008 §D13 (line 654), the `video-gen` modality whitelist
admits `apache-2.0`, `mit`, `proprietary-byo`, and
`proprietary-vendored`. `proprietary-byo` means:

- The adapter wraps a commercial vendor model (Seedance 2.0 via
  fal.ai); fal.ai's licensing terms govern model use.
- The tenant brings their own API credentials (a fal.ai API key
  and potentially a base URL override). The descriptor declares
  the credentials anchor via `sandbox.{kind: 'remote-service',
  baseUrlEnvVar: 'FAL_API_BASE_URL'}` — that env var is the
  production wire-up's secrets entry point.
- StageFlip ships **no vendored model checkpoint**.
- The `pnpm check-asset-licenses` gate accepts the descriptor
  because `proprietary-byo` is in the `video-gen` whitelist; tenant
  credential validation is a runtime concern at the orchestrator
  boundary.

T-430 ships only the descriptor declaration of this posture. The
production wire-up (T-430a) reads the env var, builds an HTTPS
client, polls fal.ai's async job endpoint, downloads the produced
MP4, and surfaces the `LF-ADAPTER-CREDENTIAL-MISSING` failure
class (per ADR-008 §D11) when credentials are absent. The stub
mode never reads the env var.

## Stub-mode vs production-mode contract

The `SeedanceProviderMode` discriminator gates the `generate()`
body behavior **only**. Every other surface (descriptor,
capability, validation, error throwing, cache-key derivation) is
identical between modes. The production wire-up (T-430a) MUST:

1. Keep `seedanceDescriptor` byte-identical (no new capability
   fields in v1; capability expansion lands in a follow-up at
   earliest).
2. Replace the `generate()` `mode === 'production'` branch with a
   real fal.ai API call (HTTPS POST to the job-submit endpoint at
   `process.env[SEEDANCE_BASE_URL_ENV_VAR]`, polling the
   job-status endpoint, downloading the produced MP4).
3. Keep the input validation paths (empty prompt → throw)
   byte-identical.
4. Keep the cache-key derivation byte-identical (so cached results
   from the stub-mode era + production-mode era share the same
   keyspace — production-mode results MUST hash identically to
   stub-mode results when the same `(prompt, aspectRatio,
   frameRate, durationS, outputFormat, seed)` is used; the
   canonical params dict declared here is the contract).
5. NOT widen the `VideoGenResult` shape (no new fields).
6. Honor the `capability.maxDurationS` budget — refuse calls whose
   `durationS` exceeds the budget (per ADR-008 §D6).
7. Honor the `capability.aspectRatios` allow-list — refuse calls
   whose `aspectRatio` is not in the allow-list.
8. Honor the `capability.frameRates` allow-list — refuse calls
   whose `frameRate` is not in the allow-list.

Anything in the production wire-up that conflicts with this
contract is a spec change — file an ADR.
