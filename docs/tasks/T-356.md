# T-356 — Preset: `bloomberg-ticker` (newsTicker, LiveDataClip, Cluster E)

**Branch**: `task/T-356-bloomberg-ticker`

## Goal

Promote the existing `bloomberg-ticker` preset stub from `status: stub` to `status: substantive` and ship it as the **fourth Cluster E preset to land** (after T-359 / `f1-sector-purple-green`, T-358 / `cricket-ball-by-ball-dots`, T-360 / `big-number-stat-impact`). The preset captures the universal financial-broadcast convention modeled on Bloomberg TV's iconic ticker bar: a continuous horizontal left-scrolling band along the bottom of the screen carrying ticker symbols + price + delta + arrow (▲/▼). Common uses: market open/close coverage, earnings reports, crypto trading dashboards, lower-third stock chyrons.

T-356 is the **first Cluster E preset to bind LiveDataClip** AND the **first preset to ship using `clipKind: newsTicker`**. The clip-family duality matters: per ADR-003, `live-data` is an interactive-tier family with two render paths — `liveMount` (host fetches an endpoint, renders live) and `staticFallback` (deterministic snapshot for parity goldens, exports, screenshots). T-356 covers the **staticFallback path** end-to-end (parity golden + signed sign-off); the liveMount path is documented in prose only — host responsibility per ADR-003 §D2.

T-356 is **M-sized** (one step up from T-358/T-359's S, on par with T-360) because of: (1) the **high-probability primitive carve-out** (D-T356-2) — the existing `stock-ticker` clip is a candlestick chart, not a horizontal scrolling chyron; (2) a new resolver entry for `newsTicker` (~10–15 LOC) plus the cached-snapshot constant; (3) the LiveDataClip-vs-parity integration path (D-T356-11). Inherits T-359a's multi-variant infra in trivial-arity mode, T-359b/T-359c's prod-renderer pipeline, T-358a's primitive-carve-out precedent, T-360's multi-preset-per-clipKind resolver shape.

## Architectural decisions

### D-T356-1. On-disk location — modify the existing stub in place

The stub already exists at `skills/stageflip/presets/data/bloomberg-ticker.md` (verified on disk: 56 lines, all six H2 sections present at stub-fidelity, `status: stub`). T-356 **modifies** that file — does NOT create a new one. `id: bloomberg-ticker`, `cluster: data`, `clipKind: newsTicker`, `permissions: [network]`, `source: docs/compass_artifact.md#financial-market-data` stay. ### D-T356-2. **Pivotal decision** — primitive fit: existing `stock-ticker` does NOT fit; carve out `T-356a news-ticker-bar` follow-up

**Verified during spec drafting**: `packages/runtimes/frame-runtime-bridge/src/clips/stock-ticker.tsx` (line 2: "Candlestick chart with per-candle stagger reveal + header ticker line") is a **vertical candlestick price chart** with header text — NOT a continuous horizontal scrolling chyron. Its prop schema (`candles: { open, close, high, low, label? }[]`) models OHLC bars across an X axis; there is no scroll-position knob, no symbol/price/delta row composition, no continuous ticker geometry.

**Survey of the rest of the bridge clip catalog** (verified via `packages/runtimes/frame-runtime-bridge/src/clips/index.ts`): no clip carries the horizontal-scrolling-chyron register cleanly. `outcome-row` (T-358a) is a static row of fixed chips; `lower-third` is a static text band; `comparison-table` is a multi-row data grid; `audio-visualizer` is animated bars; nothing scrolls a continuous strip horizontally.

**Decision**: the Bloomberg ticker shape requires a **new generic primitive** — `news-ticker-bar` — that renders a horizontal row of token entries (symbol + price + delta + arrow) translating left at a frame-determined offset. T-356a (analog of T-358a → outcome-row) carves this out as a separate small primitive PR. T-356's own PR is **paused** at the preset-markdown stage until T-356a merges, then the resolver entry + parity golden land in the T-356 retry PR.

**Mandated check at implementation start**: the Implementer re-verifies (a) `stock-ticker.tsx` is still a candlestick chart and (b) no new horizontal-scrolling primitive has appeared in `packages/runtimes/frame-runtime-bridge/src/clips/` since spec-drafting time. If either is false (i.e., a fitting primitive exists), document the find and skip the carve-out — wire directly. If both hold (almost certain), STOP IMMEDIATELY and escalate per CLAUDE.md §6 with a one-line spec sketch for `T-356a news-ticker-bar` (props: `entries: { symbol, price, delta, direction: 'up'|'down'|'flat' }[]`, `scrollSpeed: number`, `chipGap: number`, theme slots for `background`/`upColor`/`downColor`/`foreground`).

**Do NOT** try to shoehorn the Bloomberg shape onto `stock-ticker` (wrong geometry), `outcome-row` (wrong content), `lower-third` (no scroll), or any other existing primitive. The carve-out is the correct pattern; T-358a established it; T-356a follows.

### D-T356-3. Resolver entry shape — clipKind-default keyed by `newsTicker`, with cached-snapshot constant

T-360 D-T360-2 evolved the resolver to `(clipKind, presetId)` keyed lookups with backward-compat fallback. T-356 lands a **clipKind-default** entry (matches T-358's `scoreBug → outcome-row` posture, NOT a per-preset override): the `newsTicker` clipKind is generic enough that future financial / sports / news-feed presets can share the binding. Per-preset overrides are added later if a sister preset needs different visual tokens.

```ts
// In packages/parity-cli/src/generate-fixture.ts:

// Bloomberg-canonical six-token snapshot per D-T356-4.
// Cluster owners rebrand at compose time; this is the parity-golden payload.
export const BLOOMBERG_CANONICAL_SNAPSHOT: ReadonlyArray<{
  symbol: string;
  price: string;
  delta: string;
  direction: 'up' | 'down' | 'flat';
}> = [
  { symbol: 'AAPL',    price: '230.45', delta: '+1.2%', direction: 'up' },
  { symbol: 'MSFT',    price: '412.10', delta: '-0.4%', direction: 'down' },
  { symbol: 'GOOGL',   price: '178.92', delta: '+0.8%', direction: 'up' },
  { symbol: 'NVDA',    price: '925.34', delta: '+2.7%', direction: 'up' },
  { symbol: 'TSLA',    price: '252.18', delta: '-1.1%', direction: 'down' },
  { symbol: 'BTC-USD', price: '67,234', delta: '+2.1%', direction: 'up' },
];

const NEWS_TICKER_DEFAULT_SCROLL_SPEED = 60; // px/sec — middle of the stub's 50–80 range
const NEWS_TICKER_DEFAULT_FRAME = 60;        // mid-hold parity frame

const newsTickerBinding: ClipKindBinding = {
  runtimeId: 'frame-runtime',
  clipName: 'news-ticker-bar',  // shipped by T-356a
  buildProps() {
    return {
      entries: BLOOMBERG_CANONICAL_SNAPSHOT.map((e) => ({ ...e })),
      scrollSpeed: NEWS_TICKER_DEFAULT_SCROLL_SPEED,
      chipGap: 60,
      background: '#0A0A0A',
      upColor: '#00D26A',
      downColor: '#FF3C3C',
      foreground: '#FFFFFF',
    };
  },
};

export const DEFAULT_CLIP_KIND_RESOLVER: ClipKindResolver = (clipKind, presetId) => {
  if (presetId !== undefined) {
    const override = PRESET_ID_BINDINGS[presetId];
    if (override !== undefined) return override;
  }
  if (clipKind === 'bigNumber') return bigNumberBinding;
  if (clipKind === 'scoreBug') return scoreBugDotsBinding;
  if (clipKind === 'newsTicker') return newsTickerBinding;  // T-356
  return undefined;
};
```

**Budget**: ~15–25 LOC inclusive of the snapshot constant. If `buildProps` grows past ~25 LOC (because the `news-ticker-bar` prop schema needs a non-trivial transformation), escalate — that signals either the primitive's prop schema is wrong (push back to T-356a) or a per-preset override is warranted.

### D-T356-4. Static-fallback content — `BLOOMBERG_CANONICAL_SNAPSHOT` constant; six representative entries

The cached snapshot is the parity-golden payload. Per D-T356-3 the constant ships six entries: four equities (AAPL / MSFT / GOOGL / NVDA / TSLA) + one crypto (BTC-USD), mixing ▲ and ▼ deltas to exercise both color paths. Six entries fit the 1920×1080 canvas with the stub's 50–80 px/s scroll at frame 60 (~120 px scroll offset → 4–5 entries visible mid-band, depending on chip width). The values are illustrative — cluster owners rebrand at compose time. Document the constant with TSDoc citing this decision.

**Why a constant + not a JSON file**: the preset's parity contract is the **shape** (symbol + price + delta + direction → styled chyron entry), not the literal values. Inlining as a TS constant keeps the resolver self-contained and obvious to a Reviewer; a JSON file would invite drift between the preset prose and the renderer.

### D-T356-5. Single canonical mid-hold variant; concrete frame `60`

ADR-004 §D5 + T-313 specify a single canonical mid-hold reference frame per preset. T-356 ships **one mid-hold fixture** at `frame: 60`. At 30 fps and `scrollSpeed: 60 px/sec`, frame 60 = 2 seconds = 120 px of leftward scroll — enough to show the ticker in motion (entries partially clipped on entry/exit edges) but well past the entrance window. The golden captures one frame; the manifest pins `frame: 60`.

If frame 60 lands on a "between entries" position (no entry centered), the Implementer adjusts the canonical frame to 45 or 75 (within ±15 of the 60-frame convention) and documents the choice. Do NOT introduce a second variant — the preset's stylistic point is the continuous scroll, not a per-frame palette swap (contrast with T-359 which has three semantically-distinct states).

### D-T356-6. LiveMount vs staticFallback in the prose contract — both documented; only staticFallback ships goldens

T-356's `## Rules` documents BOTH render paths per ADR-003 §D2:

- **liveMount**: host fetches a market-data endpoint (e.g., a Bloomberg feed, IEX Cloud, Coinbase Pro WebSocket); a refresh policy of 1–5 s ticks the entries; the per-entry update flash (150 ms pulse) renders on price change. **Host owns this entirely.** The preset documents the endpoint shape contract (`{ symbol, price, delta, direction }[]`) but does not implement fetching, authentication, or rate-limiting.
- **staticFallback**: the `BLOOMBERG_CANONICAL_SNAPSHOT` constant (D-T356-4) substitutes for the endpoint payload. The deterministic frame-runtime path renders the constant via the bound `news-ticker-bar` primitive. This is the **parity-golden path** AND the path used for non-interactive exports (PNG / non-live MP4) per ADR-003.

The preset's frontmatter does NOT today carry a structured `interactiveTier` / `liveMount` / `staticFallback` block — the schema (`packages/schema/src/presets/frontmatter.ts`) does not expose those fields (verified). The contract lives in `## Rules` prose. If a Reviewer demands a schema field, escalate — that is a preset-system schema change (out of envelope; analog of T-308's invariant set evolution).

### D-T356-7. Font posture — `IBM Plex Mono` (ofl, w500) for numerics; `IBM Plex Sans` (ofl, w600) for symbols; BYO posture inherited from stub

Stub already declares `Bloomberg in-house` (proprietary-byo) as `preferredFont` and `IBM Plex Mono` (ofl, w500) as `fallbackFont`. T-356 **broadens** the fallback shape to a pair to honor the stub's `## Typography` "Mono is mandatory for column-stable scrolling" rule:

- **Numerics (price + delta)**: `IBM Plex Mono` w500 (tabular figures; column-stable). Keeps the stub's existing fallback.
- **Symbols (AAPL / MSFT / etc.)**: `IBM Plex Sans` w600 (denser; reads as a broadcast register). Symbols are 3–5 ASCII characters; tabular spacing matters less than glyph weight.

Per ADR-004 §D4, cluster-E presets do not require type-design sign-off — `signOff.typeDesign: na` stays. Confirm both `IBM Plex Mono` w500 AND `IBM Plex Sans` w600 are in the FontManager preload list AND `THIRD_PARTY.md`'s OFL block. If either is missing, parity falls back to a system stack and the golden is wrong.

If the heaviest registered `IBM Plex Sans` weight is below 600, drop to the heaviest available and pin in `## Typography` (cluster-E "good enough not broadcast-exact" posture, mirrors T-359's `Barlow Condensed` fallback per T-359 D-T359-7). Escalate only if the heaviest available weight produces a visibly broken render. If a Reviewer demands a fully-OFL `preferredFont` (drops BYO posture), escalate.

### D-T356-8. Hand-pin PSNR ≥ 42 dB, SSIM ≥ 0.98 in `thresholds.json`

Generator default is `35 / 0.95`. Match T-358 / T-359 / T-360's pin (`42 / 0.98`) for cluster-E consistency. ### D-T356-11. LiveDataClip-vs-parity integration — bypass the LiveDataClip wrapper; mount the inner `news-ticker-bar` directly

`packages/runtimes/interactive/src/clips/live-data/static-fallback.ts` ships `defaultLiveDataStaticFallback` — a generic Element[] generator that emits a header `TextElement` (endpoint summary) + a body `TextElement` (JSON-pretty-printed snapshot body). This is **NOT** a styled Bloomberg ticker bar; it is a generic developer-facing fallback for any LiveData clip without a custom renderer.

T-356's parity flow **bypasses** the LiveDataClip wrapper and `defaultLiveDataStaticFallback`. The resolver returns a binding to `news-ticker-bar` (a frame-runtime-bridge primitive); the renderer mounts `news-ticker-bar` directly with the `BLOOMBERG_CANONICAL_SNAPSHOT` payload (D-T356-4) inlined as props. The wrapper's job (host the live mount, emit telemetry, route to staticFallback on failure) is a runtime concern that does not surface in the parity flow.

**Rationale**: the parity golden's purpose is to verify the **rendered visual** matches the stub's prose contract. Routing through the LiveDataClip wrapper would bring its telemetry surface, its endpoint-prop validation, and its placeholder-on-missing-snapshot fallback into the parity render — none of which contribute to the visual output and all of which would couple the parity golden to wrapper behavior that legitimately changes between releases (T-391/T-392 evolution). The bypass keeps the parity contract focused on **the visual**, not the integration mechanism.

Document this bypass in the preset's `## Rules` AND the resolver entry's TSDoc so a future reader does not assume the parity path exercises LiveDataClip end-to-end. The integration is exercised by T-391/T-392's own tests; T-356 is not the right harness for that surface.
