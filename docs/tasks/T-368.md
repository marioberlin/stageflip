# T-368 — Cluster F skill + 4 caption/lyrics composer tools

**Branch**: `task/T-368-cluster-f-compose-tools`

## Goal

Ship a non-canonical engine handler bundle — `cluster-f-compose` — exposing four read-only composer tools that map a brief's caption / subtitle / lyric / keyword-highlight intent onto exactly one of the six Cluster F presets (`hormozi-montserrat-black`, `mrbeast-komika-axis`, `tiktok-rounded-box`, `ali-abdaal-opacity-karaoke`, `netflix-invisible`, `karaoke-progressive-wipe`). The four tools — `compose_creator_caption`, `compose_subtitle`, `compose_lyric_video`, `compose_keyword_highlight` — are the agent-layer entry points the cluster's `SKILL.md` already promises (lines 38–43); shipping them flips Cluster F from "presets exist" to "agent can pick a preset". The bundle dispatches purely on input metadata (style / accessibility-mode / explicit-keywords / clipKind) — handlers do **not** mutate the document and emit zero JSON-Patch ops; they return a `{ presetId, clipKind, rationale }` envelope the executor or downstream `clip-animation` bundle consumes.

T-368 is **the first of four cluster-compose tasks** to ship (Cluster F is the highest-volume cluster in practice — every creator video uses captions; per the cluster `SKILL.md` line 15). Sister cluster-compose tasks for B/D/E (T-340, T-348, T-361) follow the same shape and are not drafted yet — T-368 is the prototype that anchors the pattern. The handler bundle pattern mirrors `element-cm1` (T-161; `packages/engine/src/handlers/element-cm1/`) verbatim — Zod input/output schemas, `ToolHandler<I,O,MutationContext>` instances, a barrel + `register*Bundle()` function, paired `LLMToolDefinition[]` for the LLM-facing JSONSchema half, gen-tool-skills regen. The departure is that Cluster F handlers are **read-only** (no `patchSink.push(...)`) — they exist to translate brief intent into a preset binding, not to mutate the document.

## Architectural decisions

### D-T368-1. Read-only composers — zero JSON-Patch ops emitted

Compose handlers are **read-only**: they validate input, dispatch on metadata (style / accessibility-mode / clipKind / explicit-keywords), and return a `{ ok: true, presetId, clipKind, rationale, brand?, transcript? }` envelope. **No** handler calls `ctx.patchSink.push(...)`; the test suite asserts zero ops are queued after each handler invocation (per AC #18).

The `MutationContext` parameter type is preserved for symmetry with every existing canonical handler bundle (T-155..T-168 all use `MutationContext`), keeping the router's type signature uniform. Reviewer demand to switch to `DocumentContext` (the narrower read-only context) is acceptable but optional — the conventional posture across the codebase is `MutationContext` even for read-tier tools (`packages/engine/src/handlers/read/handlers.ts` precedent). Default: `MutationContext`.

The downstream consumer of the compose envelope (the `clip-animation` bundle's `mount_clip` tool, T-160) is the surface that emits JSON-Patch ops — Cluster F compose returns the binding decision; the executor or a follow-up tool call mounts the clip.

### D-T368-2. Bundle naming — `cluster-f-compose`

Bundle name: `'cluster-f-compose'`. Rationale:

- **Cluster-prefixed** — every sister cluster-compose bundle (T-340 → `cluster-b-compose`, T-348 → `cluster-d-compose`, T-361 → `cluster-e-compose`) follows the same `cluster-{letter}-compose` convention. Predictable for the gen-tool-skills generator + agent-facing skill discovery.
- **Single-purpose suffix** — `-compose` distinguishes from canonical mutation bundles (`element-cm1`, `slide-cm1`, `table-cm1`). Compose bundles map intent → preset; mutation bundles map tool → JSON-Patch.
- **Lowercase kebab-case** — matches every existing handler bundle name (`element-cm1`, `slide-cm1`, `clip-animation`, `arrange-variants`).

The bundle name appears in: `ELEMENT_CM1_BUNDLE_NAME` constant analog → `CLUSTER_F_COMPOSE_BUNDLE_NAME = 'cluster-f-compose'`; each handler's `bundle: CLUSTER_F_COMPOSE_BUNDLE_NAME`; the auto-gen skill at `skills/stageflip/tools/cluster-f-compose/SKILL.md`; the `OWNER_TASK_MAP['cluster-f-compose'] = 'T-368'` entry in `gen-tool-skills.ts`.

### D-T368-3. Non-canonical bundle — registered via `registry.register(...)`, NOT `mergeTools`

`packages/engine/src/bundles/catalog.ts` declares 14 canonical bundles. The catalog is **sealed** — adding a 15th canonical entry requires an ADR and broad coordination across `CANONICAL_BUNDLES`, `gen-tool-skills.ts` `OWNER_TASK_MAP`, the bundles concept skill, and downstream consumers.

T-368 ships `cluster-f-compose` as a **non-canonical** bundle: `registerClusterFComposeBundle(registry, router)` calls `registry.register({ name: 'cluster-f-compose', description: '...', tools: CLUSTER_F_COMPOSE_TOOL_DEFINITIONS })` — `register` (not `mergeTools`) because the catalog has no pre-existing entry to merge into (`mergeTools` throws on unknown bundles per `bundles/registry.ts` line 27). The bundle appears in `BundleRegistry.list()` after registration but never lives in `CANONICAL_BUNDLES`.

This decision applies symmetrically to T-340 / T-348 / T-361 once those are drafted. If a future ADR consolidates the four cluster-compose bundles into the canonical catalog, that's a v2 migration.

### D-T368-5. Preset-id dispatch table

The four tools dispatch on input metadata to exactly one of the 6 Cluster F preset IDs. Verbatim mapping:

| Tool | Discriminator | Routes to |
|---|---|---|
| `compose_creator_caption` | `style: 'hormozi'` | `hormozi-montserrat-black` |
| `compose_creator_caption` | `style: 'mrbeast'` | `mrbeast-komika-axis` |
| `compose_creator_caption` | `style: 'tiktok'` | `tiktok-rounded-box` |
| `compose_creator_caption` | `style: 'ali-abdaal'` | `ali-abdaal-opacity-karaoke` |
| `compose_creator_caption` | `style: 'netflix'` | `netflix-invisible` |
| `compose_creator_caption` | `style` absent | `tiktok-rounded-box` (platform-native default — highest-volume) |
| `compose_subtitle` | `accessibility_mode: 'strict'` (default) | `netflix-invisible` |
| `compose_subtitle` | `accessibility_mode: 'relaxed'` | `tiktok-rounded-box` (platform-native; non-FCC-grade fallback) |
| `compose_lyric_video` | `style: 'progressive-wipe'` (default) | `karaoke-progressive-wipe` |
| `compose_keyword_highlight` | `style: 'hormozi'` (default — yellow / green / red keyword color-pop) | `hormozi-montserrat-black` |
| `compose_keyword_highlight` | `style: 'mrbeast'` (green-on-monetary subvariant) | `mrbeast-komika-axis` |

Dispatch is implemented as a `switch` on the discriminator string in each handler. Unknown style values fail Zod validation (the schema enums are sealed); the handler never receives a non-canonical style.

The dispatch table is encoded as a single `const PRESET_DISPATCH = { ... } as const` map at the top of `handlers.ts` so every handler reads from one source of truth — no duplicated string literals.

### D-T368-6. `compose_subtitle` defaults `accessibility_mode: 'strict'` → `netflix-invisible`

Per Cluster F's accessibility canon (`SKILL.md` lines 51–58 + `netflix-invisible.md` lines 22, 60–63), `netflix-invisible` is the **only** Cluster F preset that guarantees strict-subtitle rules (≥ 833 ms minimum per event, 42-char-per-line / 2-lines-max upstream invariant, sentence-case canonical, `muteOpacity: 0` strict-accessibility active-only visibility, FCC-grade legibility). When the subtitle composer is invoked **without** an explicit `accessibility_mode`, the handler defaults to `'strict'` and routes to `netflix-invisible`. The output envelope's `rationale` field documents this default explicitly: `"defaulted to 'strict' accessibility_mode → netflix-invisible (FCC-grade subtitle register)"`.

`accessibility_mode: 'relaxed'` routes to `tiktok-rounded-box` (the only Cluster F caption preset with platform-native register that survives non-strict subtitle scenarios — e.g., short-form-vertical creator content where Netflix's strictness is over-engineered). Future relaxed-mode targets are a v2 enum extension; v1 is sealed at `'strict' | 'relaxed'`.

### D-T368-7. `compose_lyric_video` routes to `karaoke-progressive-wipe`

`karaoke-progressive-wipe` is the **only** Cluster F preset with `clipKind: lyrics` (verified at `skills/stageflip/presets/captions/karaoke-progressive-wipe.md` line 4); the other 5 are `clipKind: caption`. `compose_lyric_video` is sealed to `style: 'progressive-wipe'` in v1 (single-variant enum). Future lyric-video subvariants (e.g., `'static-stack'`, `'verse-page-flip'`) are v2 enum extensions.

The handler validates the input `lyrics: WordTiming[]` length ≥ 1 and the optional `music: { bpm?, beatGrid? }` shape, then returns `{ ok: true, presetId: 'karaoke-progressive-wipe', clipKind: 'lyrics', rationale, brand?, lyrics }`. The host/downstream `clip-animation` bundle mounts a `LyricsClip` (T-322) with the supplied `lyrics`.

### D-T368-8. `compose_keyword_highlight` routes to `hormozi-montserrat-black` (default) / `mrbeast-komika-axis`

Per `SKILL.md` line 50 ("Color highlights convey meaning. Hormozi's yellow/green/red highlight keywords; MrBeast's green highlights monetary amounts. When `compose_keyword_highlight` is invoked, the preset's color semantics apply") — the two presets in the cluster that semantically encode keyword-color meaning are `hormozi-montserrat-black` (default; broadest color palette) and `mrbeast-komika-axis` (green-on-monetary subvariant).

`compose_keyword_highlight` accepts `style?: 'hormozi' | 'mrbeast'` (default `'hormozi'`) + `keywords: string[]` (length ≥ 1) + `transcript: WordTiming[]` (length ≥ 1). The handler does **not** colorize the words inline — it returns a `{ presetId, clipKind: 'caption', keywords, transcript, rationale }` envelope; the downstream `clip-animation` mounts the preset and the preset's bundle defaults colorize the keyword-tagged words.

The keyword-tagging shape (per-word `emphasis?: 'keyword' | 'monetary' | 'standard'` field on `WordTiming`) is **not** computed inside T-368 — the host transcript-segmenter (or upstream agent step) tags words before the compose call. The handler echoes the input `transcript` array through to the output envelope verbatim.

### D-T368-9. Mixed `clipKind` dispatch — `caption` and `lyrics` both supported

Cluster F's preset stack mixes `clipKind`s — 5 presets bind to `caption` (T-316), 1 binds to `lyrics` (T-322; `karaoke-progressive-wipe`). Composer tools dispatch across both clipKinds: `compose_lyric_video` is the only tool that returns `clipKind: 'lyrics'`; the other three tools return `clipKind: 'caption'`. The output envelope's `clipKind` field is **always present** so downstream `clip-animation` knows which clip's `defineFrameClip` registration to mount.

This deviates from a hypothetical single-clipKind cluster (e.g., Cluster B's all-`scoreBug` posture, T-332a) — the cluster's compose tools are **clip-aware**, not clip-agnostic. The dispatch is via the per-tool routing table (D-T368-5), not via a free-form `clipKind` input.

### D-T368-10. Zod input/output schemas — discriminated unions on `ok`

Every handler emits a `z.discriminatedUnion('ok', [okSchema, errSchema])` output (mirrors `element-cm1` handlers verbatim). Output envelope:

```ts
const composeOk = z.object({
  ok: z.literal(true),
  presetId: z.enum([
    'hormozi-montserrat-black',
    'mrbeast-komika-axis',
    'tiktok-rounded-box',
    'ali-abdaal-opacity-karaoke',
    'netflix-invisible',
    'karaoke-progressive-wipe',
  ]),
  clipKind: z.enum(['caption', 'lyrics']),
  rationale: z.string().min(1),
  brand: brandShape.optional(),
  // tool-specific echoed payload (transcript / lyrics / keywords) — strict; one of the four shapes
}).strict();

const composeErr = z.object({
  ok: z.literal(false),
  reason: z.enum([
    'invalid_input',
    'unsupported_style',
    'transcript_empty',
    'keywords_empty',
  ]),
  detail: z.string().optional(),
}).strict();
```

The `reason` enum is sealed at 4 values; v2 extends additively. Input schemas use `z.object({ ... }).strict()` to reject extras (mirrors `element-cm1` discipline; D-T368-12).

### D-T368-11. `WordTiming` schema reused from `@stageflip/schema`

The shared `WordTiming` Zod schema lives in `@stageflip/schema` (per T-316 / T-322 — the Caption / Lyrics primitives consume it). T-368 imports `wordTimingSchema` from `@stageflip/schema` and reuses it verbatim — no local re-declaration. If `@stageflip/schema` exports a different name (e.g., `captionWordTimingSchema`), the handler imports under the existing name. Implementer verifies the import name from `packages/schema/src/index.ts` before drafting (likely `wordTimingSchema`; not in spec authority).

If the schema is not exported from `@stageflip/schema` (rare; would mean T-316 / T-322 declared it locally), Implementer escalates per CLAUDE.md §6 — adding a cross-package schema export is a separate concern.

### D-T368-12. Strict-mode Zod (every nested object) + sealed enums

Every input schema uses `z.object({...}).strict()` at top level + every nested object. Mirrors `element-cm1` handlers (every input/output schema is `.strict()`). Unknown fields throw at parse time; Implementer relies on Zod's strict mode rather than ad-hoc validation.

Sealed enums:
- `compose_creator_caption.style`: `'hormozi' | 'mrbeast' | 'tiktok' | 'ali-abdaal' | 'netflix'` (5 values; matches the 5 `caption`-clipKind Cluster F presets)
- `compose_subtitle.accessibility_mode`: `'strict' | 'relaxed'` (2 values; v1 sealed)
- `compose_lyric_video.style`: `'progressive-wipe'` (1 value; v1 sealed; v2 enum extension)
- `compose_keyword_highlight.style`: `'hormozi' | 'mrbeast'` (2 values; v1 sealed)
- Output `presetId`: 6 Cluster F preset IDs (D-T368-10)
- Output `clipKind`: `'caption' | 'lyrics'` (D-T368-9)

Reviewer demand for additional enum values (e.g., a 6th creator style not in the cluster, a 3rd subtitle accessibility mode) → escalate per CLAUDE.md §6; v1 enum surface is sealed.

### D-T368-13. `brand` passthrough — opaque, validated shape

Every tool accepts an optional `brand?: { primary?: string, accent?: string, font?: string }` (`primary` / `accent` are hex `#RRGGBB`, `font` is a font family string). The handler validates the shape but **does not interpret** the values — the `brand` is echoed through to the output envelope as-is. Downstream `clip-animation`'s `mount_clip` consumes the brand and merges with the preset's bundle defaults at clip-mount time.

`brand` is **opaque passthrough** — T-368 does not look up a tenant's design-system, does not resolve theme tokens, does not apply the brand to the transcript. v2 may add a `resolve_brand` companion tool that turns a tenant ID into `brand` tokens; not in scope for T-368.

Hex validation: `z.string().regex(/^#[0-9a-fA-F]{6}$/)` (mirrors `breaking-banner` D-T324a-4 / `score-bug` D-T332a-4 hex discipline). Empty `brand: {}` is valid (every sub-field is optional).

### D-T368-14. Test strategy — pure-function dispatch tests + bundle-registration smoke

`handlers.test.ts` (~12–15 cases) covers each handler's:

1. Happy-path dispatch for every enum branch (every `style` / `accessibility_mode` value → expected `presetId`)
2. Default-branch dispatch (style absent → fallback presetId; subtitle without accessibility_mode → `'strict'`)
3. Zod-validation error branches (transcript empty, keywords empty, invalid hex on `brand.primary`, unknown enum value, extra unknown field)
4. Zero JSON-Patch ops emitted (assert `ctx.patchSink.push` was never called via a spy / collector)
5. Output envelope shape — `presetId` matches D-T368-5 dispatch table; `clipKind` matches D-T368-9; `rationale` is a non-empty string

`register.test.ts` (~3–4 cases): bundle is registered (`registry.has('cluster-f-compose') === true`); registry tool count matches handler count (4); router resolves each tool name (`router.resolve('compose_creator_caption')` etc. is non-undefined); bundle name constant matches the bundle entry.

Test fixture: a minimal `MutationContext` factory (mirrors `element-cm1/handlers.test.ts` pattern) — empty document, in-memory `PatchSink` collector, no selection. Compose handlers don't read from `ctx.document`; the document is a no-op fixture.
