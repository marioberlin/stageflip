# T-474 — Audience-data persistence (Firestore)

**Branch**: `task/T-474-audience-data-persistence`

## Goal

Ship the **Firestore-backed `AudienceResultsStore` impl** per ADR-009
§D5. T-453 already shipped the interface + `InMemoryAudienceResultsStore`;
T-474 adds the production Firestore impl in `@stageflip/storage-firebase`,
matching the pattern T-411a established for `TenantSettingsStore`.

Carries three concerns:

1. **`FirebaseAudienceResultsStore` impl**:
   - Targets the `audience-sessions/{sessionId}` collection per
     ADR-009 §D5.
   - Events stored in the `events/` sub-collection (append-only).
   - 5 methods: `openSession` / `closeSession` / `appendEvent` /
     `readSnapshot` / `listEvents` / `setTtl` (matches T-453's
     interface + T-459's `listEvents` extension).
   - Uses the structural `FirestoreDocRefLike` / `FirestoreCollectionRefLike`
     pattern from `packages/storage-firebase/src/tenant-settings.ts`
     so unit tests run without an emulator.
2. **TTL enforcement**:
   - The session doc's `ttlAt` field drives Firestore's TTL policy
     (configured at deployment time on the `audience-sessions`
     collection).
   - Default `ttlAt = closedAt + 90 days` (for closed sessions) /
     `ttlAt = createdAt + 24 hours` (orphan sessions per ADR-009 §D5).
   - Per-tenant override via `TenantSettings.features.audience.retentionDays`.
3. **EU residency posture**:
   - Re-uses the existing `region-router.ts` (`@stageflip/storage-firebase`)
     pattern that routes per-tenant docs to the correct
     multi-region. EU tenants get the EU multi-region; default to US.
   - Audience-results writes use the tenant's resolved region from
     the existing router; the factory accepts the resolved Firestore
     reference.

**Strict scope** — production Firestore impl + tests. NO changes to
the storage interface (T-453's contract is frozen). NO changes to the
in-memory impl. NO Firestore emulator dependency (use the structural
shim pattern). NO new abuse-tracking-store impl (T-458 may be a
separate persistence task in a future hardening pass; T-474 covers
audience-results only).

## Implementation notes

- **Firestore collection layout** per ADR-009 §D5:
  - `audience-sessions/{sessionId}` — session doc.
  - `audience-sessions/{sessionId}/events/{eventId}` — append-only.
- **`openSession(doc)`**: write the session doc at
  `audience-sessions/{doc.sessionId}`.
- **`closeSession(sessionId, snapshot, closedAt, retentionDays?)`**:
  read the doc, merge `closedAt + snapshot`, set
  `ttlAt = closedAt + (retentionDays ?? 90 days)`.
- **`appendEvent(sessionId, event)`**: write to
  `audience-sessions/{sessionId}/events/{event.eventId}` (use
  `event.eventId` as the doc id so writes are idempotent).
- **`readSnapshot(sessionId)`**: read the session doc; return null if
  not exists; return the parsed `AudienceSessionDoc` otherwise.
- **`listEvents(sessionId, opts)`**: query
  `audience-sessions/{sessionId}/events/` ordered by `appendedAt`
  asc; apply `opts.after` (where `appendedAt > opts.after`) + `opts.limit`.
- **`setTtl(sessionId, ttlAt)`**: write `ttlAt` field on the session
  doc.
- **`updateQuizState(sessionId, mutator)`** (per T-473): read the
  doc, run the mutator, write back. Use a transaction if the
  Firestore shim supports it; otherwise document the race window.
- **EU residency**: the factory accepts a pre-resolved Firestore
  instance per `region-router.ts`'s contract — T-474 doesn't
  re-implement region selection.
- **Voter-token hashing**: NO hashing in the store — the caller
  (T-453's apps/api WS handler) hashes BEFORE calling
  `appendEvent`. T-474 just stores whatever the caller passes.
- **No `console.log`** in the store.
