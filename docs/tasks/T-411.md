# T-411 — Enterprise admin flows (tenant-level frontier enablement)

**Branch (downstream implementation)**: `task/T-411-enterprise-admin-impl` (or
multi-PR sequence under that prefix). **This** PR ships the spec only on
`task/T-411-enterprise-admin-spec`.

## Goal

Specify the architecture for **tenant-scoped frontier enablement**: the
storage layer, API surface, and permission-shim integration that together
implement ADR-005 §D3's `features.interactive: 'disabled' | 'preview' | 'ga'`
toggle.

The implementation must give a **tenant administrator** the ability to set
their tenant's `features.interactive` posture, must give the **interactive
runtime tier** a deterministic mount-time check that gates `liveMount` per
ADR-005 §D5, and must give **superadmins** the ability to override a tenant's
posture (e.g. for security-incident rollback).

T-411 is the spec; the implementation lands as a downstream task — likely a
**multi-PR sequence** given the storage + API + shim surface area. v1 admin
**UI is explicitly out of scope** (see §"Out of scope") and is deferred to a
named follow-up task.

## §13 (structural extension) statement

**NOT a structural extension.** This task adds:

- A new **storage row schema** (tenant settings) on an existing storage
  adapter — not a new field on `ClipKindBinding` / `RIRElement` /
  `RIRDocument`.
- A new **API surface** (CRUD on tenant settings) — does not change the
  document model, binding model, or renderer pipeline.
- A new **mount-time check** in the permission shim — reads a tenant flag;
  does not introduce a new clipKind, element type, or compositing mode.

Render verification N/A — no rendered output changes; the toggle gates
whether `liveMount` proceeds vs. falls back to `staticFallback`, both of
which already have render verification under their respective preset specs
(Cluster H static-fallback ratified; Track A finale gates the live half).

## Architectural decisions

### D-T411-1 — Storage layer: extend existing adapters; no new storage package

Add a `TenantSettingsStore` facet to `@stageflip/storage` (the contract) and
implement it on both `@stageflip/storage-postgres` and
`@stageflip/storage-firebase`. The in-memory adapter
(`InMemoryStorageAdapter`) gets the same facet for tests + dev.

Rationale:

- Tenant settings are **durable, low-frequency, single-row-per-tenant** —
  natural fit for the snapshot tier of the existing 3-method contract, not a
  new method category.
- A new `@stageflip/tenant-settings` package would re-implement adapter
  selection / region routing / connection pooling that the storage
  packages already do. Re-use beats parallel infra.
- The existing region-router (`storage-firebase/src/region-router.ts`) gives
  us EU/US tenant-data residency for free.

Counter-considered: a dedicated `@stageflip/tenant-settings` package fronting
the existing storage adapters via composition. Rejected because the surface
area (single CRUD on a single typed row) does not justify a new package
boundary at this stage. **If** the API grows to include audit log,
multi-region replication policy, and SSO config (a future task — explicitly
out of scope here), a dedicated package is the right time to extract.

### D-T411-2 — Schema: `TenantSettings` Zod schema, minimal v1 surface

```ts
// packages/storage/src/tenant-settings.ts (illustrative; the implementation
// will own the exact code — this spec defines the contract)
export const tenantSettingsSchema = z.object({
  tenantId: z.string().min(1),
  features: z.object({
    interactive: z.enum(['disabled', 'preview', 'ga']),
  }),
  updatedAt: z.string().datetime(),
  updatedBy: z.string().min(1),  // actor id of the admin who last changed it
}).strict();
export type TenantSettings = z.infer<typeof tenantSettingsSchema>;
```

**v1 surface is deliberately minimal.** Future fields (audit-log retention
window; per-permission-kind grants; per-region overrides; SSO config) are
out of scope. They can be added without breaking changes by widening
`features` and adding sibling fields.

### D-T411-3 — API surface: tRPC router + CLI command, no REST in v1

The implementation ships:

1. **tRPC router** at `packages/api/src/routers/tenant-settings.ts` (or
   wherever the existing tRPC root lives — implementer to confirm). Three
   procedures:
   - `tenantSettings.get(tenantId)` — read current settings; auto-creates
     row with v1 defaults (D-T411-5) if absent.
   - `tenantSettings.setInteractive({ tenantId, value })` — set the
     `features.interactive` posture; authorization check per D-T411-6.
   - `tenantSettings.list()` — superadmin-only; lists all tenants for
     incident-response triage.
2. **CLI command** `stageflip tenant set-interactive --tenant <id> --value
   <disabled|preview|ga>` — for break-glass operational use; same
   authorization gate as the tRPC procedure (D-T411-6) but executed via a
   service-account credential.

**No REST endpoints in v1.** The admin UI (deferred per D-T411-7) consumes
tRPC; ops uses the CLI. A REST surface adds versioning / OpenAPI overhead
without a current consumer.

### D-T411-4 — Permission-shim integration: extend ADR-005 §D5 step 1

ADR-005 §D5 enumerates the mount-time check sequence:

> 1. Reads `features.interactive` for the tenant; aborts to `staticFallback`
>    if posture is insufficient for the target.

T-411 wires step 1 to a **deterministic** read against an in-process cache
that the interactive-runtime host populates at session start. The cache
read is sync; the cache populator (called from the host shell, not from
clip code) is the only async / network surface. Clip-mount code stays
deterministic per CLAUDE.md §3.

The cache keys on `(tenantId, target)` where `target ∈ { 'html',
'browser-live-preview', 'on-device-display' }` per ADR-005 §D4. The
`features.interactive` value gates each target as follows:

| Setting | html / browser-live-preview | on-device-display |
|---|---|---|
| `'disabled'` | static-fallback only | static-fallback only |
| `'preview'` | live-mount permitted | static-fallback only |
| `'ga'` | live-mount permitted | live-mount permitted |

This matrix is restated from ADR-005 §D3; the implementation MUST link
back to it inline as the source of truth.

### D-T411-5 — Default value posture: new tenants default to `'disabled'`

A tenant row that does not exist yet (first call to `tenantSettings.get`)
returns `features.interactive: 'disabled'` and is auto-materialized into
the store on first write (lazy creation; reads are pure-function over
"absent or present").

Rationale:

- ADR-005 §D3 explicitly states "ships disabled by default for all
  tenants." This is the literal implementation.
- Default-deny is the only safe posture for a security-gated capability
  surface. A misconfigured tenant must not accidentally get live-mount.

Operators who want a tenant to ship in `'preview'` from day one MUST flip
the flag explicitly via the CLI or admin API as part of tenant
provisioning.

### D-T411-6 — Authorization: two-role model, hardcoded in v1

Two principals can change a tenant's `features.interactive`:

- **Tenant admin** (i.e. an actor whose JWT / session claim places them in
  the tenant's admin role) — may change THEIR tenant's flag between
  `'disabled'` and `'preview'`.
- **Superadmin** (a dedicated platform role; verified by JWT claim
  `role: 'superadmin'`) — may change ANY tenant's flag to ANY value,
  including escalation to `'ga'` and emergency rollback to `'disabled'`.

`'ga'` is deliberately superadmin-only. Per ADR-005 §D7, GA enablement
requires the security review (T-403) sign-off; a tenant admin clicking a
button cannot bypass it.

The role model is **hardcoded** in v1 — no RBAC plumbing, no role-grant
admin UI. This is sufficient for the GA criterion (5.1 + 5.2 just need the
flag plumbing wired). A richer role model (per-feature grants; delegated
admin; audit-log review-only role) is explicitly out of scope (see
§"Out of scope").

### D-T411-7 — UI deferral: out of scope for v1; downstream task

No admin UI ships with the v1 implementation. Operators set the flag via
the CLI (D-T411-3) or via direct tRPC call from a privileged context
(e.g. a one-off script).

A follow-up task (`T-411b` placeholder; orchestrator to assign) ships:

- The admin settings panel in the editor shell (or a dedicated `apps/admin`
  surface).
- A change-log view (depends on audit-log infra — also out of scope here).
- An RBAC management UI (depends on D-T411-6 maturation).

Rationale: the GA criterion is "tenant-level frontier enablement is
*operationally possible*", not "tenant admins have a polished settings
panel." CLI + tRPC satisfies the GA gate; UI is product polish.

### D-T411-8 — Rollout posture: instant, no migration window

Because `features.interactive` defaults to `'disabled'`, deploying the
T-411 implementation is instant-on without behavior change for any existing
tenant. The first behavioral effect happens when:

- A superadmin flips a tenant to `'preview'` → that tenant's `liveMount`
  paths become reachable for `html` and `browser-live-preview` targets.
- A superadmin flips a tenant to `'ga'` → that tenant's `liveMount` paths
  become reachable for `on-device-display` targets too.

**Rollback** is symmetric: superadmin flips back to `'disabled'`. The shim
re-reads on the next mount; in-flight live-mounts are not torn down (the
implementation MAY add a tear-down path as a follow-up if security review
asks for it; v1 ships with mount-time-only gating).

If a tenant gets stuck on `'preview'` and an interactive clip mounts
incorrectly, the recovery path is: superadmin CLI flip to `'disabled'` →
all subsequent mounts go to `staticFallback`. There is no "soft kill"
intermediate posture in v1.

### D-T411-9 — Testing posture

The implementation must include:

- **Unit tests** on the `TenantSettings` Zod schema (round-trip; reject
  invalid values; reject extra keys per `.strict()`).
- **Unit tests** on the tRPC procedures with each adapter (in-memory;
  Postgres via testcontainers per existing storage-postgres test posture;
  Firebase via the existing emulator hooks per storage-firebase tests).
- **Unit tests** on the authorization predicate — every transition matrix
  cell (tenant-admin × disabled→preview, etc.) tested explicitly,
  including the negative cases (tenant admin cannot set `'ga'`;
  cross-tenant calls denied).
- **Unit tests** on the permission shim's mount-time check — for each
  `(setting, target)` cell of the D-T411-4 matrix, assert the shim
  routes to `liveMount` vs `staticFallback` correctly.
- **Integration test** wiring all four (storage, API, authorization,
  shim) end-to-end against the in-memory adapter: superadmin flips
  tenant to `'preview'`, mounts a frontier clip into a `html` target,
  asserts `liveMount` was chosen; flips back to `'disabled'`, mounts
  again, asserts `staticFallback`.

Coverage: ≥85% on changed files per CLAUDE.md §11. The integration test
is the load-bearing one; unit tests cover the permutations.

## Out of scope

Explicit non-goals for T-411. These are valid follow-up tasks but MUST NOT
be folded into the T-411 implementation.

- **Admin UI.** Settings panel, change-log view, RBAC management screens
  (D-T411-7).
- **Audit log.** A persistent log of who-changed-what-when. Useful but
  separate concern; needs its own retention / privacy / region policy.
- **Multi-region replication policy.** Region-routing the storage tier is
  in scope (D-T411-1); a per-tenant override of region policy is not.
- **SSO integration** for the admin role (D-T411-6's tenant-admin / superadmin
  roles are claim-based; provisioning those claims is out of scope).
- **Per-permission-kind grants.** The `features.interactive` flag is
  global per tenant; finer-grained "preview for shaders only" gating is
  not v1.
- **Soft-kill of in-flight live-mounts on rollback** (D-T411-8). Mount-time
  gating only.
- **Telemetry dashboards.** The `permission-denied-tenant-flag`
  observability event is logged; aggregate dashboards are downstream.
- **Self-service GA enablement.** `'ga'` requires superadmin per D-T411-6;
  no self-service flow.
- **GraphQL or REST API surface.** tRPC + CLI only in v1 (D-T411-3).
