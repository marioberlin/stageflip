# T-428 — `@stageflip/3d-tripo` (Tripo3D character adapter; proprietary-byo; quad topology + auto-rigging; stub-mode v1)

**Branch**: `task/T-428-3d-tripo`

## Goal

Ship the **third reference adapter** in the Phase 14 β sequence
(T-426..T-434) and the **first 3D adapter**:
`@stageflip/3d-tripo`. Wraps the Tripo3D character-model generator
(commercial AI; quad-clean topology; auto-rigging; GLB output)
behind the `ThreeDAssetProvider` interface from T-419, declares an
`AdapterDescriptor` per T-418, and **exercises the
`proprietary-byo` license posture for the first time** (per
ADR-008 §D13: tenant supplies API credentials; the per-modality
license whitelist allows `proprietary-byo` for `three-d`).

T-428 follows the **structural template** T-426 / T-427 established.
The deltas vs the two TTS adapters:

| Field | Kokoro / Fish Speech (TTS) | Tripo3D (3D) |
|---|---|---|
| Modality | `tts` | `three-d` |
| `id` | `kokoro` / `fish-speech` | `tripo` |
| `license.kind` | `apache-2.0` | **`proprietary-byo`** |
| Tenant credentials | none | **required** (BYO API key; see "BYO credentials posture") |
| `sandbox.kind` | `in-process` / `sidecar` | **`remote-service`** (`baseUrlEnvVar: 'TRIPO_API_BASE_URL'`) |
| `costPerCall.usd` | `0` | **`0.50`** (per-asset; tenant pays Tripo) |
| `latencyMs.{p50,p95}` | sub-second / few seconds | **`60_000 / 120_000`** (~1–2 min; **batch tier**) |
| Output format | `wav` | **`glb`** (only) |
| Capability shape | `voices`, `sampleRates`, ... | `outputFormats: ['glb']`, `topology: 'quad-clean'`, `supportsAutoRigging: true`, `maxVertices: 50_000` |
| Stub payload | silent-WAV `data:` URI | deterministic **GLB** `data:model/gltf-binary;base64,...` URI (unit cube + 1 named bone) |
| Voice-consent path | n/a / cloned voices | n/a |

T-428 ships in **stub mode**: the `generate()` body emits a
deterministic placeholder GLB byte payload (a unit cube with a
single named bone `'root'`) and returns a shaped `ThreeDResult`.
Production wire-up (Tripo HTTPS API call + GLB download) is gated on
a follow-up task (T-428a) — same v1-stub-mode-with-production-deferral
pattern as T-426 / T-427.

T-428 is M-sized: one new package, ~350–500 LOC across 3 src modules
(descriptor / provider / stub-glb) + matched tests, ~250–400 lines
of spec, no schema / parity / clip / preset / ADR changes.

## Out of scope

| Item | Why deferred |
|---|---|
| **Production wire-up to the real Tripo HTTPS API** (multipart job submit, polling, GLB download to `AssetStorage`) | The Tripo public API surface in May 2026 is still iterating; locking the production path now would couple the adapter shape to the current vendor surface. Deferring to **T-428a** keeps T-428's blast radius tight + lets downstream T-437 (3D scene clip integration) develop against the deterministic stub. The `descriptor` shape declared here is the contract the production wire-up MUST match; T-428a only swaps the body, never the shape. |
| **Tenant-credential injection mechanism** (env var → typed `TripoCredentials` struct, secret rotation, per-tenant overrides) | The descriptor declares `sandbox: { kind: 'remote-service', baseUrlEnvVar: 'TRIPO_API_BASE_URL' }` — that env var is the production credentials anchor. A typed credentials struct lands with the production wire-up (T-428a); the stub-mode body never reads the env var. |
| **Topology / vertex-count enforcement** (refusing requests over `capability.maxVertices`) | The descriptor declares `maxVertices: 50_000`. Enforcement (refusing over-budget calls) is the orchestrator's job per ADR-008 §D6 — the adapter declares its budget; the routing layer (T-425) honors it. |
| **Triangle-soup or mixed-topology variants** (a Tripo-prop adapter, a Tripo-environment adapter) | Out of scope. T-428's descriptor declares `topology: 'quad-clean'` exclusively — character output only. Other Tripo product lines ship as separate adapters (separate packages with their own descriptors). |
| **Per-call cost metering / Tripo-side billing introspection** | `costPerCall.usd: 0.50` is the static representative-call hint. Real per-call billing requires a Tripo billing-API consumer; out of scope. |
| **Adapter-side caching** | `generate()` derives the canonical `cacheKey` per ADR-008 §D1 + returns it in `ThreeDResult.cacheKey`, but the adapter does NOT consult `AssetCacheStore` itself. The orchestrator (handler bundle T-423) is the cache owner. |
| **Telemetry / cost-emission on real calls** | Telemetry lives at the orchestrator boundary. |
| **AssetStorage upload of the GLB** | `generate()` returns `url` as an inline `data:model/gltf-binary;base64,...` URI for the stub. Production wire-up (T-428a) uploads to an `AssetStorage` adapter + returns the storage URL; the shape stays identical. |
| **Capability-validator hook into `CapabilityDescriptorParser`** | T-419 ships `validateThreeDCapability`; T-428 declares a capability that satisfies it but does NOT register the validator into a host-shell parser. Tests assert the descriptor passes `validateThreeDCapability` directly. |
| **Schema / parity / clip / preset / parity-golden / ADR changes** | All untouched. |

3. **Descriptor shape** (verbatim from ADR-007 §D1 + ADR-008 §D6):
   ```ts
   {
     id: 'tripo',
     modality: { kind: 'three-d' },
     capability: {
       outputFormats: ['glb'],
       topology: 'quad-clean',
       supportsAutoRigging: true,
       maxVertices: 50_000,
       // T-424 catalog-summary fields (read by skills-sync's
       // capabilitySummary helper for `three-d`):
       formats: ['glb'],
       maxPolyCount: 50_000,
     },

   ```
   `formats` + `maxPolyCount` are catalog-summary fields the T-424
   generator reads via `readStringArray('formats')` /
   `readNumber('maxPolyCount')` — the strict T-419
   `threeDCapabilityDescriptorSchema` is `.strict()` and would
   reject them. Tests assert: (a) the descriptor passes
   `parseAdapterDescriptor()`; (b) the relevant subset
   `{outputFormats,topology,supportsAutoRigging,maxVertices}`
   passes `validateThreeDCapability` after stripping the
   catalog-summary keys.
4. **`TripoThreeDProvider` class** implements `ThreeDAssetProvider`:
   - Constructor takes `{ mode?: TripoProviderMode }`.
     Default: `mode = 'stub'`. (No tenant-credential injection in
     v1 — the stub mode never makes a real API call; T-428a adds
     the credentials struct.)
   - `id` / `modality` / `capability` / `license` / `sandbox` /
     `costPerCall` / `latencyMs` are passed through from
     `tripoDescriptor`.
   - `generate(call: ThreeDCall): Promise<ThreeDResult>`:
     - Validates `call.prompt` is a non-empty string after trim;
       throws `Error` on empty.
     - In `'stub'` mode: synthesizes a deterministic placeholder
       GLB payload via `generateStubGlbDataUri(call.prompt,
       call.rig === true, call.seed)`; derives a canonical
       `cacheKey` via `deriveCacheKey({ modality: 'three-d',
       model: 'tripo:character', prompt: call.prompt, params: {
       outputFormat: 'glb', topology: 'quad-clean', rig:
       call.rig === true }, seed })`. Returns `{ cacheKey, url,
       vertices: 8, rigged: call.rig === true && capability.supportsAutoRigging }`.
       The unit-cube stub has 8 vertices regardless of input;
       `rigged` is honored when the caller asks AND the capability
       declares `supportsAutoRigging`.
     - In `'production'` mode: throws `NotYetImplementedError(
       'TripoThreeDProvider.generate: production wire-up deferred
       to T-428a (Tripo HTTPS API audit pending)')`. Validation
       fires BEFORE this branch.
5. **`generateStubGlbDataUri(prompt, rig, seed?)`** in
   `src/stub-glb.ts`:
   - Pure function. No `Date`, no `Math.random`, no `fetch`, no
     timers. Deterministic — same inputs → byte-identical output.
   - Builds a minimal valid GLB binary in TypeScript using
     `Uint8Array` + `DataView` (no external GLB library — write
     the JSON chunk + binary chunk directly). The GLB conforms to
     the [glTF 2.0 binary container spec](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#binary-gltf-layout):
     - 12-byte header: `magic = 0x46546C67` ("glTF"), `version = 2`,
       `length`.
     - JSON chunk: `chunkType = 0x4E4F534A` ("JSON"), padded to a
       4-byte boundary with `0x20` (space). JSON describes 1 mesh
       (a unit cube: 8 vertices, 12 triangles via 36 indices), 1
       node, 1 scene; when `rig === true` also a 1-bone skeleton
       named `'root'` and a single skin with identity inverse-bind
       matrices.
     - BIN chunk: `chunkType = 0x004E4942` ("BIN\0"), padded to a
       4-byte boundary with `0x00`. Holds the cube's positions,
       indices, and (when rigged) joints/weights/IBM data.
   - The JSON chunk does NOT embed `prompt` or `seed` — those
     differentiate the cache key only. The on-the-wire stub bytes
     vary only with the `rig` flag (rigged variant adds the skin +
     joints chunks).
   - Returns `data:model/gltf-binary;base64,<base64-of-GLB-bytes>`.
6. **Errors**:
   - `NotYetImplementedError` — class extends `Error`, name
     `'NotYetImplementedError'`, used in `'production'` mode.

## BYO credentials posture (the differentiator vs T-426 / T-427)

Tripo3D is the **first adapter to declare the `proprietary-byo`
license posture**. Per ADR-008 §D13 (line 657), the `three-d`
modality whitelist admits `apache-2.0`, `mit`, `proprietary-byo`,
and `proprietary-vendored`. `proprietary-byo` means:

- The adapter wraps a commercial vendor model (Tripo3D); the
  vendor's licensing terms govern model use.
- The tenant brings their own API credentials (a Tripo API key and
  potentially a base URL override). The descriptor declares the
  credentials anchor via `sandbox.{kind: 'remote-service',
  baseUrlEnvVar: 'TRIPO_API_BASE_URL'}` — that env var is the
  production wire-up's secrets entry point.
- StageFlip ships **no vendored model checkpoint** (vs.
  `proprietary-vendored` which would require an ADR clearance per
  T-422's `PROPRIETARY_OK` allowlist).
- The `pnpm check-asset-licenses` gate accepts the descriptor
  because `proprietary-byo` is in the `three-d` whitelist; tenant
  credential validation is a runtime concern at the orchestrator
  boundary (the host shell verifies the env var is set before
  invoking the adapter in production mode — out of scope for
  T-428).

T-428 ships only the descriptor declaration of this posture. The
production wire-up (T-428a) reads the env var, builds an HTTPS
client, and surfaces the `LF-ADAPTER-CREDENTIAL-MISSING` failure
class (per ADR-008 §D11) when credentials are absent. The stub
mode never reads the env var.

## Stub-mode vs production-mode contract

The `TripoProviderMode` discriminator gates the `generate()` body
behavior **only**. Every other surface (descriptor, capability,
validation, error throwing, cache-key derivation) is identical
between modes. The production wire-up (T-428a) MUST:

1. Keep `tripoDescriptor` byte-identical (no new capability fields
   in v1; capability expansion lands in T-428c at earliest).
2. Replace the `generate()` `mode === 'production'` branch with a
   real Tripo API call (HTTPS POST to the job-submit endpoint at
   `process.env[TRIPO_BASE_URL_ENV_VAR]`, polling the job-status
   endpoint, downloading the produced GLB).
3. Keep the input validation paths (empty prompt → throw)
   byte-identical.
4. Keep the cache-key derivation byte-identical (so cached
   results from the stub-mode era + production-mode era share the
   same keyspace — production-mode results MUST hash identically
   to stub-mode results when the same `(prompt, rig, seed)` is
   used; the canonical params dict declared here is the
   contract).
5. NOT widen the `ThreeDResult` shape (no new fields).
6. Honor the `capability.maxVertices` budget — refuse calls whose
   declared expected vertex count exceeds the budget (per
   ADR-008 §D6).

Anything in the production wire-up that conflicts with this
contract is a spec change — file an ADR.
