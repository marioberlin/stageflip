# T-411e — TenantSettings admin UI (minimal CRUD slice)

**Fifth and final downstream PR of T-411** (parent spec merged in #472,
commit `f25405d8`; storage layer merged in #473, commit `ebffa62f`;
API + CLI merged in #474, commit `ebfaf6bc`; permission-shim wiring
merged in #475, commit `1617207d`; concept SKILL + ADR-005 cross-link
merged in #476, commit `c4fe64ec`).

Closes T-411 §D-T411-7 (admin UI deferral) with a deliberately
**minimal CRUD slice**: a single Next.js admin route in
`apps/stageflip-slide` that reads the current `features.interactive`
posture for a tenant and lets a superadmin or tenant_admin update it.
No design system; no animations; no UX polish — that's the explicit
posture per parent §D-T411-7 and is the contract this PR defines for
the downstream UX-polish task.

## Architectural decisions

### D-T411e-1 — Single Next.js admin route under `apps/stageflip-slide` only

The admin UI ships in **one app** for v1: `apps/stageflip-slide`. The
slide app is the established Next.js shell where the editor mounts
(see `app/page.tsx`); putting the admin UI here does not require
spinning up a fourth app or a dedicated `apps/admin` surface.
Mirroring this route into `apps/stageflip-video` and
`apps/stageflip-display` is a downstream task — out of scope here.

**Path**: `apps/stageflip-slide/src/app/admin/tenant-settings/page.tsx`.
The `/admin/...` segment establishes the convention for future admin
surfaces in the slide app (RBAC management, audit-log view, etc. —
all out of scope for this PR).

### D-T411e-2 — Server component for the read; server action for the write

Per Next.js 15 App Router idiom, the page is a **React Server
Component** (no `'use client'` directive) that:

1. Resolves the current actor (D-T411e-3).
2. Computes the target `tenantId` — defaults to actor's tenant; a
   `?tenantId=...` query param lets a superadmin pick another tenant.
3. Reads the current settings via the injected `TenantSettingsStore`
   (default-deny synthesis if absent, mirroring T-411b's route handler).
4. Renders an HTML `<form>` whose `action` is a server action
   (`updateTenantInteractiveAction`) that calls `canSetInteractive`,
   patches the row, and revalidates the route.

Rationale:

- Server components remove the need to ship a tRPC client into the
  bundle (no new dependencies).
- Server actions match Next 15 conventions (the slide app is on
  Next 15.5).
- Direct in-process call to the same `canSetInteractive` predicate
  the API uses keeps the authorization logic single-sourced
  (no duplication; no drift risk).

**The route does NOT call `apps/api` over HTTP.** v1 keeps the data
plane in-process: the page injects its own `TenantSettingsStore`
instance (in-memory by default) so the admin UI is functional out of
the box without any deployment wiring. Production deployments will
inject a Postgres / Firebase store factory (same pattern as the API's
`createApp`) — that wiring is a deployment-tier task, not a UI task.

### D-T411e-3 — Actor resolution: stub helper with a clear contract for production replacement

Resolving the current actor (`{ role, org, sub }`) from the request is
a deployment concern (JWT cookies, Firebase session cookies, custom
headers) that the slide app does NOT currently solve. v1 ships a
**stub helper** at `apps/stageflip-slide/src/lib/admin-auth.ts`:

```ts
export interface AdminActor {
  readonly role: 'viewer' | 'editor' | 'admin' | 'owner' | 'superadmin' | (string & {});
  readonly org: string;
  readonly sub: string;
}

export async function resolveAdminActor(): Promise<AdminActor | null>;
```

The stub reads optional environment variables
(`STAGEFLIP_ADMIN_ROLE`, `STAGEFLIP_ADMIN_ORG`, `STAGEFLIP_ADMIN_SUB`)
for local dev / CI, and returns `null` if none are set. The page
treats `null` as "unauthenticated" → renders a 401-shaped message
(does not redirect; redirect target is undefined for v1).

Production deployments **replace this stub** by reading a session
cookie / JWT and projecting the verified principal onto `AdminActor`.
The contract is documented inline in the helper.

This matches the API's posture: `apps/api/src/server.ts` ships an
in-memory store + a TODO-stub `resolvePrincipal`; production deploys
override both.

### D-T411e-4 — Authorization gating in the page (read + write)

Both the read and the write are gated:

| Actor | Read own tenant | Read other tenant | Update own tenant | Update other tenant |
|---|---|---|---|---|
| `superadmin` | yes | yes | yes (any value, incl. `'ga'`) | yes (any value, incl. `'ga'`) |
| `admin` / `owner` (tenant_admin) | yes | no — 403 | yes (`'disabled' ↔ 'preview'` only) | no — 403 |
| `editor` / `viewer` | yes | no — 403 | no — read-only view, no form | no — 403 |
| unauthenticated | no — 401 | no — 401 | no — 401 | no — 401 |

The page reuses `canSetInteractive` from `@stageflip/app-api` for the
write check (the predicate's matrix is the source of truth). The
read check (cross-tenant gate) is restated inline because
`apps/api`'s read gate is a private helper (`denyReadIfCrossTenant`).
v1 reproduces it in the page; a future refactor can extract a shared
helper.

Tenant-admin / superadmin actors render the update form; other roles
render a read-only "current value" view with a help line explaining
that updates require an admin role.

### D-T411e-5 — Native HTML, no design system, ~10 lines of inline CSS

Per parent §D-T411-7 ("UI is product polish"; this PR's contract):

**In scope (functional CRUD):**
- Native HTML `<form>`, `<select>`, `<button>`, `<dl>`/`<dd>`/`<dt>`
  for the current-value display.
- ~10 lines of `<style>`-tag CSS for vertical spacing + label/input
  alignment + readability (font-family inherit; padding; max-width).
- A help paragraph linking to
  `skills/stageflip/concepts/tenant-settings/SKILL.md` (relative path
  is non-resolvable in the browser, but the link makes the contract
  discoverable from the rendered HTML and from "view source").
- Server-side error handling on the action (display an error message
  in the rendered page after redirect; v1 uses `redirect(...)` with a
  `?error=...` query param).

**Explicitly OUT of scope (the contract for the downstream UX task):**
- Design-system styling (Tailwind classes for layout polish,
  shadcn/ui components, custom theme tokens).
- Animations, transitions, hover states, focus rings beyond the
  browser default.
- Mobile responsiveness (no media queries; no responsive layout).
- Internationalization / i18n catalog wiring (CLAUDE.md §10 requires
  i18n for translated UI strings, but the v1 admin UI is English-only
  by deliberate choice; the downstream task wires i18n).
- Bulk admin views (list-all-tenants page; per-tenant detail with
  audit log).
- Audit log UI (depends on audit-log infrastructure — out of scope
  per parent T-411 §"Out of scope").
- Multi-tenant batch operations (e.g. flip 10 tenants to
  `'preview'` at once).
- RBAC management UI (delegated admin; per-permission-kind grants).
- Onboarding-style coachmarks; toast notifications; modal dialogs.
- Confirmation dialogs for destructive transitions (rolling back from
  `'ga'` to `'disabled'` mid-incident — covered by the CLI today).
- Real-time updates (WebSocket / SSE refresh on remote change).
- Session-aware "you are logged in as ..." header chrome.

The downstream UX-polish task takes this contract as a starting point
and replaces the rendered HTML with a designed surface; the server
action and the authorization gating are reusable (they already
encapsulate the data-plane behavior).

### D-T411e-6 — Per-process store instance; production wiring is deployment-tier

The page module instantiates a process-local
`InMemoryTenantSettingsStore` at module load. This is sufficient for
local dev (the admin UI works out of the box without any deployment
configuration) and is consistent with how `apps/api/src/server.ts`
defaults the same store (T-411b D-T411b-5).

Production deployments override this by replacing the
module-level store factory (or by reading a per-request store from a
Next.js `headers()` / `cookies()` context — left to the deployment
team). The store boundary is a single module-level constant; the
swap is one-line.

The store does NOT share state with `apps/api`'s store. v1's data
plane is in-process per app. Aligning them across apps is a
deployment-tier task — out of scope.

### D-T411e-7 — Testing posture

The page is testable via two surfaces:

- **Server action unit tests** — invoke `updateTenantInteractiveAction`
  directly with a stubbed actor / store; assert it routes to the
  predicate correctly and persists allowed writes. Server actions are
  plain async functions, so this is a pure unit test.
- **Component tests** — render the page as an async function and
  assert the rendered JSX (read-only vs update-form gating per
  D-T411e-4). Vitest + happy-dom + `@testing-library/react` per the
  existing `apps/stageflip-slide` test posture.

Three role-gated test cases cover the matrix:

1. **superadmin sees update form** for any tenant (own or other via
   `?tenantId=...`).
2. **tenant_admin sees update form** for own tenant only;
   cross-tenant request → 403.
3. **viewer / unauthenticated sees read-only** for own tenant; no
   form rendered.

Coverage: ≥85% on the new files per CLAUDE.md §11.

## Acceptance criteria

### Route + page

1. `apps/stageflip-slide/src/app/admin/tenant-settings/page.tsx`
   exists and is a Next.js App Router page.
2. The page is a server component (no `'use client'` directive at the
   page boundary).
3. The page resolves the current actor via
   `apps/stageflip-slide/src/lib/admin-auth.ts` (D-T411e-3).
4. When the actor is `null` (unauthenticated), the page renders a
   401-shaped message and does NOT render the form.
5. When the actor is `superadmin`, the page renders the update form
   for ANY `tenantId` (defaults to actor's `org`; `?tenantId=...`
   query param lets the superadmin pick another tenant).
6. When the actor is `admin` / `owner` (tenant_admin), the page
   renders the update form for the actor's own tenant only;
   cross-tenant requests → 403-shaped message and no form.
7. When the actor is any other role, the page renders a read-only
   "current value" view with a help line explaining update
   requirements; no form.
8. The page reads the current settings via a process-local
   `InMemoryTenantSettingsStore` instance (D-T411e-6); absent rows
   are synthesised as `{ features: { interactive: 'disabled' } }`
   (mirroring the API's default-deny posture).
9. The rendered form has a native HTML `<select>` with three options
   (`disabled`, `preview`, `ga`); the current value is pre-selected.
10. The form has a `<button type="submit">` and submits to the
    server action `updateTenantInteractiveAction`.
11. The page renders a help paragraph that links to
    `skills/stageflip/concepts/tenant-settings/SKILL.md` (path link).
12. The page renders `~10` lines of inline CSS via a `<style>` tag —
    no design-system classes, no Tailwind, no external CSS.

### Server action

13. `updateTenantInteractiveAction` (module:
    `apps/stageflip-slide/src/app/admin/tenant-settings/update-action.ts`)
    is a server action (`'use server'` directive at module top).
14. The action validates its input via Zod
    (`{ tenantId: string, value: 'disabled' | 'preview' | 'ga' }`);
    invalid input redirects to the page with `?error=invalid_input`.
15. The action calls `resolveAdminActor()` to resolve the current
    actor; `null` → redirect with `?error=unauthenticated`.
16. The action calls `canSetInteractive(actor, tenantId,
    currentValue, nextValue)` from `@stageflip/app-api`; on deny,
    redirect with `?error=forbidden&reason=<reason>`.
17. On allowed write, the action constructs a `TenantSettings` row
    via `tenantSettingsSchema.parse(...)`, persists via
    `store.putTenantSettings(...)`, calls `revalidatePath(...)` on
    the admin route, and redirects with `?status=updated`.
18. The action's clock + actor resolver + store are injectable via
    a module-level `setUpdateActionDeps(...)` testing hook (matches
    the in-process testing pattern across the codebase).

## Determinism posture

The admin route lives in `apps/stageflip-slide/src/app/**`, which is
NOT under the determinism-gated paths (`packages/frame-runtime/**`,
`packages/runtimes/**/src/clips/**`, `packages/renderer-core/src/clips/**`).
The server action uses `new Date().toISOString()` for `updatedAt`;
this is allowed because the file lives outside the §3 scope.

The clock IS injectable via `setUpdateActionDeps(...)` for test
hermeticity, not for determinism — good hygiene, not a §3
requirement.
