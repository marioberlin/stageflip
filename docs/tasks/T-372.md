# T-372 — Preset: `coinbase-dvd-qr` (qrCodeBounce, Cluster G)

**Branch**: `task/T-372-coinbase-dvd-qr`

## Goal

Promote the existing `coinbase-dvd-qr` preset stub from `status: stub` to `status: substantive` and ship it as the **fourth Cluster G (CTAs / social) preset to land** AND the **first consumer of the `qrCodeBounce` clipKind** in the parity-CLI resolver AND the **first production consumer of T-319's `qr-code-bounce` runtime-clip primitive** (just landed at main HEAD `4d0879c8`). The preset captures the Coinbase Super Bowl LVI DVD-screensaver QR canon: a standard square QR matrix on a pure-black `#000000` backdrop with **zero branding / zero text / zero context**, sized to ~22 % of the canvas's smaller dimension, traversing the frame with continuous reflective-rebound bounce physics, and uniformly cycling all dark modules through a rainbow HSL hue rotation over a 7 s cycle. Common uses: attention-max moments (Super Bowl, premiere events, viral campaigns) where the curiosity gap of an unbranded bouncing QR drives scan rates that branded variants cannot match (Coinbase delivered 20 M+ landing-page hits in 60 s on Super Bowl LVI by trusting absence).

T-372 is the **first** preset to bind the `qrCodeBounce` clipKind. The `'qrCodeBounce'` clipKind is in `VALID_CLIP_KINDS` (verified: `scripts/check-preset-integrity.ts` line 76) but has no entry in the parity-CLI resolver as of main `4d0879c8`. T-372 must therefore wire its binding via the **`PRESET_ID_BINDINGS` override map** keyed on `'coinbase-dvd-qr'` — Pattern C from `docs/handover-phase13-cluster-b.md` §"Pattern C", consistent with the entire Cluster B cohort AND the three Cluster G presets already merged (T-369 youtube-subscribe-bounce + T-370 tiktok-follow-pulse + T-373 social-handle-lower-third). The `DEFAULT_CLIP_KIND_RESOLVER` is **NOT** modified — there is no clipKind-default arm for `'qrCodeBounce'` in v1, and T-372 does NOT introduce one (the override-only pattern matches the entire Cluster G posture; clipKind-defaults are reserved for the all-presets-of-the-clipKind-share-a-binding case, which does not apply since v1 has exactly one `qrCodeBounce`-bound preset — T-372).

T-372 is **M-sized** — same envelope as T-369 / T-370 / T-373. ~30–45 LOC binding + snapshot constant (the snapshot is heavier than the other Cluster G snapshots because it carries a literal 21 × 21 QR matrix as a string-array constant) + single mid-bounce parity golden + sign-off in-PR. No primitive carve-out; no schema change. Inherits the Cluster G `PRESET_ID_BINDINGS` shape end-to-end from T-369 / T-370 / T-373.

T-372 carries the **first cluster-norm divergence on parity thresholds in Phase 13**: PSNR ≥ 38 dB / SSIM ≥ 0.94 instead of the cluster-norm 42 / 0.98. The motion-blur footprint of the bouncing QR (every frame moves by `~50 px` and the QR's high-contrast pixel-grid edges magnify any sub-pixel quantization mismatch) AND the per-frame hue cycling of every dark module (every frame produces a different `darkColor` hex) BOTH reduce parity precision below the steady-state-icon range that 42 / 0.98 assumes. The preset stub explicitly pre-declares these thresholds (line 48: "PSNR ≥ 38 dB (motion blur reduces precision), SSIM ≥ 0.94"); T-372 must respect them at the F-4 generator-flag invocation. **This is the architectural pin for T-372** — re-pin via `--psnr=38 --ssim=0.94 --mark-signed`, not the Cluster B / earlier-Cluster G cluster-norm.

Cluster G is currently **3/5 signed** as of main `4d0879c8` (T-369 youtube-subscribe-bounce + T-370 tiktok-follow-pulse + T-373 social-handle-lower-third). T-372 brings it to **4/5**. The remaining one (T-371 instagram-link-sticker — likely consumes the `'instagram'` branch of T-318 follow-prompt OR a separate `link-sticker` primitive; verify against `docs/implementation-plan.md` before pinning) ships in its own preset PR.

- **Backdrop**: pure black `#000000` (stub line 23). T-372 inherits the primitive default `DEFAULT_BACKGROUND = '#000000'` — does NOT pass `background` (the default dominates theme; consumer must explicitly override). Zero-brand canon per stub line 25.
- **QR shape**: standard QR code (the matrix dimensions + finder-pattern shape — three corner squares at top-left, top-right, bottom-left — convey "this is scannable") (stub line 23). T-372 ships a **synthetic 21 × 21 Version 1 placeholder matrix** carrying valid finder patterns + timing patterns + a synthetic data region (D-T372-2). 21 × 21 is the smallest QR-spec version (Version 1); chosen for compactness in the source file (~21 string rows fit in ~25 LOC vs. Version 5's 37 rows or Version 10's 57 rows). Does NOT encode any real URL.
- **Size**: ~22 % of canvas's smaller dimension (mid of stub's 20–25 % range; line 27). T-372 inherits the primitive default `DEFAULT_SIZE_PERCENT = 22` — does NOT pass `sizePercent`. At parity-CLI 1280 × 720, `rectSize = round(720 * 22 / 100) = 158 px` (square).

At fps 30, that's 1.33–2.0 px/frame. T-372 ships **`startVelocity: { vx: 8, vy: 6 }`** (per-frame; D-T372-3) — note this is in PIXELS PER FRAME (the primitive's velocity unit), corresponding to 240 / 180 px/s respectively. **D-T372-3 is a substantive divergence from the stub's "40–60 px/s" guidance**: 40–60 px/s = 1.3–2 px/frame would place the QR at position `(80, 60)` at frame 60 — top-left corner, visually understated. The brand-register identity is **the QR + rainbow + bounce shape**, not a literal Coinbase-spot speed. Faster velocities deliver a more visually-canonical mid-flight register at frame 60. Document this divergence in the PR body per D-T372-11.
- **Color cycle**: rainbow HSL hue rotation across all dark modules, 6–8 s cycle (stub line 25 + 36). T-372 inherits the primitive default `cycleFrames = ceil(fps * 7) = 210` at fps 30 (mid of 6–8 s range). At frame 60, `hue = 60 / 210 * 360 ≈ 102.86°` (yellow-green) → `darkColor ≈ #7BFF00` per HSL→RGB conversion. T-372 does NOT pass `colorCycle` (default applies).

### D-T372-2. Snapshot QR matrix — synthetic 21 × 21 Version 1 placeholder (does NOT encode a real URL)

The `qrMatrix` is REQUIRED on `qrCodeBouncePropsSchema`. T-372 must ship a literal matrix as a string-array constant in the snapshot. Two options were considered:

- **(A) Real Coinbase Super Bowl URL encoding** (e.g., `coinbase.com/sb`) — would require running an encoder at spec-write time AND would embed a third-party URL into the parity fixture. Risks: (a) the parity test only cares about the rendered pixel pattern, so real-URL fidelity is not load-bearing; (b) ambiguity around redistribution of an encoded third-party URL in test data; (c) URL encoding requires choosing error-correction level, mask pattern, and version, none of which affect the visual register beyond the pixel pattern.
- **(B) Synthetic placeholder QR matrix** (valid square shape with finder patterns; arbitrary data bits) — captures the visual register (the finder-pattern + timing-pattern + data-region shape that conveys "this is scannable") without encoding any real URL. Lower risk.

**Decision**: Option B. T-372 ships a **synthetic 21 × 21 Version 1 placeholder QR matrix** as a string-array constant `COINBASE_DVD_QR_MATRIX`. The matrix MUST:

- Be exactly 21 × 21 (Version 1 QR-spec dimensions; smallest valid).
- Carry the three canonical finder patterns: 7 × 7 squares at `(0, 0)–(6, 6)`, `(0, 14)–(6, 20)`, `(14, 0)–(20, 6)`. Each finder pattern is a 7 × 7 block with outer ring `'1'`, inner ring `'0'`, center 3 × 3 `'1'`.
- Carry timing patterns: row 6 (cols 8–12) alternating `'1010101'`; col 6 (rows 8–12) alternating same.
- Carry a synthetic data region: arbitrary `'0'`/`'1'` bits in the remaining cells. Does NOT need to be a valid encoded URL — Reed-Solomon error-correction parity bits are NOT computed.

The exact matrix is the Implementer's choice subject to the constraints above. Recommended approach: hand-construct a string-array literal (~21 lines of 21 chars each = ~440 chars) inline in the snapshot constant. Keep the matrix exported as a separate `COINBASE_DVD_QR_MATRIX` constant for testability (so a unit test can assert "matrix is 21 × 21" + "row 0 starts with `'1111111'` (top-left finder outer ring)").

If the Implementer prefers, they MAY lift the matrix from a publicly-available Version 1 QR encoder run on a placeholder string (e.g., `"PLACEHOLDER"`) — `qrcode-generator`, `qrcode` npm packages, or online encoders. Document the source string in a comment if so. **Do NOT use a real URL for the placeholder string** — even if the Reed-Solomon bits aren't load-bearing for parity, the URL would still be embedded as data bits.

If the matrix is malformed (wrong dimensions, missing finder patterns, jagged rows), the primitive's Zod schema will reject at validation time. The synthetic placeholder must pass `qrMatrixSchema` validation (square, 7–177 row count, equal-length rows, all `'0'`/`'1'`).

### D-T372-3. Velocity snapshot — `startVelocity: { vx: 8, vy: 6 }` (NOT 1.3–2.0 px/frame from stub line 36)

The stub specifies "Speed: moderate enough to allow scanning while in motion (40–60 px/s)" (line 36). At fps 30, that's `40 / 30 = 1.33` to `60 / 30 = 2.0` px/frame. With `startPosition: { x: 0, y: 0 }` and `startVelocity: { vx: 2, vy: 2 }`, position at frame 60 = `(120, 120)` — still close to the top-left corner; the QR has moved barely 1× its own width (`rectSize = 158`). Visually understated as a "mid-bounce" register; an observer would not distinguish "frame 60" from "frame 30" or "frame 90".

**Decision**: T-372 ships **`startVelocity: { vx: 8, vy: 6 }`** — 4–6× faster than the stub guidance. At frame 60: `naive position = (480, 360)`. Both axes are still in the first leg (no rebound yet — `spanX = 1280 - 158 = 1122`, `spanY = 720 - 158 = 562`; `480 < 1122` and `360 < 562`). Center-canvas placement; visually canonical mid-flight. Picking `vx ≠ vy` means the bounce trajectory is non-degenerate (avoids a 45° diagonal that always returns to corners — the canonical DVD-screensaver always uses different axis speeds).

**Rationale for the divergence**: the stub's 40–60 px/s figure is a reasonable scan-rate floor for real-world Coinbase-style ads (a viewer needs ~2–3 s of stable QR position to scan). For the **parity golden** — a single rendered frame, not a watching experience — the visually canonical "QR mid-flight, center-canvas, rainbow-cycling" register requires faster velocities. The brand-register identity is **the bouncing-rainbow-QR shape at a recognizable mid-flight position**, not a literal Coinbase-broadcast scan speed.

If a Reviewer demands the literal stub velocities (1.3–2.0 px/frame) → escalate per CLAUDE.md §6; the parity golden's purpose is to lock the visual register, not the consumer-facing scan rate. Real consumer renders can override `startVelocity` per their broadcast spot.

If the Implementer wants alternative tunings: `(10, 7)` lands at `(600, 420)` (right-of-center mid-flight); `(6, 9)` lands at `(360, 540)` (lower-of-center mid-flight); `(11, 11)` lands at `(660, 660) → fold(660, 562) → 464` so y = 464 (one rebound off the bottom edge — harder to read as "mid-bounce" since the rebound is invisible in a single frame). Stick with `(8, 6)` unless render review indicates otherwise.

### D-T372-7. F-4 generator flags — `--psnr=38 --ssim=0.94 --mark-signed` (NOT cluster-norm 42 / 0.98)

Per the F-4 generator-flag pattern (handover §"F-4 generator flags"): `--psnr=38 --ssim=0.94 --mark-signed` ships the preset-pinned thresholds AND the signed sign-off in a single generator invocation. NO manual hand-pin of `thresholds.json` post-generation; the generator writes 38 / 0.94 directly under F-4.

**Why 38 / 0.94 instead of cluster-norm 42 / 0.98**:
1. **Motion blur from bounce**: every frame moves the QR rectangle by ~`(8, 6)` px. The QR's high-contrast pixel-grid edges are at sub-pixel positions every frame; any rendering quantization mismatch (puppeteer vs. test harness) magnifies the per-pixel error. PSNR is sensitive to high-frequency edge discrepancies.
2. **Per-frame hue cycling**: `darkColor` changes every frame (hue advances by `360 / 210 ≈ 1.71°` per frame). Sub-degree HSL→RGB→hex quantization differences between renders produce per-pixel color differences across all dark modules. SSIM penalizes uniform-tone differences.
3. **Stub-pre-declared thresholds**: the stub explicitly sets these thresholds at line 48 ("PSNR ≥ 38 dB (motion blur reduces precision), SSIM ≥ 0.94"). The compass research artifact already accepted the precision trade-off.

Cluster-norm 42 / 0.98 is the steady-state-icon range (used by Cluster A lower-thirds, Cluster B scoreBugs, Cluster G T-369 / T-370 / T-373 which are all near-static or single-axis-animated). Bounce + per-frame hue cycle is the **first multi-axis continuously-animated parity register in Phase 13**; the precision floor is correspondingly lower.

If the F-4-flagged 38 / 0.94 still fails, escalate per CLAUDE.md §6 — that signals a deeper precision issue (e.g., font-fallback mismatch unrelated to T-372, or a primitive-side render bug). Do NOT silently widen thresholds further; root-cause first.
