## Architectural decisions

### D-T321b-1. Composition model — separate clip kind (`'lightLeak'`), NOT a `TitleSequenceClip` prop

T-321b ships a **separate clip kind** (`'lightLeak'`), NOT an extension of `TitleSequenceClip`'s props. Two options were evaluated; Option A (separate clipKind) is chosen — mirroring T-321a's D-T321a-1 decision verbatim.

- **Option A — separate `'lightLeak'` clipKind**. Standalone overlay clip with its own props (`mode`, `intensity`, `cycleFrames`, `color`, `position`). Composes onto a base render via z-stack ordering at the host-html level (e.g., `titleSequence` at z-1 + `grain` at z-2 + `lightLeak` at z-3). Pro: clean composition; testable in isolation; reusable across non-titleSequence clips (T-351 true-detective + T-353 severance + future Cluster D / atmospheric needs); matches the established carve-out pattern (T-321a, T-371a, T-356a, T-358a all introduced new clipKinds). Adding a new clipKind is a one-line bump in `VALID_CLIP_KINDS`. Cluster D presets that need multiple atmospheric effects (grain + lightLeak + particles) compose them as separate clips at host-html level — no coupling between effects.
- **Option B — `TitleSequenceClip` prop extension**. Extend T-321's props with optional `lightLeak: { mode, intensity, cycleFrames, color }` block. Pro: tight integration; no new clipKind. **Con**: violates T-321's documented out-of-scope table (the `lightLeak` carve-out was committed at T-321 spec time); concentrates Cluster D effect logic into titleSequence (won't reuse for any other clip — particles, photographic-overlay each become a separate prop, ballooning the schema); T-321 v1 schema is in `.strict()` mode and rejects unknown props; T-321a already chose Option A for grain (architectural consistency demands lightLeak follow).

**Decision: Option A.** Matches T-321a precedent and the established carve-out pattern. Decouples atmospheric effects from the titleSequence primitive. Reusable across Cluster D consumers + future presets. The composition model is "host-html z-stack ordering": consumers wire `lightLeak` as a sibling clip in their preset config, not as a nested prop. Reviewer demand for Option B → escalate per CLAUDE.md §6; the sealed posture is Option A.

### D-T321b-2. Approach — single primitive, single Zod object schema with sealed flat `mode` enum

**Decision**: a single `lightLeak` primitive with a single `z.object({ ... }).strict()` schema and a sealed flat `mode: 'warm-corner' | 'warm-edge'` enum. Mirrors T-371a sealed-flat-enum posture. Diverges from T-321a (which has NO enum at all because grain has no spatial-register split) and from T-317 / T-318 (which have a sealed `platform` enum + `discriminatedUnion`).

The Orchestrator evaluated three approaches:

- **Approach A (single primitive, single object schema, sealed `mode` enum)** — Single `lightLeak` primitive. ~250–400 LOC. Two visual modes dispatched at render time via a switch on `mode`: `'warm-corner'` renders an `<svg>` with `<radialGradient>` anchored at a corner; `'warm-edge'` renders an `<svg>` with `<linearGradient>` swept along an edge. Numeric props (`intensity ∈ [0, 1]`, `cycleFrames ≥ 1`) modulate amplitude / frequency. **Chosen.**
- **Approach B (single primitive, single object schema, NO enum — derive mode from `position` shape)** — Infer mode from whether `position` is corner-shaped or edge-shaped. **Rejected.** Implicit dispatch is hostile to readers; explicit sealed enum is preferred.
- **Approach C (separate primitives per mode — `light-leak-corner`, `light-leak-edge`)** — Excessive split for v1; rejected outright. The two modes share intensity-envelope math + color-prop wiring + region-resolution logic; splitting into two clipKinds doubles the registration surface for marginal benefit. Multi-clipKind splits reserved for fundamentally different render approaches (e.g., when a future T-321b-extend introduces `'random-blob'` mode that needs multi-element rendering, the splits may be justified).

**Rationale for A**:

1. **Spatial register requires explicit dispatch.** Corner vs. edge are visually distinct registers; the user-facing prop should make the choice obvious.
2. **Sealed-flat-enum proven.** T-371a's `variant: 'short' | 'long' | 'compact'` ships happily as a single-schema sealed enum; T-321b reuses that posture.
3. **Forward-compatible.** Adding `'random-blob'` (T-321b-extend), `'edge-sweep'`, `'corner-rotation'`, etc. extends the enum non-breakingly. Cross-mode props (intensity, cycleFrames, color, position) stay shared.
4. **Smaller LOC budget than `discriminatedUnion`.** No per-mode Zod schema definitions; one schema with one enum field. Per-mode rendering in a single component via a switch.

Reviewer demand for Approach B / C → escalate; the architectural rule is sealed at A.

### D-T321b-3. Schema shape (Zod) — single object, strict mode, sealed `mode` enum

Top-level Zod schema is a single `z.object({ ... }).strict()` with a sealed flat enum field. Mirrors T-371a / T-319 / T-321a Zod discipline (hex-color regex where used, position schema, strict mode).

```ts
const HEX_COLOR_RE = /^#[0-9a-fA-F]{6}$/;

const positionSchema = z
  .object({
    /** Absolute pixel x within the canvas (top-left of light-leak region). */
    x: z.number(),
    /** Absolute pixel y within the canvas (top-left of light-leak region). */
    y: z.number(),
    /** Width of the light-leak region in canvas pixels. */
    width: z.number().positive().min(1).max(1920),
    /** Height of the light-leak region in canvas pixels. */
    height: z.number().positive().min(1).max(1080),
  })
  .strict();

export const lightLeakPropsSchema = z
  .object({
    /**
     * Spatial mode. Sealed flat enum.
     * - `'warm-corner'`: stationary `<radialGradient>` anchored at a corner of the region.
     * - `'warm-edge'`: `<linearGradient>` swept along an edge of the region.
     */
    mode: z.enum(['warm-corner', 'warm-edge']),
    /** Peak intensity ∈ [0, 1]. Default 0.5. */
    intensity: z.number().min(0).max(1).optional(),
    /** Frames per pulse cycle. Default 180 (7.5 s @ 24 fps). Minimum 1. */
    cycleFrames: z.number().int().positive().min(1).optional(),
    /** Hex color. Default '#FF8C00' (warm orange — Cluster D canonical register). */
    color: z.string().regex(HEX_COLOR_RE).optional(),
    /** Optional region; defaults to the full canvas at runtime. */
    position: positionSchema.optional(),
  })
  .strict();
```

`mode` is **required** (no default — the consumer must explicitly pick the spatial register). All other fields optional with sensible defaults applied at render time. Strict mode (no extras). Diverges from T-321a (which has no required fields) because lightLeak's spatial register is fundamental to the rendered output; defaulting it would mask consumer intent.

### D-T321b-4. Animation lexicon — frame-driven sin-wave intensity envelope (no `pattern` enum in v1)

T-321b v1 has NO `pattern` enum. The intensity is **always animated** via a smooth sin-wave envelope:

```
intensity(frame) = baseIntensity * (0.5 + 0.5 * Math.sin((frame % cycleFrames) / cycleFrames * 2 * Math.PI))
```

Pure trigonometry; closed-form. Output is `intensity(frame) ∈ [0, baseIntensity]`. The envelope produces the perceived "intermittent" register (the compass-canon term in stranger-things-benguiat.md line 26) — intensity rises to peak at the cycle midpoint and falls back to zero at cycle boundaries.

The "intermittent" canon term could imply a `'flash'` pattern (sudden on / off) instead of a smooth pulse; the Orchestrator evaluated both and chose pulse for v1 (per the Out of scope table — `'flash'` defers to T-321b-flash). Smooth pulse is the conservative interpretation: the leak fades in and out without abrupt transitions, which matches the analog warmth canon. If a Reviewer demonstrates the consumer preset requires sharp on / off transitions, escalate; T-321b-flash carve-out is the documented path.

There is no opt-out "static" mode in v1. If a Reviewer demands a static-leak phase (e.g., constant intensity throughout), escalate; that's a v2 enhancement. Consumers can approximate static via `cycleFrames: 1_000_000` (intensity stays near peak for the duration of any reasonable render), but this is not the documented path.

**Determinism**: the envelope is a pure function of `frame`, `intensity`, `cycleFrames`. `Math.sin` is bit-exact across V8 versions per ECMAScript (specified to use IEEE 754 double precision; same input → same output). Frame is integer; `cycleFrames` is integer; the modulo + division yields a rational approximation; `Math.sin` is the only float-arithmetic step. Snap to integer is NOT required because the output flows into SVG `stop-opacity` / `stroke-opacity` attributes which accept floats.

### D-T321b-5. Rendering surface — SVG gradients (`<radialGradient>` / `<linearGradient>`), NOT canvas + ImageData

T-321b v1 renders the leak via a single `<svg>` element with one `<radialGradient>` (for `'warm-corner'`) or `<linearGradient>` (for `'warm-edge'`) and one `<rect>` filled by the gradient. Diverges from T-321a (which uses `<canvas>` + `ImageData` for per-pixel noise).

Three approaches were evaluated:

- **`<canvas>` + `ImageData`** (T-321a's choice for grain): write per-pixel alpha values to a `Uint8ClampedArray` based on a gradient distance function. **Rejected for T-321b.** Per-pixel canvas is the right choice for noise (high-frequency per-pixel data with no DOM-native primitive); it's overkill for a smooth gradient. SVG `<radialGradient>` / `<linearGradient>` are gradient-native: the rasterizer interpolates between gradient stops at sub-pixel precision. Cheaper render path; less code; no `useEffect` discipline needed.
- **SVG gradients** (`<radialGradient>` / `<linearGradient>` + `<rect>`): **Chosen.** Gradient stops have integer offsets and rational opacity values; rasterizer produces deterministic output across CDP versions because SVG gradient interpolation is fully specified by SVG 1.1 (unlike `<feTurbulence>` whose pseudo-random number generator is implementation-defined). Pro: minimal DOM (one `<svg>` + one `<defs>` + one `<rect>`); zero `useEffect` (the SVG attributes are pure JSX renders driven by `useCurrentFrame()`); native gradient interpolation; trivial parity-golden capture.
- **CSS `background: radial-gradient(...)` on a `<div>`**: alternative gradient render path. **Rejected.** CSS gradient interpolation across CDP versions is less tightly specified than SVG (gamma-correct vs. naive interpolation differs between Chromium versions); SVG is the safer determinism path. Also, CSS `background-image` parity-golden capture is more brittle than SVG attribute capture.

**Why differ from T-321a's canvas choice?** Per-pixel noise (T-321a) needs deterministic per-pixel control — gradient interpolation is the wrong tool. Smooth gradients (T-321b) are exactly what SVG `<radialGradient>` / `<linearGradient>` are good for, and unlike `<feTurbulence>` (pseudo-random noise filter; CDP-version-dependent output), gradient interpolation IS deterministic across CDP versions per SVG 1.1 §13.2 (gradient interpolation is a well-defined linear blend in the gradient's color-interpolation space). Document the choice in the file header.

**Determinism caveat — color interpolation space**. SVG defaults to `color-interpolation: sRGB` (gamma-encoded space) which is the same default across all CDP versions. T-321b explicitly sets `color-interpolation="sRGB"` on the `<svg>` element to guard against any future CDP default change. Verified 2026-05-08 against Chromium 130 + Chromium 132; output bit-identical for the same gradient stops + region.

### D-T321b-6. Per-mode rendering — switch-on-`mode` dispatch within one component

Single component with switch-on-mode dispatch:

- **`'warm-corner'`** mode: `<radialGradient>` with `cx` / `cy` at a region corner (default top-left = `cx=0% cy=0%`); two stops `[#FF8C00 with stop-opacity=intensity(frame)]` at `offset=0%` and `[#FF8C00 with stop-opacity=0]` at `offset=100%`; gradient radius `r=70%`. The `<rect>` fills the region.
- **`'warm-edge'`** mode: `<linearGradient>` with `x1=0% y1=0% x2=100% y2=0%` (default left-to-right edge sweep); two stops at `offset=0%` and `offset=100%` with stop-opacity values modulating across frame. For v1, the gradient is fixed left-to-right; the *intensity envelope* (D-T321b-4) modulates the overall stop-opacity uniformly. (A future T-321b-sweep follow-up may add a frame-driven `offset` shift for true sweep motion.)

Both modes share the intensity envelope: `intensity(frame) = baseIntensity * (0.5 + 0.5 * Math.sin((frame % cycleFrames) / cycleFrames * 2 * Math.PI))`. The envelope output flows into the `<stop stop-opacity="...">` attribute of the gradient stops.

The corner / edge defaults to top-left / left edge respectively in v1; consumers can override the spatial anchor by passing a `position: { x, y, width, height }` that shifts the bounding box (the gradient is anchored to the region's coordinate space). True corner / edge selection (top-right vs. bottom-left, top vs. left edge) defers to a future T-321b-anchor follow-up if a preset demonstrates the need; v1 ships fixed-anchor.

Stable SVG instance IDs derived from props for the `<linearGradient>` / `<radialGradient>` `id` attribute: `light-leak-${mode}-${seed-hash-of-color-and-position}` where the seed-hash is derived from the `color` + `position.x` + `position.y` via a deterministic integer hash (same posture as T-321a's hash mixer; can be a smaller variant or `JSON.stringify`-then-djb2). The `<rect fill="url(#light-leak-...)">` references the gradient. NO `crypto.randomUUID()`, NO `useId()` (which is non-deterministic across SSR / CSR boundaries).

### D-T321b-7. Determinism

Frame-derived only. No `Date.now()`, no `Math.random()`, no `crypto.randomUUID()`, no `setTimeout`, no `setInterval`, no `fetch`, no `navigator.*`. The intensity envelope is closed-form (per D-T321b-4); the SVG attributes are pure JSX renders driven by `useCurrentFrame()`. SVG instance IDs are derived from props via a deterministic integer hash (NO `crypto.randomUUID()`, NO React `useId()`).

`scripts/check-determinism.ts` globs `packages/runtimes/*/src/clips/**/*.{ts,tsx}` — the new file is automatically in scope. No gate plumbing needed.

Float drift hazards:

- **`Math.sin` output**: bit-exact across V8 versions per ECMAScript (specified to use IEEE 754 double precision); `Math.sin(x)` for the same `x` always returns the same float. No drift.
- **`%` (modulo) for integers**: bit-exact. `frame % cycleFrames` for integer inputs returns integer.
- **Float-multiplication chain** `(frame % cycleFrames) / cycleFrames * 2 * Math.PI`: each step is IEEE 754; result is bit-exact for the same inputs.
- **SVG attribute serialization**: React serializes float attributes via `String(...)` which is bit-exact for the same float. No drift.

**Determinism test**: render the same props twice at frame 60; both renders produce byte-identical SVG attribute output (catches accidental `Date.now()` / `Math.random()` / float drift). Verified in AC #29 / #30.
