# T-358 — Preset: `cricket-ball-by-ball-dots` (scoreBug annex, Cluster E)

**Branch**: `task/T-358-cricket-ball-by-ball-dots`

## Goal

Promote the existing `cricket-ball-by-ball-dots` preset stub from `status: stub` to `status: substantive` and ship it as the **second Cluster E preset to land** (after T-359 / `f1-sector-purple-green`). The preset captures the universal cricket broadcast convention for an over-progression visualization: a horizontal row of six dots representing the last six legal deliveries of the current over, color-coded by outcome (dot / 1 / 2 / 4 / 6 / wicket). It is the **scoreBug annex** of the data cluster — uses the `scoreBug` `clipKind` but for ball-by-ball over visualization, NOT a full broadcast scoreBug header (those are Cluster B, owned by T-332+).

T-358 doubles the empirical evidence that the **preset → parity-fixture → signed** workflow holds. T-359 was the first preset to flow through the chain; T-359a built the multi-variant infrastructure; T-359b signed the first golden; T-359c made the prod renderer runnable end-to-end. T-358 inherits all three and runs the same loop on a different cluster-E preset and a different `clipKind`.

T-358 is **S-sized**: markdown promotion + a single canonical mid-hold parity fixture + a small resolver entry wiring `scoreBug → <runtime-clip>` in `packages/parity-cli/src/generate-fixture.ts`. No new runtime-clip primitive (see D-T358-2).

## Architectural decisions

### D-T358-1. On-disk location — modify the existing stub in place

The stub already exists at `skills/stageflip/presets/data/cricket-ball-by-ball-dots.md`. T-358 **modifies** that file — does NOT create a new one. `id`, `cluster: data`, `clipKind: scoreBug` stay. Mirrors T-359's stub-promotion pattern.

### D-T358-2. Bound primitive — declared in prose; NO new runtime-clip in T-358

The `scoreBug` `clipKind` is an integrity-gate sentinel today (in `VALID_CLIP_KINDS`). No existing runtime-clip in `packages/runtimes/frame-runtime-bridge/src/clips/` is a clean semantic fit for "row of six outcome dots" — `kpi-grid` is a 2-or-3 column dashboard, `lower-third` is a chyron, `timeline-milestones` anchors on dates.

T-358's posture (mirrors T-359 D-T359-4 — "prose binding IS the contract"):

- The preset's `## Rules` names the canonical render binding **in prose** — likely **`kpi-grid` configured with `columns: 6, rows: 1` and per-card outcome-color overrides**, OR a tiny inline composition built by the resolver's `buildProps` shim. Implementer's call within S-size.
- T-358 does NOT add a new clip file under `packages/runtimes/frame-runtime-bridge/src/clips/`. A bespoke `score-bug-dots` primitive is a separate task.
- If NO existing primitive can carry the visual register acceptably (parity render visibly broken), escalate per CLAUDE.md §6.

### D-T358-3. Single canonical mid-hold variant; NO multi-variant goldens

Cricket dots have six natural per-ball outcomes (dot / 1 / 2 / 4 / 6 / W), but the preset's semantic point is **the over as a sequence**, not a per-ball palette swap. T-358 ships **one mid-hold fixture** showing a representative over — e.g. `[1, 0, 4, W, 0, 2]` — so all six outcome colors appear in one frame.

Contrast with T-359 (three variants, one per `state` prop): T-359 had three semantically distinct mid-holds; T-358 has one mid-hold displaying six outcomes within it. The T-359a multi-variant infrastructure is exercised in trivial-arity mode (one entry).

### D-T358-4. `scoreBug` resolver entry in `packages/parity-cli/src/generate-fixture.ts` — IN SCOPE

T-359a wired `bigNumber → animated-value` as the first entry in `DEFAULT_CLIP_KIND_RESOLVER`. T-358 adds the second:

```ts
const scoreBugDotsBinding: ClipKindBinding = {
  runtimeId: 'frame-runtime',
  clipName: '<bound-primitive per D-T358-2>',
  buildProps(variant) {
    // No variant → canonical six-ball over.
    return { /* six dots, color-coded per outcome */ };
  },
};

export const DEFAULT_CLIP_KIND_RESOLVER: ClipKindResolver = (clipKind) => {
  if (clipKind === 'bigNumber') return bigNumberBinding;
  if (clipKind === 'scoreBug') return scoreBugDotsBinding;  // T-358
  return undefined;
};
```

Budget: ~10–15 LOC. If `buildProps` grows past ~15 LOC (inline React tree, duplicated color-mapping that belongs in a helper), escalate — that signals a bespoke runtime-clip is needed and the resolver entry is the wrong abstraction.

### D-T358-5. Hand-pin PSNR ≥ 42 dB, SSIM ≥ 0.98 in `thresholds.json`

Generator default is `35 / 0.95`. T-358's content is flat-color geometric (six circles, optional over-count label) — tighter thresholds are tolerable. T-358 matches T-359's pin (`42 / 0.98`) for cluster-E consistency. The stub's `## Acceptance (parity)` already names these.

This surfaces (does NOT fix) the **preset-driven-thresholds follow-up** flagged during T-359b — the generator should read thresholds from preset frontmatter, not require post-render hand-pinning.
