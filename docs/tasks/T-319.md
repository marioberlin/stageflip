# T-319 — `QRCodeBounce` primitive

**Branch**: `task/T-319-qr-code-bounce-primitive`

## Goal

Ship a frame-runtime-bridge clip — `qr-code-bounce` (kebab-case file/kind, mirroring `follow-prompt` / `subscribe-button` / `breaking-banner` / `news-ticker-bar` / `lower-third` / `score-bug`) — that renders a DVD-screensaver-style bouncing QR-code rectangle with rainbow color cycling on a pure-black backdrop. The primitive is the missing piece that blocks T-372 `coinbase-dvd-qr` (Cluster G's QR-canon preset) and is the architectural sibling of T-317 (`SubscribeButton`, shipped at `1cc4da93`) and T-318 (`FollowPrompt`, shipped at `46d81348`); together the three primitives unlock all five Cluster G presets. T-319 is the **third + final** Cluster G blocking primitive.

T-319 is **deliberately distinct from T-317 and T-318**. T-317 ships a *horizontal subscribe pill* (one-shot entrance bounce, anchored bottom-right of a 16:9 frame). T-318 ships a *circular avatar with corner badge* (always-present, periodic attention-pulse, anchored right-thumb-zone of vertical video). T-319 ships a fundamentally different visual register: a *square QR-code rectangle traversing the screen* with continuous DVD-screensaver bounce physics + rainbow hue cycling on a pure-black background, **zero branding, zero text, zero context**. The Cluster G consumer canon (per `skills/stageflip/presets/ctas/coinbase-dvd-qr.md` line 41) anchors the spec: *"ZERO branding is the point. Every brand element added kills the curiosity gap."* The visual diverges from T-317 and T-318 on every axis (geometry, anchor, animation lexicon, color register, presence model).

T-319 is also distinct in **schema dispatch shape**. Unlike T-317 / T-318 which dispatch on a sealed `platform` enum (4 platform bundles each), T-319 has **NO platform enum** — QR codes are platform-agnostic. The schema is a single Zod object (no `discriminatedUnion`), with the `coinbase-dvd-qr` preset as the v1 canon. A future "branded QR" register (with logo overlays, corner-rounded modules, brand-tinted color schemes) is **deferred to T-319b** as an additive enum extension when the second consumer materializes.

QR encoding: T-319 v1 ships with a **pre-rendered QR pixmap** — the QR matrix is passed into the primitive as a 2D boolean array (or row-string array) via props, NOT live-encoded from a URL. Live URL → matrix encoding (via a license-clean library such as `qrcode-generator`) is **deferred to T-319a**. Rationale: the v1 use case (Coinbase fixed URL embedded in a 60-second commercial) does not need dynamic encoding; deferring keeps the primitive's dependency surface minimal and the bundle bytes small. The matrix-as-prop posture is also test-friendly (tests pass synthetic 7×7 / 21×21 matrices without invoking a QR library).

T-319 is **M-sized**: ~400–600 LOC component + ~250–350 LOC tests + barrel + ~6 LOC catalog/manifest entries + changeset. Comparable to T-318 `follow-prompt` (M, ~400–600 LOC) and T-317 `subscribe-button` (M, 612 LOC). Slightly heavier than T-318 because the bounce-physics math (continuous 2D position interpolation with edge rebounds) + the rainbow hue cycle (per-module HSL → RGB color computation) introduce two non-trivial deterministic computations not present in either sibling. Slightly leaner because there is no `discriminatedUnion`, no per-platform render fan-out, no font surface, and no theme-text typography. Net: similar LOC budget. It does NOT touch T-372's preset markdown, parity resolver, or parity goldens — those land in T-372 (the consumer preset PR) after this primitive merges.

## Architectural decisions

### D-T319-1. Distinct primitive vs. extending `cta-pulse` / `subscribe-button` / `follow-prompt`

T-319 ships a **distinct** primitive (`qr-code-bounce`), NOT an extension of `cta-pulse` (T-202a), `subscribe-button` (T-317), or `follow-prompt` (T-318). Rationale:

- **Visual register diverges from all three siblings.** `cta-pulse` is a generic radial pulse around an arbitrary child. `subscribe-button` is a horizontal pill with a label. `follow-prompt` is a circular avatar with a corner badge. T-319 is a *square QR-code matrix bouncing across a black backdrop* — none of the three sibling registers come close.
- **Animation lexicon diverges.** `cta-pulse` ships radial pulsing. `subscribe-button` ships entrance-bounce + press-dip. `follow-prompt` ships bounded sustained-pulse + checkmark-morph. T-319 ships *continuous 2D position bounce with reflective edge rebounds* + *uniform hue cycling*. Different animation primitives.
- **Schema shape diverges.** The three siblings dispatch on a sealed `platform` enum (or `mode` enum for `cta-pulse`'s parent register family). T-319 has NO platform enum — QR codes are platform-agnostic by definition. The schema is a single Zod object.
- **Presence model diverges.** T-317 is a one-shot entrance. T-318 is always-present with periodic pulses. T-319 is *always-moving* — the QR rectangle never stops; it traverses the screen continuously for the clip's duration.
- **One consumer stub explicitly pins `clipKind: qrCodeBounce`** (`coinbase-dvd-qr.md` line 4). The clipKind is **already** reserved in `VALID_CLIP_KINDS` (line 76). The architectural intent is a dedicated primitive.
- **Cluster G's "absence as design" canon for the QR register** (per `coinbase-dvd-qr.md` line 41: *"ZERO branding is the point. Every brand element added kills the curiosity gap"*) demands a primitive that natively encodes the zero-brand discipline. The primitive's defaults (black background, rainbow modules, no overlays) bake this in.

Reviewer demand for merging into any sibling primitive → escalate per CLAUDE.md §6.

### D-T319-2. Approach — single primitive, single Zod object schema, no discriminatedUnion

**Decision**: a single `qr-code-bounce` primitive with a single Zod object schema (NO `discriminatedUnion`). Diverges from T-317 / T-318's posture intentionally — there is only one register in v1, no platform fan-out.

The Orchestrator evaluated three approaches:

- **Approach A (single primitive, single schema, no enum)** — Single `qr-code-bounce` primitive. ~400–600 LOC. No `platform` / `register` enum. `coinbase-dvd-qr` is the v1 consumer; future "branded QR" register adds via T-319b's additive enum extension. ALL_BRIDGE_CLIPS grows 54 → 55.
- **Approach B (single primitive, sealed `register: 'screensaver' | 'branded'` enum from day one)** — Pre-bake the future T-319b register split. ~500–700 LOC. Forces v1 to ship two register paths even though only one consumer exists. Adds dispatch surface for no v1 benefit.
- **Approach C (single primitive, single schema, but with extensibility hooks)** — Add a free-form `style?: Record<string, unknown>` prop to allow future palette / register extensions without schema changes. Breaks strict-mode discipline; deferred extensions become harder to seal.

**Rationale for A**:

1. **YAGNI.** v1 has exactly one consumer (`coinbase-dvd-qr`) and a clear zero-brand canon. Pre-baking the branded register adds dispatch surface for no current benefit.
2. **Additive enum extension is non-breaking.** When T-319b ships, adding a `register` enum with `'screensaver'` as the default value (the v1 behavior) does not break v1's call sites. The schema migration is backward-compatible.
3. **Consumer-stub-driven design.** `coinbase-dvd-qr.md` is the only stub binding `clipKind: qrCodeBounce`. The single-register shape is exactly what the canon demands.
4. **Smaller LOC budget.** No platform fan-out → no `renderXxx` per-bundle functions → no `switch (...)` dispatch block. The primitive is a single render path with conditional sub-rendering for animation phase.

Reviewer demand for Approach B (pre-baked enum) or Approach C (extensibility hooks) → escalate; the architectural rule is sealed at A.

### D-T319-3. Schema shape (Zod) — single object, strict mode

Top-level Zod schema is a single `z.object({ ... }).strict()`. NO `discriminatedUnion` (per D-T319-2). Mirrors the Zod discipline (hex-color regex, position schema, strict mode) of `subscribe-button.tsx` / `follow-prompt.tsx` without their union dispatch.

```ts
const HEX_COLOR_RE = /^#[0-9a-fA-F]{6}$/;

/** A QR matrix row is a string of '0' / '1' characters (e.g., "1010111"). */
const qrMatrixRowSchema = z.string().regex(/^[01]+$/);

/** A QR matrix is a non-empty array of equal-length row strings.
 * Width and height MUST match (square matrix). Validated via `.refine()`. */
const qrMatrixSchema = z
  .array(qrMatrixRowSchema)
  .min(7) // smallest QR-spec version is 21x21; we accept synthetic 7x7+ for tests
  .max(177) // largest QR-spec version is 177x177 (version 40)
  .refine((rows) => rows.every((row) => row.length === rows[0]!.length), {
    message: 'qrMatrix rows must all have equal length (square matrix)',
  })
  .refine((rows) => rows.length === rows[0]!.length, {
    message: 'qrMatrix must be square (rows.length === rows[0].length)',
  });

const positionSchema = z
  .object({
    /** Absolute pixel x within the canvas. */
    x: z.number(),
    /** Absolute pixel y within the canvas. */
    y: z.number(),
  })
  .strict();

const velocitySchema = z
  .object({
    /** Pixels per frame in the x-axis. Sign indicates direction. */
    vx: z.number(),
    /** Pixels per frame in the y-axis. Sign indicates direction. */
    vy: z.number(),
  })
  .strict();

const bounceSchema = z
  .object({
    /** Initial top-left position of the QR rectangle (px from canvas top-left). */
    startPosition: positionSchema,
    /** Initial velocity vector (px/frame). */
    startVelocity: velocitySchema,
  })
  .strict();

/** Color-cycle config. v1 sealed at `palette: 'rainbow'`. */
const colorCycleSchema = z
  .object({
    palette: z.literal('rainbow'),
    /** Cycle period in frames. Default ceil(fps * 7) (7s mid-range of 6–8 s canon). */
    cycleFrames: z.number().int().positive().optional(),
  })
  .strict();

export const qrCodeBouncePropsSchema = z
  .object({
    /** Square QR matrix (boolean-equivalent rows of '0'/'1' chars). 1 = dark module, 0 = light. */
    qrMatrix: qrMatrixSchema,
    /** Rendered rectangle size as a percent of the canvas's smaller dimension.
     * Default 22 (mid-range of 20–25 % per coinbase-dvd-qr.md line 27). */
    sizePercent: z.number().positive().min(5).max(80).optional(),
    /** Bounce physics config (start position + velocity). */
    bounce: bounceSchema,
    /** Color-cycle config; default rainbow with cycleFrames = ceil(fps * 7). */
    colorCycle: colorCycleSchema.optional(),
    /** Backdrop color hex. Default '#000000' (black, per Cluster G canon). */
    background: z.string().regex(HEX_COLOR_RE).optional(),
    /** Light-module color hex (the QR background color INSIDE the rectangle).
     * Default '#FFFFFF' (white) — the QR-spec canonical light color. */
    lightModuleColor: z.string().regex(HEX_COLOR_RE).optional(),
  })
  .strict();
```

All optional except `qrMatrix` and `bounce`. Strict mode (no extras). Mirrors the Zod posture of the sibling primitives. NO `.refine()` chain on the top-level (the matrix-shape `.refine()` lives on `qrMatrixSchema`); top-level properties are independent.

Note that — unlike T-317 (which requires `label`) and T-318 (which requires only `position`) — T-319 has *two* required top-level fields (`qrMatrix` + `bounce`) because both are domain-essential: there is no sensible "default QR matrix" (consumer must provide content) and there is no sensible "default starting position + velocity" (consumer must seed the trajectory).

### D-T319-4. Bounce physics — DVD-screensaver canon with reflective edge rebounds

The bounce is a continuous 2D linear-velocity traversal with reflective rebounds at canvas edges (preserving angle of incidence; |vx|, |vy| magnitudes preserved; signs flipped on edge contact). Per `coinbase-dvd-qr.md` line 39: *"Bounces preserve angle of incidence at edges (rebound physics)"*.

**Math** (frame-derived; integer-pixel positions for crisp parity):

Let the canvas inner-bounds be `[0, W - rectW] × [0, H - rectH]` where `W` and `H` are the canvas dimensions and `rectW = rectH = round(min(W, H) * sizePercent / 100)` is the rendered QR rectangle size. Let `(x0, y0)` be `bounce.startPosition` and `(vx, vy)` be `bounce.startVelocity` (in px/frame).

The naive integration is:

```
x_t = x0 + vx * t
y_t = y0 + vy * t
```

with reflective rebounds applied via the standard "fold + mod" trick: define `period_x = 2 * (W - rectW)` and `period_y = 2 * (H - rectH)`; then

```
fold_x = ((x0 + vx * t) - 0) mod period_x   // wrap into [0, period_x)
x_t = (fold_x < (W - rectW)) ? fold_x : period_x - fold_x
```

(and analogously for `y`). This produces the canonical DVD-screensaver triangle wave on each axis without iterative collision detection — entirely closed-form, deterministic, integer-pixel-stable.

Implementation must use integer-pixel positions: `x_t_render = round(x_t)`, `y_t_render = round(y_t)`. Float drift across frames is forbidden (root cause of nondeterministic parity goldens).

The starting velocity is consumer-provided (per `bounceSchema`); typical values per `coinbase-dvd-qr.md` line 36 are 40–60 px/s, which at 30 fps = 1.33–2.0 px/frame. Consumers are encouraged to pass integer velocities for crispest parity; non-integer velocities are accepted (the schema does not enforce integers) and produce sub-pixel float drift that `round()` snaps to integer pixels.

### D-T319-5. Rainbow color cycle — uniform HSL hue rotation

The rainbow color cycle is a **uniform** HSL hue rotation across all dark QR modules. At any given frame, all dark modules share the same hue. Light modules render at `lightModuleColor` (default `#FFFFFF`); they do NOT cycle.

**Math**: hue ∈ [0, 360) is computed as `(frame % cycleFrames) / cycleFrames * 360`. Saturation is fixed at `100 %`; lightness fixed at `50 %`. The resulting `hsl(h, 100%, 50%)` is converted to RGB via the standard HSL → RGB algorithm and applied as the dark-module color for all dark modules in that frame.

Default `cycleFrames` is `ceil(fps * 7)` (7 s — mid-range of the 6–8 s canon per `coinbase-dvd-qr.md` line 26; also chosen because 7 is coprime with most likely commercial-spot durations, avoiding visible loop-points within a 60 s window).

Implementation: use the runtime's `useCurrentFrame()` + `useVideoConfig().fps` (no `Date.now()`, no `Math.random()`). The HSL → RGB conversion is a pure function of `frame`, `cycleFrames` — fully deterministic.

Per-module rendering: iterate the QR matrix once; for each `(row, col)` cell with `qrMatrix[row][col] === '1'`, render an absolutely-positioned `<div>` (or `<rect>` inside a single SVG) with `width = height = moduleSize` (= `rectW / matrixSize`) at offset `(col * moduleSize, row * moduleSize)` within the rectangle, with `background` set to the current rainbow RGB. Light modules either render with `lightModuleColor` OR are skipped (the rectangle's outer `background` is `lightModuleColor`, so light modules need no per-cell rendering — saves DOM nodes).

LOC budget: the per-module rendering loop is the largest sub-component (~80–120 LOC). The HSL → RGB helper is ~20–30 LOC.

### D-T319-6. Animation lexicon — continuous bounce + uniform hue cycle (no phase enum)

Unlike T-317 and T-318 which ship a sealed `phase` enum (`'idle'` / `'pulsing'` / `'pressing'` / `'subscribed'` / `'followed'`), T-319 has **NO phase enum**. The QR rectangle is *always moving* and *always hue-cycling* throughout the clip's duration. There are no "states" — just continuous time-evolved position and color.

This simplifies the schema (no `phase` prop) and the component (no conditional rendering paths driven by phase). The animation is a single deterministic function of `frame`.

Future v2 might introduce a `phase: 'pre-scan' | 'mid-scan' | 'scanned'` enum (analog to T-317's `'subscribed'` post-press state) to render a "scanned" confirmation overlay. v1 ships without it — the QR is *always pre-scan*, perpetually inviting.

### D-T319-7. Theme slots — `background` only

T-319's theme-slot surface is minimal compared to T-317 / T-318. Only the `background` (canvas backdrop) maps to the theme palette. The `lightModuleColor` (QR background inside the rectangle) defaults to white and is NOT theme-bound — the QR-spec canonical contrast pair is dark-on-light, and overriding the light-module color via theme could break scannability. Dark-module color is rainbow-cycled (not theme-bound).

```ts
themeSlots: {
  background: { kind: 'palette', role: 'background' },
}
```

Top-level optional color props with theme fallback: `background?` (canvas backdrop) → `palette/background`. **Default canon**: even when the theme palette resolves to a non-black color, the v1 `'screensaver'` register *defaults to `#000000`* per `coinbase-dvd-qr.md` line 25 — the consumer must explicitly pass `background: '<hex>'` to override. This is "zero-brand canon dominates theme" — analogous to T-317 / T-318's "brand canon dominates theme" posture, but inverted: the *absence* of a brand color (pure black) is the canon.

Implementation: in the component, resolve `background ?? '#000000'` (literal default) BEFORE consulting the theme slot. Document the inversion inline.

`lightModuleColor` is not theme-bound; defaults to `#FFFFFF` literal.

### D-T319-8. No font surface

Unlike T-317 and T-318 which register `fontRequirements`, T-319 has **NO font surface**. The QR matrix is icon-only (no text content); the primitive does not consume any font.

`fontRequirements` is NOT defined on `qrCodeBounceClip` (or is defined as `() => []` if the registration helper requires it).

This is divergent from every other Cluster G primitive (T-317 / T-318 both register fonts). It is consistent with the QR canon: zero text, zero typography.

### D-T319-9. Determinism

Frame-derived only. No `Date.now()`, no `Math.random()`, no `crypto.randomUUID()`, no `setTimeout`, no `setInterval`, no `fetch`. The bounce-position math is closed-form (per D-T319-4); the hue cycle is a pure function of `frame % cycleFrames` (per D-T319-5); the per-module rendering iterates the input matrix in deterministic row-major order.

No SVG instance-IDs needed in v1 (the per-module `<div>` rendering avoids any `<filter id="...">` / `<linearGradient id="...">` / `<clipPath id="...">`). If a future v2 introduces SVG primitives (e.g., for a scanned-overlay glow filter), they MUST be derived from stable inputs (e.g., `qr-code-bounce-overlay-glow`), NOT `crypto.randomUUID()`.

Float drift hazards:

- **Bounce position**: the `mod period` arithmetic involves floats. Apply `Math.round()` on the final rendered position to snap to integer pixels.
- **Hue cycle**: `(frame % cycleFrames) / cycleFrames` is a float in `[0, 1)`. The HSL → RGB conversion produces float RGB components in `[0, 1]` which are then rounded to integers in `[0, 255]` (standard `Math.round(255 * c)`). Do this rounding consistently.
- **Determinism test**: render the same props twice at the same frame; rendered HTML strings byte-identical (catches accidental float drift, `Date.now()`, `Math.random()`, `crypto.randomUUID()`).

### Primitive shape (AC #1–#14)

8. Inside the QR-rectangle wrapper, dark modules (cells where `qrMatrix[row][col] === '1'`) render as absolutely-positioned `<div>` elements at offset `(col * moduleSize, row * moduleSize)` with `width = height = moduleSize` and `background` set to the current rainbow RGB. 9. **Bounce position math** (per D-T319-4): given `bounce.startPosition`, `bounce.startVelocity`, the `frame` from `useCurrentFrame()`, the canvas dimensions, and the rectangle size, the rendered position uses the closed-form fold + mod algorithm. 10. **Reflective rebound** (per D-T319-4): when the cumulative naive position exceeds `[0, W - rectW]` on x or `[0, H - rectH]` on y, the rendered position folds back symmetrically (triangle-wave). 11. **Rainbow hue cycle** (per D-T319-5): at frame `f` with `cycleFrames = ceil(fps * 7) = 210` (at fps 30), the hue is `(f % 210) / 210 * 360`. At `f = 0`, hue = 0 (red).
