## Architectural decisions

This sub-spec is mostly mechanical — the design intent already lives in
the parent T-411 spec and the three implementation sub-specs. The
decisions here scope the docs surface only.

### D-T411d-1 — Single concept SKILL covers the whole shipped surface

The new `skills/stageflip/concepts/tenant-settings/SKILL.md` is the one
canonical place describing the tenant-settings surface end-to-end. It
covers four sections matching the four implementation sub-tasks:
storage, API + CLI, authorization, and permission-shim integration.

Rationale:

- A reader looking up "tenant settings" / "frontier flag" / "interactive
  feature gate" should land on one page that walks the full shape
  without chasing four sibling specs.
- The four shipped implementations expose distinct types but compose
  into a single conceptual surface (default-deny → admin flip → cache
  populate → mount-time gate). One SKILL keeps that flow intact.
- Per CLAUDE.md §5, every concept gets a SKILL.md; tenant-settings is
  one concept across four packages.

The SKILL deliberately does NOT duplicate the design-decision rationale
from the parent T-411 spec (§D-T411-1..§D-T411-9). It links back to
those for the "why"; the SKILL focuses on the "what shipped" so future
implementers can read it without re-deriving the design.

### D-T411d-2 — ADR-005 §D3 update is a single inline link, no design change

Per parent §AC31's explicit hedge: "Spec link only — does NOT require
re-ratification, since D3's design intent is unchanged." The update is a
single inline reference inserted into the existing prose: somewhere in
§D3 we add "Implementation reference: `docs/tasks/T-411.md`" (or
equivalent inline phrasing). No matrix change. No design change. The
ADR's `Status: Accepted` and `Ratified: 2026-04-25` lines stay
unchanged.

The link points to the parent T-411 spec (which itself enumerates the
sub-tasks T-411a..T-411e) rather than to the four sub-task specs
individually — the parent is the single entry point and stays
discoverable as the implementations evolve.

### D-T411d-3 — No `docs/user-manual.md` edit needed

Parent §AC32 says "user-manual lines 196 + 408 still accurate after the
implementation merges." Verifying the manual remains accurate is an
implicit AC, not a required edit. The user-manual references T-411 by
ID; the implementations did not change the user-facing wording. No
manual edit ships in this PR; verification is a reviewer-side check.

### D-T411d-4 — Skills-sync regen runs after the SKILL is written

Per the lessons baked into this session's onboarding (skills-sync drift
is a common one-shot CI failure mode for any new SKILL.md), the
implementer runs `pnpm --filter @stageflip/skills-sync build && pnpm
skills-sync` after writing the SKILL and commits any auto-gen drift in
a separate commit. Generators that may regen because the concept tree
expanded:

- `skills/stageflip/clips/catalog/SKILL.md` (auto-generated catalogue)
- `skills/stageflip/runtimes/SKILL.md` (auto-generated index)
- `skills/stageflip/tools/SKILL.md` (auto-generated index)
- `skills/stageflip/reference/cli/SKILL.md` (auto-generated CLI ref;
  may pick up the new `stageflip tenant set-interactive` command if
  that generator scans the registry)

If none of these drift, the regen is a no-op and no commit ships.

### D-T411d-5 — No code, no package, no fixture changes

The PR is strictly:

- 1 new concept SKILL (~80–150 lines).
- 1 minimal ADR prose tweak (single inline link).
- 1 sub-task spec (this file, ~150–200 lines).
- 1 chore changeset (no version bump).
- 0 or more auto-gen regen commits if `skills-sync` drifts.

Reviewer rejects the PR if any `packages/**`, `apps/**`, `scripts/**`,
or fixture file is touched.
