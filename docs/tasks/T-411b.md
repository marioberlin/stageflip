# T-411b — TenantSettings API + CLI surface

**Second downstream PR of T-411** (parent spec merged in #472, commit
`f25405d8`; storage layer merged in #473, commit `ebffa62f`). Implements
the **API + CLI surface only** per T-411 §D-T411-3 + §D-T411-6: adds
three HTTP procedures on `apps/api` (`tenantSettings.get` /
`setInteractive` / `list`), adds the CLI command
`stageflip tenant set-interactive`, and ships the authorization
predicate `canSetInteractive`.

Strict scope: NO permission-shim wiring (T-411c), NO docs/skill
cross-link (T-411d), NO admin UI (T-411e), NO changes to the storage
adapters (T-411a owns).

## Deviation from parent spec: HTTP routes, not tRPC

Parent T-411 §D-T411-3 specifies "tRPC router". The actual API package
(`@stageflip/app-api`) is built on **Hono** — there is no tRPC root in
the codebase. Per the parent spec's own hedge ("or wherever the existing
tRPC root lives — implementer to confirm"), this PR ships the procedures
as Hono routes following the existing `apps/api/src/routes/mcp-session.ts`
convention. The route URLs map 1:1 onto the procedure names:

- `GET  /v1/tenant-settings/:tenantId`               → `tenantSettings.get`
- `POST /v1/tenant-settings/:tenantId/interactive`   → `tenantSettings.setInteractive`
- `GET  /v1/tenant-settings`                         → `tenantSettings.list`

Procedure semantics, authorization, default-deny posture, and CLI
contract are unchanged from the parent spec. A future tRPC migration is
non-breaking — the route handlers extract their inputs from
`zValidator('json' | 'param')` and would be reusable as procedure
implementations.

## Architectural decisions

All design decisions are inherited from the parent T-411 spec. This
sub-spec restates the API/CLI-relevant ones for inline reviewability and
notes the HTTP-routes deviation above.

### D-T411b-1 — Three procedures, route shape per "Deviation" above

The router exposes three handlers under `/v1/tenant-settings`:

```
GET  /v1/tenant-settings/:tenantId               // get
POST /v1/tenant-settings/:tenantId/interactive   // setInteractive
GET  /v1/tenant-settings                         // list
```

All routes sit behind the existing `authMiddleware` (`/v1/*` is already
the protected-surface convention per `server.ts`).

**`get` semantics (D-T411-5 default-deny materialisation):**

- Read `getTenantSettings(tenantId)` from the injected store.
- If `null`, return a synthesised default-deny payload:
  `{ tenantId, features: { interactive: 'disabled' }, updatedAt: '<now>',
  updatedBy: '<system>' }`. The synthesis happens in the route handler;
  the store stays pure (T-411a D-T411a-7).
- The synthesised default is NOT persisted on read; per parent
  D-T411-5 "lazy creation; reads stay pure".
- Authorization-gated: the actor must be permitted to read this
  tenant — see D-T411b-2.

**`setInteractive` semantics:**

- Validate the body `{ value: 'disabled' | 'preview' | 'ga' }`.
- Run `canSetInteractive(actor, tenantId, currentValue, nextValue)`
  per D-T411b-2; on deny, return 403 with `{ error: 'forbidden',
  reason }`.
- Read the current settings (default-deny synthesis if absent), patch
  `features.interactive` to the requested value, set
  `updatedAt: '<now>'` and `updatedBy: '<actor sub>'`, validate via
  `tenantSettingsSchema.parse()`, then `putTenantSettings(...)`. This
  is the **first write** that materialises the row per D-T411-5.
- Returns the persisted payload.

**`list` semantics:**

- Superadmin-only per parent D-T411-6 — return 403 to non-superadmin.
- Returns `await store.listTenantSettings()`. May be empty.

The "now" clock is injected (`now: () => string`) so tests are
deterministic. The route handler is I/O-bound (HTTP + storage); not
clip code, so the CLAUDE.md §3 determinism rules don't apply, but the
clock injection is good hygiene.

### D-T411b-2 — Authorization predicate `canSetInteractive`

A pure function in `apps/api/src/auth/can-set-interactive.ts`:

```ts
export type InteractiveValue = 'disabled' | 'preview' | 'ga';

export interface AuthorizationActor {
  readonly role: 'viewer' | 'editor' | 'admin' | 'owner' | 'superadmin';
  readonly org: string;
}

export type AuthorizationDecision =
  | { readonly allowed: true }
  | { readonly allowed: false; readonly reason: string };

export function canSetInteractive(
  actor: AuthorizationActor,
  tenantId: string,
  currentValue: InteractiveValue,
  nextValue: InteractiveValue,
): AuthorizationDecision;
```

**Two-role model (parent D-T411-6, mapped onto the existing
`McpSessionRole` namespace):**

| Actor role | Same tenant | Other tenant | Allowed transitions |
|---|---|---|---|
| `superadmin` | yes | yes | any → any (including `'ga'`) |
| `admin` (tenant_admin equivalent) | yes | no | `'disabled' ↔ 'preview'` only; `'ga'` denied |
| `owner` | yes | no | `'disabled' ↔ 'preview'` only; `'ga'` denied |
| `editor` / `viewer` | no | no | always denied |

**Mapping note.** The parent spec's "tenant_admin" role maps onto the
existing `McpSessionRole` namespace `'admin' | 'owner'` — both are
tenant-level admin grants per the existing JWT claim model
(`packages/mcp-server/src/auth/jwt.ts`). `'superadmin'` is a NEW role
value not yet in `McpSessionRole`; for v1 it is recognised by the
authorization predicate via a string-typed `role` field on
`AuthorizationActor`. The predicate accepts any string role; an
unrecognised role returns `{ allowed: false, reason: '...' }`. A future
PR adds `'superadmin'` to `McpSessionRole` proper.

Cross-tenant calls: any non-superadmin actor whose `org !== tenantId` is
denied with a structured `reason: 'cross-tenant'`. (Tenants are
identified by org id in the v1 model — every `org` IS a tenant in the
sense of T-411. Future multi-tenant-per-org carving is out of scope.)

The `currentValue` argument lets the predicate enforce
"same-cell transitions are no-ops" — the route handler may short-circuit
without writing if `currentValue === nextValue` AND the predicate
allows the read (a read-only "would set to same value" call is allowed
for any actor permitted to read). v1 ships the simple form: the
predicate decides; the route always writes if allowed.

### D-T411b-3 — CLI command `stageflip tenant set-interactive`

Registers a new `tenant set-interactive` entry in
`apps/cli/src/registry.ts`. Shape:

```
stageflip tenant set-interactive --tenant <id> --value <disabled|preview|ga> [--dry-run]
```

**Authorization:** the CLI runs under the user's logged-in MCP session
JWT (the existing `createFileTokenStore` / `verifyMcpSessionJwt`
pattern). The CLI does NOT re-implement authorization locally — it
sends a `POST /v1/tenant-settings/<id>/interactive` and reports the
server response. Authorization is enforced server-side. This matches
parent D-T411-3's "service-account credential" intent: in production,
the CLI's session JWT is granted the `superadmin` role for ops use.

**`--dry-run`** prints the would-be call (URL, body) and returns 0
without sending. Useful for break-glass rehearsals.

The HTTP client is injected so tests can stub it (no real network in
unit tests).

### D-T411b-4 — Default-deny materialisation lives in the route handler

Per parent D-T411-5: an absent tenant row maps to
`features.interactive: 'disabled'`. T-411a kept the storage layer pure
(returns `null` for absent rows). This PR materialises the default in
the `get` route handler (synthesises a `{ interactive: 'disabled' }`
payload without persisting). On the **first write** (`setInteractive`),
the row is materialised in the store.

### D-T411b-5 — Subrouter factory pattern; consumers wire the store

The subrouter is a factory:

```ts
export function createTenantSettingsRoute(deps: {
  readonly store: TenantSettingsStore;
  now?: () => string;        // injectable clock (defaults to () => new Date().toISOString())
  systemActor?: string;      // updatedBy value for synthesised default reads (defaults to 'system')
}): Hono<{ Variables: AuthVariables }>;
```

`apps/api/src/server.ts` instantiates the store at boot (in-memory for
tests; production wiring to Postgres / Firebase is a future deployment
task — out of scope here) and mounts the subrouter under
`/v1/tenant-settings`.

This matches the existing `createMcpSessionRoute` pattern.

### D-T411b-6 — Testing posture

- **Unit tests on the predicate** (`can-set-interactive.test.ts`):
  every (actor.role × same-tenant × current → next) cell tested
  explicitly per the matrix in D-T411b-2; cross-tenant denials covered
  for every role.
- **Unit tests on the routes** (`tenant-settings.test.ts`): in-memory
  Hono `app.request(...)` per `mcp-session.test.ts` posture; one
  in-memory store seeded per test; coverage of `get` (absent →
  default-deny synthesised; present → returned), `setInteractive`
  (allowed → 200 + persisted; denied → 403; invalid value → 400; first
  write materialises the row), `list` (superadmin → 200 + array;
  non-superadmin → 403). The route tests bypass `authMiddleware` by
  passing a stub principal directly into the subrouter via Hono's
  `c.set('principal', ...)` shim (matches the existing test pattern).
- **Unit tests on the CLI command** (`tenant.test.ts`): capture-buffer
  `CliEnv` per `render.test.ts` posture; injected HTTP client; coverage
  of missing args, invalid value, `--dry-run`, success, server error
  (403 / 500).

## Acceptance criteria (API + CLI subset of parent T-411 AC list)

### API — routes

1. `apps/api/src/routes/tenant-settings.ts` exists and exports
   `createTenantSettingsRoute(deps): Hono` per D-T411b-5.
2. `GET /v1/tenant-settings/:tenantId` returns the persisted row when
   present.
3. `GET /v1/tenant-settings/:tenantId` returns the synthesised
   default-deny payload (`{ features: { interactive: 'disabled' } }`)
   when the row is absent (D-T411b-4); does NOT persist the default.
4. `POST /v1/tenant-settings/:tenantId/interactive` validates the body
   `{ value: 'disabled' | 'preview' | 'ga' }`; returns 400 on invalid.
5. `POST /v1/tenant-settings/:tenantId/interactive` runs
   `canSetInteractive` and returns 403 with structured
   `{ error: 'forbidden', reason }` on deny.
6. `POST /v1/tenant-settings/:tenantId/interactive` on first allowed
   write materialises the row in the store (D-T411b-4 / parent
   D-T411-5).
7. `POST /v1/tenant-settings/:tenantId/interactive` updates `updatedAt`
   (from the injected `now()`) and `updatedBy` (from the actor's `sub`).
8. `GET /v1/tenant-settings` (list) returns 403 to non-superadmin
   actors.
9. `GET /v1/tenant-settings` returns the list of all stored tenant
   settings to a superadmin actor (may be empty).
10. The subrouter is registered on the root Hono app in
    `apps/api/src/server.ts`, mounted under `/v1/tenant-settings`,
    behind the existing `/v1/*` `authMiddleware`.

### API — authorization predicate

11. `apps/api/src/auth/can-set-interactive.ts` exports
    `canSetInteractive(actor, tenantId, currentValue, nextValue):
    AuthorizationDecision` per D-T411b-2.
12. Predicate covers every (role × same-tenant × current → next) cell
    in the D-T411b-2 matrix and is tested for each.
13. Predicate denies cross-tenant calls (actor.org !== tenantId) for
    all non-superadmin roles.
14. Predicate denies all writes for `viewer` / `editor`.
15. Predicate denies `'ga'` transitions for `admin` / `owner`.
16. Predicate allows `'disabled' ↔ 'preview'` for `admin` / `owner`
    on their own tenant.
17. Predicate allows any value for `superadmin` on any tenant,
    including `'ga'`.
18. Predicate is a pure function (no I/O, deterministic for same
    inputs).

### CLI

19. `apps/cli/src/commands/tenant.ts` exports
    `createTenantCommands(deps?: TenantCommandDeps)` returning
    `{ runSetInteractive }` per D-T411b-3.
20. `apps/cli/src/registry.ts` registers `tenant set-interactive`
    with `--tenant <id>`, `--value <disabled|preview|ga>`, `--dry-run`
    flags.
21. CLI command errors when `--tenant` is missing.
22. CLI command errors when `--value` is missing or invalid (not in
    `{ disabled, preview, ga }`).
23. CLI command with `--dry-run` prints the would-be call and returns
    0 without invoking the HTTP client.
24. CLI command on success prints the server's response payload and
    returns 0.
25. CLI command on a 403 error prints a `forbidden:` line including
    the server-supplied `reason` and returns 1.
26. CLI command on any non-2xx prints a structured error and returns
    a non-zero exit code.
27. CLI command's HTTP client is injectable for tests
    (`TenantCommandDeps.createClient`).
