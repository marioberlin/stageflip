# T-439 — Provenance-aware export: display IAB exporter

**Branch**: `task/T-439-iab-ai-disclosure`

## Goal

The display IAB exporter (`@stageflip/export-html5-zip`, ~Phase 9 era)
auto-marks any document MediaElement whose `provenance.kind` indicates
an AI-generated asset as such per **FTC** (US Federal Trade Commission)
and **EU AI Act** disclosure requirements. Auto-disclosure runs at
export time and produces three observable artifacts:

1. An invisible HTML attribute `data-ai-generated="true"` on the
   element's mount node (when the bundler emits a stable element-id
   selector — see "HTML attribute injection scope" below).
2. A visible "AI" badge (small text or icon in a corner) injected into
   the banner's `<body>`. Configurable per-tenant: text, position
   (`top-right` default), color, opacity.
3. A top-level `aiContent: AiContentDisclosure` field in the orchestrator's
   `BannerExportResult` carrying per-element provenance details
   (provider, modality, cacheKey, prompt) plus a coarse
   `disclosure: { ftc, euAiAct }` compliance summary.

The disclosure is **per-element**, not global — only elements whose
`provenance.kind` is one of the seven generated-asset kinds (`tts`,
`video-gen`, `music-gen`, `sfx`, `three-d`, `image-gen`, plus T-438's
non-terminal `asset-gen-pending`) flag the disclosure path. Elements
whose provenance kind is `imported` OR whose `provenance` is absent
(hand-authored / imported assets) DO NOT trigger disclosure.

## Function

The orchestrator (existing `exportHtml5ZipForSize` /  `exportHtml5Zip`
entry points) walks an opt-in `BannerExportInput.aiElements` list at
export time. For each element where `provenance` is set AND the
`kind` is an AI-generated discriminator:

1. The walker extracts a per-element `AiContentDisclosure` row:
   `{ elementId, provider, modality, cacheKey, prompt? }`. `provider`
   is read from `provenance.provider`; `modality` is read from
   `provenance.kind` (which is, by design, a modality-shaped string).
   `cacheKey` / `prompt` propagate verbatim when set.

2. The walker produces an aggregated disclosure record:
   `{ elements: [...], disclosure: { ftc, euAiAct } }`. The `disclosure`
   sub-record reports either `'compliant'` or
   `'requires-tenant-config'` per-jurisdiction:
   - `ftc`: `'compliant'` when a visible badge is enabled AND at least
     one element has provider info; `'requires-tenant-config'`
     otherwise (e.g. badge disabled by tenant).
   - `euAiAct`: `'compliant'` when a visible badge is enabled AND the
     badge text is non-empty AND at least one element carries
     `provider` + `model`; `'requires-tenant-config'` otherwise.

3. The orchestrator generates a visible badge `<div>` via
   `aiBadgeHtml(config)` and injects it into the banner's `<body>`
   via `injectAiBadge(html, config)`. The injector is idempotent
   (marker-bracketed) and is a no-op when no AI elements are present.

4. The orchestrator populates `BannerExportResult.aiContent` with the
   walker's aggregated disclosure. When no AI elements are present,
   `aiContent` is `undefined` and the badge is NOT injected — every
   existing non-AI export path is byte-identical.

## HTML attribute injection scope

Per-element `data-ai-generated="true"` injection requires the bundler
to emit a stable element-id selector (e.g.
`<div data-element-id="el-123">...</div>`) — which is bundler-specific
and outside the orchestrator's responsibility. T-439 ships a pure
`annotateAiElementsInHtml(html, elementIds)` helper that rewrites
mount nodes carrying the agreed `data-element-id` attribute, AND
makes the helper opt-in (the orchestrator calls it only when at
least one AI element is present AND the bundler-emitted HTML
exposes a matching `data-element-id`). When no matching node is
found, the helper is a no-op (silent — the visible badge + manifest
disclosure still fire).

## Tenant-configurable badge

`AiDisclosureBadgeConfig` shape:

```ts
interface AiDisclosureBadgeConfig {
  /** Badge text. Default: 'AI'. Set to '' to disable visible badge. */
  text: string;
  /** Corner position. Default: 'top-right'. */
  position: 'top-left' | 'top-right' | 'bottom-left' | 'bottom-right';
  /** CSS color. Default: '#fff'. */
  color: string;
  /** CSS background color. Default: 'rgba(0, 0, 0, 0.55)' (semi-transparent). */
  background: string;
  /** Font size in px. Default: 10. */
  fontSize: number;
}
```

Defaults (`DEFAULT_AI_BADGE`): `text='AI'`, `position='top-right'`,
`color='#fff'`, `background='rgba(0, 0, 0, 0.55)'`, `fontSize=10`.

Tenant config flows in through `ExportOrchestratorOptions.aiBadge?:
AiDisclosureBadgeConfig` (full or partial — the orchestrator merges
with `DEFAULT_AI_BADGE`).

## Regulatory references

- **FTC** — "Endorsement Guides" (16 CFR Part 255) require clear and
  conspicuous disclosure of material connections including AI
  generation when an ad implies endorsement. The visible badge plus
  per-element manifest entry satisfy the "clear and conspicuous"
  + record-keeping prongs.
- **EU AI Act** — Article 50(2) requires "AI-generated or
  manipulated" content to be marked in a machine-readable way and
  disclosed to natural persons. The `aiContent` manifest field
  serves the machine-readable prong (downstream platforms can
  surface it); the visible badge serves the human-disclosure
  prong.
- **Other jurisdictions** — China's Generative AI Service Measures
  (effective 2023-08-15) require similar labeling; the per-element
  manifest field is jurisdiction-agnostic and sufficient for
  most emerging requirements.

The `disclosure: { ftc, euAiAct }` summary is a coarse compliance
hint — final compliance is the tenant's responsibility (e.g.
they must enable the badge for FTC-regulated jurisdictions).
