# T-477 — SLA load test

**Branch**: `task/T-477-sla-load-test`

## Goal

Ship a **K6 load-test script** driving 1000 concurrent voters against
the audience-backend per ADR-009 §D4 SLA target. Verifies the v1
1000-voter target is sustainable across a 60-minute keynote profile
with the per-hop latency budget from T-475:

| Hop | p50 | p95 |
|---|---|---|
| End-to-end (voter tap → presenter screen) | < 200 ms | < 500 ms |

T-475 covers in-process latency at 10/50/100 voters via vitest;
T-477 stretches to 1000 voters via real-network K6 against a
deployed audience-backend instance.

Carries three concerns:

1. **`scripts/loadtest/audience-sla.k6.ts`** — K6 script.
   - Scenario: ramp-up to 1000 VUs over 5 min; sustain for 30 min;
     ramp-down over 5 min.
   - Per-VU lifecycle: join session → submit votes at 0.5 Hz (per-voter
     ADR-009 §D3 default rate) → close.
   - Reports p50 / p95 / p99 + error rate.
2. **`scripts/loadtest/audience-sla-README.md`** — operator runbook:
   - How to provision a target backend (Cloud Run staging URL).
   - How to run K6 (`k6 run scripts/loadtest/audience-sla.k6.ts --env BACKEND_URL=...`).
   - How to interpret results (pass criteria + alert thresholds).
   - Pre-flight checklist (rate-limit caps + tenant settings).
3. **CI-trigger documentation**:
   - The load test is **NOT** auto-triggered on every PR (it's
     expensive + requires a deployed target). Document it as a
     pre-release gate run manually by ops or via a separate
     GitHub Actions workflow_dispatch.
   - Add a `.github/workflows/audience-sla-loadtest.yml` workflow
     scaffold (manual trigger only — `on: workflow_dispatch`).

**Strict scope** — K6 script + runbook + workflow scaffold. NO
auto-execution. NO infrastructure provisioning code (the deployed
target is ops-owned). NO Firestore-backed performance optimization
(out of v1 scope for this PR; if T-477 surfaces issues, follow-up
tasks address them).

## Implementation notes

- **K6 script**:
  - Scenario `audience-sla`: `executor: ramping-vus`, stages =
    `[{ duration: '5m', target: 1000 }, { duration: '30m', target: 1000 },
    { duration: '5m', target: 0 }]`.
  - Per-VU iteration:
    1. `POST /v1/audience/sessions/<sessionId>/join` — mint voter token.
    2. WebSocket connect to `/v1/audience/ws/<sessionId>` with the
       token. (K6 supports WS via `k6/ws` module.)
    3. Submit a vote every 2 seconds (0.5 Hz per ADR-009 §D3 default).
    4. After 60s, disconnect.
  - Thresholds: `http_req_duration{name:join}: p(95)<250` + `ws_session_duration: p(95)<500ms` + `vote_ack_latency: p(95)<500ms`.
  - Custom metric `vote_ack_latency` measured via timestamping vote send + ack receipt.
- **Pure helpers** in `scripts/loadtest/audience-sla.ts` (separate from the K6 script for testability):
  - `parseThresholds(spec: string): K6Threshold[]`.
  - `synthesizeBatchSnapshot(voterCount: number): VoterTap[]` — deterministic synthetic vote sequence.
- **Workflow scaffold**:
  - `on: workflow_dispatch:` with `inputs: { backend_url: string, vu_count: number }`.
  - Installs K6 via `grafana/setup-k6-action`.
  - Runs the script + uploads the result JSON as an artifact.
  - DOES NOT block PRs.
- **Determinism**: scripts/ is OUT of CLAUDE.md §3 scope.
- **K6 TS support**: K6 0.50+ supports TS natively via esbuild. The script imports K6's modules (`k6/http`, `k6/ws`, `k6/metrics`) which are type-shimmed via `@types/k6` (add as devDep if not present; verify license MIT).
- **No `console.log`** outside the K6 script (where K6's print is the canonical output).
- **Biome format ONLY touched dirs**.
- **NEVER `git add -A`**.
