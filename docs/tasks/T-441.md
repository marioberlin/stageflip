# T-441 — Provenance-aware export: slide exporter PPTX extension

**Branch**: `task/T-441-pptx-ai-content-ext`

## Goal

The slide exporter (`@stageflip/export-pptx`) is extended with a
**provenance-aware AI-content extension** pipeline that mirrors
T-439 (IAB display disclosure manifest) and T-440 (video sidecar
manifest) for PPTX output. When the exporter sees one or more
MediaElements (`image` / `audio` / `video`) whose `provenance.kind`
indicates AI-generated content, it emits a stageflip-namespaced
`<p:extLst>` extension on `ppt/presentation.xml` carrying the
aggregated AI-content manifest.

This is **always-on** for AI-generated content — there is no opt-in
switch. PPTX consumers (PowerPoint, Keynote, LibreOffice Impress) ignore
unknown extension URIs by spec (ISO/IEC 29500-1 §15.1.1), so the
extension is safe to emit unconditionally. Consumers that DO recognize
the URI can surface the disclosure data in their own AI-content UI.

**No visual badge / watermark**. Unlike T-439's `aiContent` manifest
field (which auto-marks for FTC + EU AI Act ad-tech compliance by
emitting a visible badge inside the rendered creative) and T-440's
opt-in `Made with AI` text overlay, T-441 ships **data only**. The
PPTX consumer is responsible for any user-visible AI disclosure.

## Opt-in posture (vs T-439 / T-440)

| Exporter | Posture | Reason |
|---|---|---|
| T-439 IAB display | auto-mark with visible badge | ad-tech regulatory floor (FTC §5, EU AI Act Art. 50(2)) |
| T-440 video | opt-in watermark + sidecar | broad context (artistic / internal / broadcast); over-disclosure risk |
| **T-441 PPTX** | **always-emit data, no badge** | consumer apps own the AI-disclosure UI; PPTX format already has a standard extension slot for vendor metadata |

The always-emit-data choice is safe because:

1. Unknown `<a:ext uri="...">` entries are explicitly **forward-
   compatible** per the OOXML spec — consumers MUST preserve them
   on round-trip and ignore them on render.
2. The data has no rendering side effect — no pixel changes vs the
   base writer when zero AI-generated elements are present
   (`extLst` is suppressed entirely in that case).
3. Tenants who want AI disclosure to be machine-readable get it
   for free; tenants who don't are not over-disclosed because no
   user-visible UI is emitted.

## Function

The new `provenance-walk.ts` module classifies AI-generated kinds
and extracts per-element disclosure rows; mirrors T-439's pure
`extractAiDisclosures` walk minus the FTC / EU AI Act compliance
fields (irrelevant to a PPTX consumer that owns its own UI).

The new `ai-content-ext.ts` module serializes those rows into the
PPTX `<a:extLst>` extension XML body. The extension is emitted at
**presentation level** (top-level `ppt/presentation.xml`) rather than
per-slide for these reasons:

1. PPTX consumers walk presentation-level extensions on file load;
   per-slide extensions only fire on per-slide render.
2. A single top-level manifest is the simplest contract for
   downstream consumers (compliance scanners, jurisdiction
   routers, audit log writers).
3. Per-slide `<p:sldExtLst>` is reserved for slide-scoped metadata
   that varies by slide (transitions, animation timing); the
   AI-content manifest is deck-scoped audit data.

### Element walker

```ts
interface AiPptxElementInput {
  readonly elementId: string;
  readonly slideId?: string;             // optional — surfaced in the manifest
  readonly provenance?: MediaProvenance;
}

interface AiPptxManifestElement {
  readonly elementId: string;
  readonly provider: string;             // 'unknown' when absent
  readonly modality: MediaProvenanceKind;
  readonly slideId?: string;
  readonly cacheKey?: string;
  readonly prompt?: string;
}

interface AiPptxManifest {
  readonly elements: readonly AiPptxManifestElement[];
}

function extractAiPptxManifest(
  inputs: readonly AiPptxElementInput[],
): AiPptxManifest | undefined;
```

Returns `undefined` when zero AI rows are present so the caller
can suppress the entire `<p:extLst>` block.

### Extension emitter

```ts
function emitAiContentExtension(manifest: AiPptxManifest): string;
```

Returns an XML string of the form:

```xml
<p:extLst>
  <p:ext uri="https://stageflip.dev/extensions/ai-content/v1">
    <sf:aiContent xmlns:sf="https://stageflip.dev/extensions/ai-content/v1">
      <sf:element id="el-1" provider="tts-kokoro" modality="tts" cacheKey="..." prompt="..."/>
      ...
    </sf:aiContent>
  </p:ext>
</p:extLst>
```

The extension URI is the canonical stageflip namespace
`https://stageflip.dev/extensions/ai-content/v1`. Vendor extensions
in PPTX follow the convention of a vendor URL + `/v<n>` for
schema versioning; the `v1` suffix lets us evolve the manifest
shape without breaking older consumers.

### Driver wiring

`exportPptx` accepts an additional optional input:

```ts
interface ExportPptxOptions {
  // ... existing fields ...
  readonly aiElements?: readonly AiPptxElementInput[];
}
```

When `aiElements` is absent / empty, the writer emits the
existing `<p:presentation>` body byte-for-byte (back-compat). When
non-empty AND at least one row classifies as AI, the writer
inserts the `<p:extLst>` element after `<p:notesSz>` (the OOXML
spec requires `<p:extLst>` at the end of `<p:presentation>` body
content).

### AI classification

The walker reuses T-439 / T-440's classification: `kind` is AI
when it matches one of `tts`, `video-gen`, `music-gen`, `sfx`,
`three-d`, `image-gen`, or T-438's non-terminal
`'asset-gen-pending'`. `kind: 'imported'` and absent provenance
filter out.

    discarded, NEVER an error).

## §13 statement

**NOT a structural extension.** T-441 adds:

- A new optional option on `ExportPptxOptions` (back-compat).
- A new pure function module (provenance-walk + extension emit).
- A new XML element in `ppt/presentation.xml` guarded by the
  optional input.

It does NOT add:

- A new `RIRElement` discriminator value.
- A new `ClipKindBinding` field.
- A new top-level prop on a primitive.
- A new compositing / blending / stacking mode.
- A new runtime kind.

Existing PPTX exporter callers see byte-identical behavior. Render
verification N/A — the extension carries data, not pixels;
PowerPoint / Keynote / Impress render the existing PPTX exactly as
before (the `<p:extLst>` is ignored at render time per OOXML
forward-compatibility rules).

## Regulatory references

- ISO/IEC 29500-1 §15.1.1 — OOXML extension list forward compatibility.
- FTC §5 — endorsement / AI-disclosure rules. T-441 surfaces the
  data; the PPTX consumer surfaces the user-visible disclosure.
- EU AI Act Article 50(2) — Transparency obligations. Same
  delegation rationale.

## Shared types between T-439 / T-440 / T-441

All three exporters carry near-identical per-element disclosure
rows. T-441 deliberately duplicates the row type (with a `slideId?`
addition for PPTX context) rather than extracting a shared package
because:

1. Each exporter's surrounding context differs (T-439 ad-tech
   compliance fields, T-440 watermark config, T-441 extension URI).
2. Schema versioning per-exporter is simpler when the surface lives
   alongside the exporter that owns it.
3. A future refactor can extract a shared `@stageflip/provenance-
   manifest` package once the surfaces stabilize (4+ exporters).

The walker entry points are intentionally distinct names
(`extractAiDisclosures` / `extractAiContentManifest` /
`extractAiPptxManifest`) so the call-site reveals which exporter is
being driven.
