# T-370 — Preset: `tiktok-follow-pulse` (followPrompt, Cluster G)

**Branch**: `task/T-370-tiktok-follow-pulse`

## Goal

Promote the existing `tiktok-follow-pulse` preset stub from `status: stub` to `status: substantive` and ship it as the **third Cluster G (CTAs / social) preset to land** AND the **first consumer of the `followPrompt` clipKind** in the parity-CLI resolver AND the **first production consumer of T-318's `'tiktok'` platform branch** in the just-landed `follow-prompt` runtime-clip primitive (main HEAD `25bb0c09`). The preset captures the TikTok native follow-prompt mobile-CTA canon: a 40 × 40 px circular white avatar anchored in the right-thumb zone of a vertical-video frame (mid-axis right side, ~70% down from top), with a 16 × 16 px TikTok-Pink `#FE2C55` "+" badge bottom-right of the avatar, a 30 %-alpha expanding pulse ring drawn behind the avatar in the `'pulsing'` phase (1500 ms scale-1.0 → 1.05 → 1.0 cycle, single bounded repeat). Common uses: creator follow-acquisition prompts on TikTok-anchored vertical posts, mid-feed recommendation overlays, "follow back" CTAs in algorithmic toast bumpers.

T-370 is the **first** preset to bind the `followPrompt` clipKind. The `'followPrompt'` clipKind is in `VALID_CLIP_KINDS` (verified: `scripts/check-preset-integrity.ts` line 75) but has no entry in the parity-CLI resolver as of main `25bb0c09`. T-370 must therefore wire its binding via the **`PRESET_ID_BINDINGS` override map** keyed on `'tiktok-follow-pulse'` — Pattern C from `docs/handover-phase13-cluster-b.md` §"Pattern C", consistent with the entire Cluster B cohort AND the two Cluster G presets already merged (T-369 / T-373). The `DEFAULT_CLIP_KIND_RESOLVER` is **NOT** modified — there is no clipKind-default arm for `'followPrompt'`, and T-370 does NOT introduce one (the override-only pattern matches T-369 / T-373's posture; clipKind-defaults are reserved for the all-presets-of-the-clipKind-share-a-binding case, which does not apply here since later Cluster G presets bind to other primitives — T-372 → `qr-code-bounce`, plus a sibling `instagram-link-sticker` may bind a different primitive).

T-370 is the **first production consumer of T-318's `'tiktok'` platform branch**: T-318 (just merged at `25bb0c09`) shipped the `follow-prompt` primitive with four sealed platform branches (`'tiktok'` / `'instagram'` / `'youtube'` / `'generic'`); T-370 is the first preset to bind the `'tiktok'` discriminant to a parity golden. Sister Cluster G presets bind different primitives (T-372 → `qr-code-bounce` / T-319; an `instagram-link-sticker` v1 if scheduled would consume the `'instagram'` branch of T-318). The Instagram / YouTube / Generic branches of T-318 will get production consumers via separate v2 preset additions (none locked in v1 Cluster G).

T-370 is **M-sized** — same envelope as T-369 (third Cluster G preset of identical shape). ~30–40 LOC binding + snapshot constant + single mid-pulse parity golden + sign-off in-PR. No primitive carve-out; no schema change. Inherits the Cluster G `PRESET_ID_BINDINGS` shape end-to-end from T-369 / T-373.

Cluster G is currently **2/5 signed** as of main `25bb0c09` (T-369 youtube-subscribe-bounce + T-373 social-handle-lower-third). T-370 brings it to **3/5**. The remaining two (T-371 instagram-link-sticker + T-372 coinbase-dvd-qr — verify exact T-numbering against `docs/implementation-plan.md` before pinning) ship in their own preset PRs, each blocked on a distinct primitive (`follow-prompt` T-318 already merged for instagram-link-sticker; `qr-code-bounce` T-319 outstanding for coinbase-dvd-qr).

## Architectural decisions

### D-T370-1. Compass register match — TikTok-Pink "+" badge on white avatar + 30 %-alpha expanding pulse ring + right-thumb-zone anchor

The stub (lines 22–46) defines the canonical TikTok follow-prompt register:

- **Position**: right-thumb zone of vertical-video frame, vertically aligned with native Like / Comment / Share icons (~70 % down from top of frame; stub line 25). The TikTok native frame is 1080 × 1920 portrait, but the **parity-CLI default canvas is 1280 × 720 landscape** (`DEFAULT_COMPOSITION` per parity-CLI generator). T-370 must therefore project the right-thumb-zone anchor onto the 1280 × 720 canvas with a canvas-safe inset, mirroring T-373's posture (`insetLeftPx: 96, insetBottomPx: 96` canvas-safe). T-370 anchors at `position: { x: 1180, y: 504 }` — right edge inset ~100 px (1280 − 100 = 1180), top ~70 % down (720 × 0.70 = 504). This places the 40 px avatar fully inside the canvas with ~80 px clearance to the right edge after avatar-half (20 px) AND ~196 px clearance to the bottom edge. NOTE: the parity render is landscape so the "right-thumb zone" is conceptual — the brand-register identity is **the avatar + badge + pulse ring shape**, not literal mobile thumb-reach geometry. Document this trade-off in the PR body per D-T370-11.
- **Avatar surface**: 40 × 40 px white circle (`avatarColor` defaults to `BRANDED_AVATAR_DEFAULT = '#FFFFFF'` per `renderTiktok` line 431). T-370 inherits the default — does NOT override `avatarColor`. The stub specifies "Circular avatar: 40 × 40 px native" (line 23) — matches the primitive's `DEFAULT_SIZE = 40`.
- **Badge**: TikTok-Pink `#FE2C55` "+" glyph at 16 × 16 px bottom-right of avatar (stub line 24 — "'+' badge in TikTok Pink/Red `#FE2C55`"). The `renderTiktok` hardcodes `badgeColor = TIKTOK_PINK` at line 432; `props.badgeColor` is no-op on `'tiktok'` per D-T318-6 (brand canon dominates theme). T-370 inherits — does NOT override `badgeColor`.
- **Pulse ring**: 30 %-alpha TikTok-Pink ring expanding from `radiusFactor = 1.0` to `1.5` (60 % outward) over a 1500 ms cycle (stub line 34: "scale 1.0 → 1.05 → 1.0, 1500 ms cycle, 30 % opacity ring expanding"). The `computePulseRing` interpolates `[0, cycleFrames] → [1, 1.5]` for radius and `[0, cycleFrames] → [0.3, 0]` for opacity (lines 240–248). T-370 ships `phase: 'pulsing'` to render the ring; `showPulseRing` defaults to `true` so the ring is drawn.
- **Animation**: subtle pulse + expanding ring per stub line 34. T-370's parity golden is rendered at frame 30 in the `'pulsing'` phase (peakFrame = 15 at fps 30; cycleFrames = 45; frame 30 is past peak, mid-decay; phaseFrame = 30, `radiusFactor ≈ 1.33`, `opacity ≈ 0.10`, avatarScale ≈ 1.025). The render captures the brand register at the visually canonical mid-flight point of the pulse.

### D-T370-2. Resolver entry shape — `PRESET_ID_BINDINGS['tiktok-follow-pulse']` (Pattern C); first `followPrompt` consumer; first `follow-prompt` primitive consumer

### D-T370-5. Reference frame for the parity golden — frame 30 (mid-pulse mid-decay)

Stub line 45 lists candidate frames: "Reference frames: 0 (start of pulse), 30 (mid-pulse), 60 (end of pulse), 90 (post-follow checkmark)". v1 does NOT render the `'followed'` post-follow checkmark (D-T370-3) — frame 90 is N/A. Frame 0 is the very-start of the pulse cycle (avatarScale = 1.0; ring radiusFactor = 1.0; ring opacity = 0.30) — useful but the ring is at minimum-radius which understates the brand register. Frame 60 is past the bounded `pulseRepeat = 1` cycle (`totalFrames = ceil(30 * 1.5) * 1 = 45`) — `computeAvatarScale` returns 1.0 (settled), `computePulseRing` returns `null` (cycle over) — equivalent to `'idle'` phase. Useless as a `'pulsing'` register. Frame 30 is **inside** the cycle (< 45) AND past peak (15) — captures avatar mid-decay (~1.025) + visible expanding ring (~1.33 radius, ~0.10 opacity).

**Canonical reference frame: 30**. Mid-pulse mid-decay; the `'tiktok'` branch's `computePulseRing` returns a visible (>0 alpha) ring AND `computeAvatarScale` returns a value > 1.0 (still decaying from peak). This is the visually canonical pulse-register frame. **Note**: T-370 OVERRIDES the cluster-norm `--frame=60` (used by T-369 / T-373 / Cluster B / Cluster A) to `--frame=30` because T-370's brand register is a transient animation phase, not a steady state — frame 60 would render a settled-baseline avatar with no ring (equivalent to `'idle'` phase, which negates the entire `'pulsing'` snapshot rationale). Document this divergence in the PR body per D-T370-11.

The stub-listed candidate frames "0 / 30 / 60 / 90" assume a different cycle math (perhaps fps 60, or a longer pulse cycle); under the T-318 implementation (fps 30, `cycleFrames = 45`, single repeat), only **frame 30** captures the visually canonical mid-pulse state. If the Implementer's render at frame 30 shows the ring + scale shift as too subtle, alternatives are: frame 15 (peak avatar scale 1.05; ring radiusFactor ~1.16, opacity ~0.20) — captures the brand register at peak; frame 22 (mid-cycle compromise).
