# T-361 — Cluster-E composer-tools handler bundle (`cluster-e-compose`)

**Branch**: `task/T-361-cluster-e-compose-tools`

## Goal

Ship the engine handler bundle that wires Cluster E (Data) preset composer tools — `compose_live_data` / `compose_market_ticker` / `compose_election_board` / `compose_big_number` / `compose_stat_callout` — through the tool router. Cluster E is RATIFIED (6/6 ELIGIBLE 2026-05-06) and all 6 preset stubs are substantive. The cluster skill at `skills/stageflip/presets/data/SKILL.md` already pins the 5-tool surface; this task ships the corresponding handler bundle (`cluster-e-compose`), registers it on the canonical bundle catalog + tool-router, regenerates per-bundle tool skills via `pnpm gen:tool-skills`, and lands tests + a changeset.

T-361 is the **fourth of four** cluster-compose tasks. It mirrors the pattern T-340 (Cluster A — branding) / T-368 (Cluster D — entertainment) / T-331 (Cluster B — sports) shape verbatim, with one difference: Cluster E ships **5 composer tools** (the others ship 4). The fifth tool (`compose_stat_callout`) reflects Cluster E's broader sport-stat overlay surface — a stat callout dispatches across cricket / F1 / Olympic / generic-big-number presets within this cluster instead of overloading any single cluster-E tool. The slightly larger handler-bundle (~350–500 LOC vs the other clusters' ~280–400 LOC) is the expected consequence; no architectural divergence.

## Architectural decisions

### D-T361-1. New distinct bundle `cluster-e-compose` (vs extending an existing canonical)

T-361 ships a **new canonical bundle** named `cluster-e-compose` — NOT an extension of `clip-animation`, `semantic-layout`, `data-source-bindings`, or any existing canonical bundle. Rationale:

- **Cluster scope is sealed.** Cluster E owns 6 presets + 5 composer tools per the cluster skill. Bolting cluster-E composers onto `clip-animation` (which is generic per-clip animation tooling) or `data-source-bindings` (which is binding tools, not composing tools) pollutes their scope and breaks their existing skill semantics.
- **Symmetric to sibling clusters.** T-340 / T-368 / T-331 ship `cluster-a-compose` / `cluster-d-compose` / `cluster-b-compose` bundles by the same logic. Each cluster owns one compose bundle. Five clusters in total ship five compose bundles (Clusters A / B / D / E plus a future Cluster C / F / G); T-361 lands the fourth.
- **Per-cluster sealed scope** is the architectural rule per ADR-004 §D5 (the preset system seals cluster ownership at the cluster boundary; composer tools live with the cluster they compose into, not in a generic catch-all bundle).

Reviewer demand for merging into `clip-animation` / `semantic-layout` / `data-source-bindings` → escalate per CLAUDE.md §6.

### D-T361-2. Approach — five read-only composer handlers in one bundle (Approach A)

**Decision**: Approach A — five read-only `ToolHandler<…, …, DocumentContext>` handlers, all in the `cluster-e-compose` bundle, dispatched per-tool via `ToolRouter.register()`. Each handler resolves a preset id from its inputs and returns a routing plan (preset id + dispatched style + opaque pass-through props).

The Orchestrator evaluated three approaches:

- **Approach A (one bundle, five read-only handlers)** — One bundle with 5 sibling handlers. Each handler owns one composer tool and dispatches to one or more cluster-E preset ids based on input fields. ~350–500 LOC bundle. Mirrors the canonical bundle shape (e.g., `element-cm1` 12 handlers, `slide-cm1` 8 handlers).
- **Approach B (one bundle, one mega-handler with discriminated input)** — One handler `compose_data` with discriminated input `kind: 'live-data' | 'market-ticker' | 'election-board' | 'big-number' | 'stat-callout'`. Smaller catalog footprint but breaks the cluster-skill-pinned tool-name convention (the cluster skill already pins 5 distinct tool names — changing them is a cluster-skill rewrite).
- **Approach C (split bundles per tool — five sibling bundles)** — `cluster-e-live-data`, `cluster-e-market-ticker`, etc. Catalog bloats by 4 entries; symmetry with sibling cluster-compose bundles is broken; agent's scope-expansion experience worsens.

**Rationale for A**:

1. **Cluster skill pins 5 distinct tool names.** Approach B would require a cluster-skill rewrite — out of scope and breaks the substantive sign-off.
2. **Symmetric to sibling cluster-compose bundles** (T-340 / T-368 / T-331 ship 4-handler bundles each via Approach A; T-361 ships a 5-handler bundle via the same approach).
3. **One bundle = one cluster** is the architectural rule (D-T361-1).
4. **Read-only handler shape is established.** Read-tier canonical bundles (`read`, `validate`, `fact-check`) all use sibling-handler-per-tool dispatch. T-361 reuses the established shape.

Reviewer demand for Approach B (mega-handler) or Approach C (split) → escalate; the architectural rule is sealed at A.

### D-T361-5. Composer tool input/output schemas (Zod) — per-tool

Each tool's input is a Zod object with the cluster-skill-pinned input shape; each output is a discriminated-union routing plan (`{ ok: true, presetId, dispatchedStyle?, props } | { ok: false, reason, detail? }`).

#### `compose_live_data`

```ts
const composeLiveDataInput = z
  .object({
    domain: z.enum(['politics', 'finance', 'sports', 'olympic']),
    layout: z.enum(['wall', 'big-number']),
    state: z.record(z.unknown()).optional(), // opaque host-supplied state pass-through
    brand: z.string().optional(),
    locale: z.string().optional(),
  })
  .strict();
const composeLiveDataOutput = z.discriminatedUnion('ok', [
  z
    .object({
      ok: z.literal(true),
      presetId: z.enum(['magic-wall-drilldown', 'big-number-stat-impact']),
      dispatchedLayout: z.enum(['wall', 'big-number']),
      props: z.record(z.unknown()),
    })
    .strict(),
  z
    .object({
      ok: z.literal(false),
      reason: z.enum(['unsupported_domain', 'unsupported_layout', 'invalid_state']),
      detail: z.string().optional(),
    })
    .strict(),
]);
```

Dispatch rule: `layout: 'wall'` → `magic-wall-drilldown`; `layout: 'big-number'` → `big-number-stat-impact`. `domain: 'olympic' + layout: 'wall'` is rejected with `unsupported_domain` (the Magic Wall is electoral; Olympic data uses `olympic-medal-tracker`, which is reached via `compose_stat_callout` instead per D-T361-5e).

### D-T361-7. Read-only handlers — no patch sink

Cluster-E composers do **NOT** mutate the document. They are read-only routing helpers — they return `{ ok: true, presetId, props }` without touching `ctx.patchSink`. They declare `DocumentContext` (NOT `MutationContext`). Mirrors the read-tier canonical bundles (`read`, `validate`, `fact-check`).

The runtime — once it receives the routing plan — chooses how to materialize the preset (via `clip-animation` tools or via the parity-cli resolver). The composer tool's job is **routing only**.

This posture matches the cluster skill SKILL.md §"Semantic tools" pinning: each composer is described as routing to a preset id + brand pass-through, NOT as a mutation. Mirrors the sibling cluster-compose bundles (T-340 / T-368 / T-331).

### D-T361-8. Test strategy

- **Schema-only tests** (per tool): `inputSchema.parse(…)` accepts the minimal valid input + rejects each required-field absence + rejects each enum violation + rejects extra unknown fields (strict mode).
- **Dispatch tests** (per `(tool, input gate)` pair from D-T361-6): each handler invocation with a representative input returns the expected preset id.
- **Edge case tests**: `compose_market_ticker` with mismatched `symbols.length` and `deltas.length` returns the schema-rejection error; `compose_live_data` with `domain: 'olympic'` + `layout: 'wall'` returns `unsupported_domain`; `compose_big_number` with `figure: ''` rejected at schema parse (min(1)).

- **gen:tool-skills regen sanity test**: not a vitest case (lives in CI as `pnpm gen:tool-skills:check`); see AC #29.

`handlers.test.ts` ships ~12–14 cases; `register.test.ts` ships ~3–4 cases. Total ~15–18 vitest cases (per Test plan).

### D-T361-9. `compose_live_data` returns a routing plan only — no live-data fetch

Per the cluster skill SKILL.md line 41: `compose_live_data(endpoint, schema, brand)` "routes to `LiveDataClip` if the tenant has enabled the frontier; falls back to a static snapshot preset otherwise". T-361's handler does **NOT** evaluate `tenant.frontierEnabled` and does **NOT** initiate any fetch. The handler returns the routing plan: `{ ok: true, presetId: 'magic-wall-drilldown' | 'big-number-stat-impact', props: {…opaque host-supplied state…} }`. The runtime evaluates frontier capability at compose time and uses the live or snapshot path.

Rationale:

- **Determinism**: the engine's tool router invokes handlers in the executor loop; introducing a `fetch()` would violate the determinism gate (per CLAUDE.md §3 — handlers in `packages/engine/src/handlers/**` are NOT in the determinism deny-list, but they are in the executor loop where deterministic tool replay matters).
- **Separation of concerns**: composing a preset is a planning step; rendering a `LiveDataClip` is a runtime step. The composer should not pre-materialize live data.
- **Schema simplicity**: the input does not need an `endpoint` URL (the runtime owns endpoint resolution); the input only needs the host's choice of layout + state shape.

The cluster skill's `endpoint, schema, brand` signature simplifies in practice to `domain, layout, state, brand, locale` per D-T361-5; the cluster owner supplies `endpoint` + `schema` at runtime out-of-band. T-361's handler signature is the agent-facing slice.
