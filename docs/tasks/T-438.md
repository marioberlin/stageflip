# T-438 — Optimistic placeholder UX for async asset generation

**Branch**: `task/T-438-optimistic-placeholders`

## Goal

Async asset generation (T-423 `generate_asset` tool wrapping the Phase 14
α Provider Seam) must NOT block the editor UI. Today the tool awaits
`FallbackChainExecutor.execute(...)` which awaits the host's
`executeAdapterCall` seam, which in turn awaits the vendor HTTP call.
Adapters resolve anywhere from 1 second (TTS / Kokoro) to 5 minutes
(slide-deck-gen / report-gen). During the wait the LLM tool-call loop is
blocked and the editor sees nothing.

T-438 introduces an **optimistic placeholder** path: when the caller
sets `optimistic: true` on `generate_asset`, the tool returns
immediately with `{ ok: true, kind: 'placeholder', placeholderId,
modality, estimatedCompletionAt }` and emits a JSON-Patch op that
mounts an opaque placeholder `MediaElement` carrying
`provenance.kind: 'asset-gen-pending'`. The real adapter dispatch
runs in the background via an opt-in `placeholderResolver` seam.
The editor shell renders the placeholder visually (greyed-out box +
spinner + adapter name + estimated time) until a downstream patch
swaps it for the resolved MediaElement.

## Function

1. `generate_asset` gains an optional input field `optimistic?: boolean`
   (default `false` — back-compatible; existing callers see no change).
2. When `optimistic: true`:
   - The handler derives the same `cacheKey` it would derive in the
     synchronous path (so the eventual swap matches).
   - The handler synthesizes a `placeholderId` and an
     `estimatedCompletionAt` ISO-8601 string (computed from the
     adapter's optional `latencyHintMs` capability metadata; falls
     back to a per-modality default).
   - The handler builds a placeholder `MediaElement` with
     `provenance.kind: 'asset-gen-pending'`, `provenance.placeholderId`,
     `provenance.cacheKey`, and `provenance.estimatedCompletionAt` set.
   - The handler emits a JSON-Patch `add` op against the target slide.
   - The handler kicks off the adapter dispatch via the host-supplied
     optional `placeholderResolver` seam in a `Promise.then(...)`
     background continuation. The handler does NOT await the
     continuation; it returns the placeholder result immediately.
   - The handler returns `{ ok: true, kind: 'placeholder',
     placeholderId, modality, estimatedCompletionAt, cacheKey }`.
3. When `optimistic` is absent or `false`, the handler behaves
   identically to T-423 (synchronous; returns `{ ok: true, ... }` with
   the resolved provenance — no `kind` field).
4. The editor shell observes the placeholder element via the existing
   `documentAtom` + `elementByIdAtom` selectors. A new
   `AssetGenPlaceholder` component renders any element whose
   `provenance.kind === 'asset-gen-pending'` as a greyed-out box with
   a spinner, the adapter modality, and a "ready in ~Ns" countdown
   derived from `estimatedCompletionAt`. A new
   `useAssetGenPlaceholders()` hook selects all currently-pending
   elements across the document so the editor can show a count badge
   or a per-modality progress indicator.
5. The swap from placeholder → real asset is delivered by the
   `placeholderResolver` seam at the host's discretion (next-cycle
   tool call, SSE event, polling). T-438 does NOT prescribe the
   transport — it ships the placeholder mount + the seam contract.
   T-442 (streaming events / cancellation surface) owns the transport
   plumbing.

## Schema audit

`packages/schema/src/elements/media-provenance.ts` (T-421) currently
defines `MEDIA_PROVENANCE_KINDS` as a tuple of 7 terminal generation
kinds:

```
['tts', 'video-gen', 'music-gen', 'sfx', 'three-d', 'image-gen', 'imported']
```

There is **no pending-state variant**. The provenance shape was
intentionally shaped for terminal-state assets — ADR-008 §D2 declares
provenance as a record of HOW an asset was produced. A pending element
has no producer yet.

T-438 EXTENDS the discriminator with one new variant:

```
'asset-gen-pending'
```

And EXTENDS the `mediaProvenanceSchema` with two new optional fields,
both meaningful only when `kind === 'asset-gen-pending'` (but tolerated
on other variants per Zod's strict-but-additive permissiveness on
optional fields):

- `placeholderId?: string` — opaque correlation id linking placeholder
  emission to the eventual swap patch. Generated by `generate_asset`.
- `estimatedCompletionAt?: string` — ISO-8601 datetime, an upper-bound
  hint the UI uses for the countdown / spinner. Optional even on
  pending elements; the editor falls back to an indefinite spinner
  when absent.

The new variant carries the same optional `provider` / `model` /
`prompt` / `cacheKey` / `seed` / `voiceProvider` / `voiceId` /
`researchSessionId` fields as the terminal variants — these describe
the WORK IN FLIGHT and let the placeholder display useful labels
("Generating with kokoro-82m...") before the swap.

**Discriminator-tuple length sentinel**: existing test
`elements.test.ts:275` asserts `MEDIA_PROVENANCE_KINDS.toHaveLength(7)`.
T-438 updates this to 8 (matching pattern from T-305 bump of
`ELEMENT_TYPES` from 12 → 13).

## §13 statement — STRUCTURAL EXTENSION (option 3 deferral)

**YES** — extending `MediaProvenance.kind` with `'asset-gen-pending'`
and adding `placeholderId` + `estimatedCompletionAt` fields adds a NEW
degree of freedom to the document model (a pending element type
recognized by the schema).

Per CLAUDE.md §13 acceptable-evidence option 3: **pixel-level
verification is DEFERRED**. Justification:

- The new provenance shape is **metadata only**. It does not introduce
  a new RIR element type, a new clip kind, a new runtime, a new
  compositing mode, or any rendering pipeline change.
- The VISUAL surface for a pending element is the new
  `<AssetGenPlaceholder>` component in editor-shell. This PR's
  editor-shell tests assert the component renders for elements
  whose `provenance.kind === 'asset-gen-pending'`, that it renders
  nothing for terminal-state provenance, and that the countdown +
  spinner React appropriately to props.
- Pixel-level parity-fixture verification is N/A — the placeholder
  visual is functional UI (greyed-out box + spinner) not artistic
  content. No parity fixture asserts on placeholder pixels.
- Renderer parity goldens (parity-cli / renderer-cdp) consume
  TERMINAL-STATE assets; a pending element is never serialized
  into a render. The placeholder kind exists strictly in the
  authoring document and is filtered out at export time (the
  renderer pipeline rejects unknown provenance kinds and the
  pending kind is treated as a transient editor-state artifact
  per ADR-008 §D2 follow-up).
- Future deeper visual verification can land as a downstream Track A
  consumer task if the placeholder UI becomes more elaborate (e.g.
  per-modality preview thumbnails, vendor logos). The opaque-box
  visual shipped here is intentionally minimal.

The downstream consumer for pixel verification is **either**
T-442 (streaming events) when it lands a real-render integration
test that drives the placeholder → swap cycle through a fake
adapter and asserts on the editor-shell visual output, **or** a
dedicated Track A T-44x task if the placeholder UI grows beyond
the functional-minimum shipped here.

## Architectural seals

- **Back-compat**: every existing `generate_asset` caller that omits
  `optimistic` (or passes `false`) sees byte-identical behavior.
  Existing tests pass without modification.
- **Optional seam**: `placeholderResolver` on
  `AssetGenerationContext` is optional. Hosts that don't wire it
  cannot use `optimistic: true` — the handler returns
  `{ ok: false, reason: 'asset_generation_unavailable',
  detail: 'optimistic mode requires placeholderResolver seam' }`.
- **No background-promise leak**: the handler stores the
  background continuation under
  `placeholderResolver.dispatch(...)`. The seam owns the eventual
  swap; the handler discards the continuation reference after
  returning.
- **Determinism preservation**: the placeholder path lives outside
  `packages/frame-runtime/**` / `packages/runtimes/**/src/clips/**`
  / `packages/renderer-core/src/clips/**`. No determinism rule
  applies. (The placeholder `placeholderId` is generated via
  `crypto.randomUUID()` per Web Crypto API which is available in
  both Node ≥18 and browser editor contexts.)
- **Schema-strict roundtrip**: the extended schema still
  `.strict()`s — unknown fields fail parse. `placeholderId` +
  `estimatedCompletionAt` are first-class slot additions.
- **MediaElement parses without provenance**: the `provenance?`
  slot remains optional on every audio / image / video element;
  hand-authored / imported elements continue to omit it.
- **No new runtime dep edges**: editor-shell already depends on
  `@stageflip/schema`. The asset-gen-placeholder component
  imports `MediaProvenance` from there. No new package adds.

## Async dispatch pattern picked

**Immediate-return-then-background-promise**: the handler returns the
placeholder result synchronously (Promise resolved with the placeholder
shape), and kicks off the real adapter via
`placeholderResolver.dispatch(...).catch(...)` in a fire-and-forget
continuation. The handler does NOT thread the continuation back into
its return value or wait for it.

This is the pragmatic posture given the streaming-event infrastructure
landing in T-442 (downstream). Hosts that have a streaming-event
channel wire the swap into `placeholderResolver.dispatch` and emit a
follow-up tool-result on completion. Hosts without streaming events
treat the placeholder as a terminal authoring state and resolve it on
the next agent run (the placeholder element is visible in the document;
the next planner cycle sees it and may emit a fresh tool call to
finalize). The handler is agnostic to the transport.

Alternative considered: extending `ExecutorEvent` with a new
`asset-gen-completed` event. Rejected for T-438 scope — that's the
T-442 swap mechanism. T-438 ships the placeholder mount + the seam
only.
