## CRITICAL: Multi-clip composition gap (D-T348-1)

**The architectural concern that drives the L-size envelope.** As of `main` HEAD `233cbf19`, the parity-CLI resolver `ClipKindBinding` interface (`packages/parity-cli/src/generate-fixture.ts:66`) maps **one preset → one runtime clip + one props payload**:

```typescript
export interface ClipKindBinding {
  readonly runtimeId: string;        // e.g. 'frame-runtime'
  readonly clipName: string;          // e.g. 'titleSequence' (single clip)
  buildProps(variant: string | undefined): Record<string, unknown>;
}
```

Every existing preset in `PRESET_ID_BINDINGS` (24 entries: A/B/E/F/G clusters + T-350 `titleSequence` clipKind-default) binds a single primitive — the resolver returns one binding, `buildPresetDocument` constructs a `RIRDocument` with **one** `clip` element (`packages/parity-cli/src/generate-fixture.ts:2602` — `elements: [{ id: elementId, type: 'clip', ... }]`). Every Cluster A lower-third, every Cluster B scoreBug, every Cluster G CTA: one clip per preset.

**T-348 needs five clips composed**: titleSequence (typography base) + grain (overlay) + light-leak (overlay) + particles (overlay) + photographic-overlay (top tonal pass). The current resolver shape cannot express this; before T-348 can ship a parity golden, the resolver must be extended.

**Decision (D-T348-1)**: Extend `ClipKindBinding` to support an optional **secondary-overlays array** (`overlays?: ReadonlyArray<{ runtimeId: string; clipName: string; buildProps: (...) => Record<string, unknown> }>`). The Implementer:

1. Adds the `overlays` field as **optional** (NOT required) on `ClipKindBinding`. Every existing 24 bindings work unchanged (no `overlays` → degenerate single-clip path).
2. Extends `buildPresetDocument` to emit one `RIRDocument.elements` entry per overlay in declaration order, each with the same `transform` (full-canvas) and `timing` (full-duration) as the parent, AND a strictly increasing `zIndex` (parent at `zIndex: 0`; overlays at `zIndex: 1, 2, 3, ...`).
3. The resolver's `buildProps` for the parent (`titleSequence`) returns the parent props; each overlay's `buildProps` returns its own primitive's props.
4. A new test covers the multi-clip rendering path; existing 24 single-clip presets remain green.

This is the smallest viable extension — it preserves backward-compat for every signed preset, requires no new resolver type at the public boundary (existing callers ignore `overlays`), and lets T-348 declare `[grain, lightLeak, particles, photographicOverlay]` in declaration order = z-order.

**Alternative considered: "compose" wrapper kind.** Reject — would require a new clipKind enum value, a new primitive at the runtime boundary, AND would lose declarative clarity. The overlay-array extension is strictly smaller.

**Alternative considered: render multi-clip via a new "compose" primitive at the runtime layer.** Reject — moves composition into the determinism-critical clip layer; an overlay-stack is a parity-CLI concern (it's about how the renderer mounts clips, not about how clips render themselves). Keep the runtime clean.

**Out of scope for T-348**: complex z-stacking with per-overlay `transform` / `timing` (full-canvas + full-duration is sufficient for atmospheric overlays); blend modes per overlay (the primitives bake their own blend modes — `light-leak` already uses `mixBlendMode: 'screen'`; `photographic-overlay` uses SVG filters); per-overlay variant axes (the parent's variant is the only one consumed in v1).

If a Reviewer demands a different composition model (e.g., a wrapper clipKind / RIR `Group` element / nested compositions) → escalate per CLAUDE.md §6; the overlay-array model is the smallest viable extension that preserves all 24 existing bindings AND lets T-348 ship without a primitive-side carve-out.

## Architectural decisions

### D-T348-1. Multi-clip composition gap — extend `ClipKindBinding` with optional `overlays?` array

**The structural concern.** As of `main` HEAD `233cbf19`, `ClipKindBinding` (`packages/parity-cli/src/generate-fixture.ts:66–77`) maps one preset → one runtime clip + one props payload. Every existing preset (24 in `PRESET_ID_BINDINGS` + 10 clipKind-default arms) is single-clip. T-348 needs five clips composed.

**Resolution**. Extend `ClipKindBinding` with an optional `overlays?` array:

```typescript
export interface ClipKindBinding {
  readonly runtimeId: string;
  readonly clipName: string;
  buildProps(variant: string | undefined): Record<string, unknown>;
  /**
   * Optional secondary atmospheric overlays composed above the parent
   * clip in declaration order = z-order. Each overlay renders at full-
   * canvas extent + full duration; the parent clip is at zIndex 0,
   * overlays at zIndex 1, 2, 3, ... in array order. Single-clip
   * presets omit; existing 24 bindings remain unchanged.
   */
  readonly overlays?: ReadonlyArray<{
    readonly runtimeId: string;
    readonly clipName: string;
    buildProps(variant: string | undefined): Record<string, unknown>;
  }>;
}
```

`buildPresetDocument` (line 2585+) is extended: when the resolved binding carries `overlays`, the function emits ONE `RIRDocument.elements` entry per overlay (parent first at `zIndex: 0`; overlays at `zIndex: 1, 2, 3, ...` in declaration order), each with the SAME `transform` (full-canvas `{ x: 0, y: 0, width, height, rotation: 0, opacity: 1 }`) and `timing` (`{ startFrame: 0, endFrame: durationInFrames, durationFrames: durationInFrames }`) as the parent. Each overlay's `params` is its `buildProps(variant)` output.

**Backward compat**: every existing 24 + 10 = 34 binding sites work unchanged (no `overlays` field → degenerate single-clip path; the existing test suite continues to pass).

**For T-348**: the `strangerThingsBenguiatBinding` declares parent `clipName: 'titleSequence'` PLUS overlays `[grainOverlay, lightLeakOverlay, particlesOverlay, photographicOverlayOverlay]` in declaration order = z-order (D-T348-2).

**Rejected alternatives**:
- New "compose" wrapper clipKind requiring a fresh `clipKind` enum value + a new primitive at the runtime layer; would push composition into the determinism-critical clip layer (out-of-scope). Smallest delta principle: the overlay-array fits on the existing resolver shape.
- Per-overlay `transform` / `timing` overrides — atmospheric overlays are full-canvas + full-duration by design (grain coats every pixel; light-leaks span the canvas; dust particles drift across the frame; photographic overlay is a tonal pass over the entire canvas). Per-overlay tuning is not needed in v1.
- Blend modes per overlay — primitives bake their own blend modes (`light-leak` uses `mixBlendMode: 'screen'`; `photographic-overlay` uses SVG filter primitives; `particles` and `grain` rely on alpha-compositing into the canvas stack). The overlay path does NOT add blend-mode declarations.

### D-T348-2. Composition order (z-stack) — titleSequence (base) → grain → light-leak → particles → photographic-overlay (top)

The five clips compose at full canvas in this strict declaration order = z-order:

```
zIndex 0 — titleSequence ('letterform-assemble' style) — typography base
zIndex 1 — grain — film-grain noise overlay (alpha-blended over typography)
zIndex 2 — light-leak — warm-orange radial-blob leaks (mix-blend: screen)
zIndex 3 — particles ('snow' style) — atmospheric dust drift
zIndex 4 — photographic-overlay ('fade' mode @ 0.4 intensity) — top tonal pass
```

**Rationale**:
1. **Typography first** — letterforms must be visible through every overlay; placing them at the bottom of the stack lets grain / light-leaks / dust / fade cast their effects ON the type rather than under it. This matches the compass canon (stub line 22–28: "Letters in extreme close-up — typeface fills the screen" — the type IS the canvas).
2. **Grain second** — grain coats every pixel of the canvas equally (it's the noise field, not a localized effect). Placing it directly above the typography lets grain texture the letterforms, the background, and (with subtle alpha bleed) the underlying composition. Grain at intensity 0.15 is non-destructive; it does not obscure type.
3. **Light-leak third** — leaks are localized warm-orange highlights that "screen" onto the underlying composition. The `light-leak` primitive uses `mixBlendMode: 'screen'` (line 73), which means it lifts the highlights without darkening shadows; placing it above grain lets the leak's screen-blend interact with both type and grain.
4. **Particles fourth** — dust drifts above leaks (visual canon: dust is in the air, not in the camera's optical path; it occludes the leak when in front of it). Snow particles are fine, low-count, and additively-rendered — they do not obscure the underlying frame.
5. **Photographic-overlay fifth (top)** — final tonal pass; SVG filter primitives are pure pixel-level transforms over the underlying composite. Placing it at the top guarantees the fade tonal cast applies to the FULL composite (type + grain + leaks + particles), producing a uniform 80s analog warmth across all four underlying layers.

The overlay-array's declaration order in `strangerThingsBenguiatBinding.overlays = [grainOverlay, lightLeakOverlay, particlesOverlay, photographicOverlayOverlay]` directly encodes this z-stack.

### D-T348-10. F-4 generator flags — `--psnr=36 --ssim=0.92 --mark-signed --fps=24 --frame=480` (lowered per stub line 49)

5. **Stub-pre-declared thresholds**: stub line 49 explicitly sets these thresholds.
