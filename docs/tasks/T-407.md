# T-407 — `arrange_reveal` semantic tool

**Branch**: `task/T-407-arrange-reveal`

## Goal

Ship a new write-tier tool, `arrange_reveal`, as the **5th tool inside the existing
`semantic-layout` handler bundle** (alongside `apply_title_body_layout`,
`apply_two_column_layout`, `apply_kpi_strip_layout`, `apply_centered_hero_layout`).

The tool takes a slide id plus an ordered list of caller-supplied element ids and
applies a **staggered reveal animation sequence**: each element gets a freshly
appended `Animation` whose `timing` is an `absolute` primitive with a computed
`startFrame` (per stagger offset) and a sensible `durationFrames`, and whose
`animation` is a `fade` (or other configurable enter kind) that the renderer
plays once on mount. Mirrors the four sibling tools' shape verbatim: `MutationContext`,
`.strict()` Zod input, `z.discriminatedUnion('ok', ...)` output, JSON-Patch
ops emitted via `ctx.patchSink.push`.

This is **NOT a new bundle** and **NOT a structural extension** (per `CLAUDE.md`
§13). The bundle name stays `'semantic-layout'`; the bundle count on the
canonical registry stays at 24; no orchestrator wiring change; no
`createCanonicalRegistry` count bump; no `gen-tool-skills.ts`
`OWNER_TASK_MAP` entry (it is keyed by bundle, not by tool, and the
`semantic-layout` entry already exists from T-168). The only generator-side
effect is the auto-regenerated `skills/stageflip/tools/semantic-layout/SKILL.md`
gaining a fifth `### \`arrange_reveal\`` section + bumping the invariant
"Tool count 4" → "Tool count 5".

## Architectural decisions

### D-T407-1. Tool is the 5th member of the existing `semantic-layout` bundle

**Decision**: `arrange_reveal` is registered with `bundle: 'semantic-layout'`,
appended to `SEMANTIC_LAYOUT_HANDLERS` and `SEMANTIC_LAYOUT_TOOL_DEFINITIONS`
in `packages/engine/src/handlers/semantic-layout/handlers.ts`. No new bundle;
no new directory; no orchestrator wiring change; no `CANONICAL_BUNDLES` edit;
no `createCanonicalRegistry` count bump (stays at 24). The bundle's `tools`
array goes from length 4 → 5. The I-9 cap (≤30) is unaffected.

Reviewer demand for a separate `reveal-animations` bundle → escalate; the
"semantic layout" framing of the existing bundle (transforms +
animation-arrangements that arise from semantic intent — title-over-body,
KPI strip, staggered reveal) is the architectural seal.

### D-T407-2. `MutationContext`, NOT `ToolContext`

**Decision**: `arrange_reveal` writes JSON-Patch ops via `ctx.patchSink.push`
to append animations to each element's `animations: []` array. Therefore
`TContext = MutationContext`, mirroring the four sibling tools verbatim.

This matches `clip-animation`'s `add_animation` tool, which uses the same
patch shape: `{ op: 'add', path: '/content/slides/<i>/elements/<j>/animations/-', value: <animation> }`.

### D-T407-3. Frame-native input (no ms)

**Decision**: Input fields are frame-native (`staggerFrames`,
`initialDelayFrames`, `enterDurationFrames`). Rationale:

1. The schema's timing primitives (`timing.ts`) are frame-native at every
   level: `startFrame`, `durationFrames`, `offsetFrames`, etc. There is no
   ms surface anywhere on the canonical schema.
2. There is no `fps` on the slide content type — fps is per-clip
   (`blender-clip.ts`) or per-video-mode (`content/video.ts`). A tool that
   accepts ms would need to invent a default fps assumption and bake it in.
3. Caller-side conversion is trivial (`Math.round(ms * fps / 1000)`).
4. Determinism: pure function of input, no implicit fps.

Reviewer demand for ms-based input → escalate; the frame-native posture is
the architectural seal across the canonical schema.

### D-T407-4. Caller passes explicit element ids in reveal order

**Decision**: Input shape is `revealOrder: z.array(z.string().min(1)).min(1).max(20)`
— an ordered list of element ids. The 0th id reveals first, the 1st reveals
second, etc. No "role" discriminator (`headline` / `body` / `media`) is
hardcoded; the caller decides which element plays which slot.

Rationale:

1. Mirrors the 4 sibling tools (`titleElementId` / `bodyElementId` /
   `leftElementIds` / `rightElementIds` / `elementId` / `elementIds` —
   all caller-supplied ids).
2. The `elementBaseSchema` does NOT carry a `role` field. Inferring "this
   is the headline" from element type is brittle and out of envelope.
3. The composer-tier (cluster-compose tools) maps semantic intent →
   element ids upstream; this leaf-tier tool takes the ids and arranges
   them.
4. Max 20 caps the reveal sequence at a sensible bound (real slides rarely
   have more than ~10 enter-animatable elements; 20 is a generous cap).

The tool's name (`arrange_reveal`) and its description still mention the
"headline → body → media" intent — that's the **canonical use case**, not
a hardcoded role enum. Caller maps semantic roles → element ids; the tool
applies the staggered timing.

### D-T407-5. Input schema (full)

```ts
const arrangeRevealInput = z
  .object({
    slideId: z.string().min(1),
    revealOrder: z.array(z.string().min(1)).min(1).max(20),
    initialDelayFrames: z.number().int().nonnegative().max(600).optional(),
    staggerFrames: z.number().int().nonnegative().max(600).optional(),
    enterDurationFrames: z.number().int().positive().max(600).optional(),
    enterAnimationKind: z.enum(['fade', 'slide-up', 'slide-down', 'slide-left', 'slide-right', 'scale']).optional(),
    enterEasing: z.enum(['linear', 'ease', 'ease-in', 'ease-out', 'ease-in-out']).optional(),
    autoplay: z.boolean().optional(),
  })
  .strict();
```

Defaults applied inside `handle()`:

- `initialDelayFrames`: `0`
- `staggerFrames`: `9` (≈300 ms at 30fps — the canonical "snappy stagger" feel)
- `enterDurationFrames`: `14` (≈450 ms at 30fps)
- `enterAnimationKind`: `'fade'`
- `enterEasing`: `'ease-out'`
- `autoplay`: `true`

Caps (`max(600)`) are guard-rails — at 30fps that is 20s, more than long
enough for any reasonable enter animation. Inputs beyond 600 are
caller-error-or-confusion, not legitimate stagger.

The `enterAnimationKind` enum maps each value to a `kind: 'fade'` or
`kind: 'slide'` (with `direction`) or `kind: 'scale'` arm of the canonical
`animationKindSchema`. Mapping is documented in D-T407-7.

### D-T407-6. Output schema (full)

```ts
const arrangeRevealOutput = z.discriminatedUnion('ok', [
  z
    .object({
      ok: z.literal(true),
      slideId: z.string(),
      applied: z.array(
        z
          .object({
            elementId: z.string(),
            animationId: z.string(),
            startFrame: z.number().int().nonnegative(),
            durationFrames: z.number().int().positive(),
          })
          .strict(),
      ),
    })
    .strict(),
  z
    .object({
      ok: z.literal(false),
      reason: z.enum(['wrong_mode', 'slide_not_found', 'element_not_found', 'duplicate_element_id']),
      detail: z.string().optional(),
    })
    .strict(),
]);
```

`applied` carries the per-element computed timing so the caller can
introspect what was emitted (animation id chosen, startFrame computed,
duration applied). Useful for the agent's audit trail and for downstream
tools that want to anchor follow-up animations to the reveal sequence.

`duplicate_element_id` fires if the caller passes the same id twice in
`revealOrder` — an obvious-but-easy mistake; rejecting up front is more
helpful than silently animating the element twice.

### D-T407-7. Animation-kind mapping

```ts
function buildAnimationKind(kind: EnterAnimationKind): AnimationKind {
  switch (kind) {
    case 'fade':
      return { kind: 'fade', from: 0, to: 1, easing: 'ease-out' };
    case 'slide-up':
      return { kind: 'slide', direction: 'up', distance: 100, easing: 'ease-out' };
    case 'slide-down':
      return { kind: 'slide', direction: 'down', distance: 100, easing: 'ease-out' };
    case 'slide-left':
      return { kind: 'slide', direction: 'left', distance: 100, easing: 'ease-out' };
    case 'slide-right':
      return { kind: 'slide', direction: 'right', distance: 100, easing: 'ease-out' };
    case 'scale':
      return { kind: 'scale', from: 0.8, to: 1, easing: 'ease-out' };
  }
}
```

The `easing` defaults inside each arm are overridden with the caller's
`enterEasing` before emission. The choices (`distance: 100`, `from: 0.8`)
are the canonical "subtle reveal" defaults; future task can parameterise
distance / from / to additively.

### D-T407-8. Per-element animation id generation

**Decision**: Each emitted animation gets `id: \`reveal-${revealIndex}\``
(0-indexed). If an element already has an animation with that id (caller
re-invoked `arrange_reveal` on the same slide), it would collide — but JSON
Patch `{ op: 'add', path: '.../animations/-' }` appends, so two animations
with the same id can coexist on one element (the schema does not enforce
intra-element id uniqueness; the renderer disambiguates by array order).

For collision-safety, use the same `nextAnimationId(loc.element)` strategy
as `clip-animation/handlers.ts` lines 81–93: scan existing animation ids
for `^anim-(\d+)$`, max + 1. T-407 uses the prefix `reveal-` to make the
arrangement-origin obvious in the audit trail. Function:

```ts
function nextRevealAnimationId(element: ElementWithAnimations): string {
  const animations = element.animations ?? [];
  const needle = 'reveal-';
  let max = -1;
  for (const a of animations) {
    if (!a.id.startsWith(needle)) continue;
    const tail = a.id.slice(needle.length);
    if (!/^\d+$/.test(tail)) continue;
    const n = Number.parseInt(tail, 10);
    if (n > max) max = n;
  }
  return `${needle}${max + 1}`;
}
```

When `arrange_reveal` is invoked twice on the same slide, the second
invocation gets fresh ids (`reveal-N+1`, `reveal-N+2`, ...) on each element.

### D-T407-9. Patch shape

For each element in `revealOrder` at index `i`:

```ts
const startFrame = (initialDelayFrames ?? 0) + i * (staggerFrames ?? 9);
const durationFrames = enterDurationFrames ?? 14;
const animation: Animation = {
  id: nextRevealAnimationId(element),
  timing: { kind: 'absolute', startFrame, durationFrames },
  animation: buildAnimationKind(enterAnimationKind ?? 'fade', enterEasing ?? 'ease-out'),
  autoplay: autoplay ?? true,
};
ctx.patchSink.push({
  op: 'add',
  path: `/content/slides/${slideIndex}/elements/${elementIndex}/animations/-`,
  value: animation,
});
```

One patch per element; N elements in `revealOrder` → N patches.

### D-T407-10. Reuse the existing `locateSlide` helper

**Decision**: The existing `locateSlide(ctx, slideId, requiredIds)` helper
in `handlers.ts` already handles `wrong_mode` / `slide_not_found` /
`element_not_found` resolution. T-407 calls it with
`requiredIds = revealOrder` and gets back the slide index + element-index
map. No new helper needed. The `duplicate_element_id` check is performed
**before** calling `locateSlide` (a quick `Set` size comparison).

### D-T407-11. Determinism

Pure function of input. No `Date.now()`, no `Math.random()`, no I/O.
Same input invoked twice produces deeply-equal patch sequences (verified
by a determinism test case). Mirrors the four sibling tools.

### D-T407-12. Test strategy

`handlers.test.ts` gains 7 new test cases (in a `describe('arrange_reveal', ...)` block):

1. **Happy path: 3-element fade reveal at default stagger** — emits 3
   patches, each with `op: 'add'`, path matching `.../animations/-`, value's
   `timing.startFrame` = 0 / 9 / 18, value's `animation.kind === 'fade'`.
2. **Custom stagger + initial delay** — `initialDelayFrames: 30`,
   `staggerFrames: 15`; verify startFrames are 30 / 45 / 60.
3. **Slide-up enter animation** — `enterAnimationKind: 'slide-up'`; verify
   each emitted animation has `kind: 'slide'`, `direction: 'up'`,

4. **Returns `applied` array with one entry per revealed element** — output

6. **Refuses `element_not_found`** — one id in `revealOrder` doesn't exist
   on the slide → `{ ok: false, reason: 'element_not_found' }`.
7. **Refuses `duplicate_element_id`** — `revealOrder: ['a', 'b', 'a']`
   returns `{ ok: false, reason: 'duplicate_element_id' }`.
